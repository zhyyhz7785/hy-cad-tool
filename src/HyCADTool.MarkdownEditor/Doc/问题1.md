# 二、结构问题分析

------

## ⚠️ 1️⃣ Html/ 目录存在“隐式领域逻辑”

```
Html/
  ├─ PreviewHtmlRenderer
```

问题：

PreviewHtmlRenderer 本质上不是 UI。

它是：

> Markdown → 布局 → HTML 分栏算法

这已经属于：

> Layout Domain Logic

而不是“Html 工具”。

------

### 第一性原理

你当前流程：

```
Markdown → Markdig → HTML → CSS column
```

这意味着：

- 排版完全交给浏览器
- 列数不可精确控制
- 无法计算真实几何尺寸
- 未来无法对接 CAD 精确布局

这在工程级排版是不可控的。

------

## ⚠️ 2️⃣ EditorViewModel 过重风险

你说：

> 唯一 ViewModel，管理所有参数

风险：

- 变成 God Object
- 参数调节 + 编辑 + 统计 + 命令绑定 混在一起
- 未来会 > 2000 行

典型违反：

**Single Responsibility Principle（SRP）**

------

## ⚠️ 3️⃣ Services 边界模糊

```
Services/
  ├─ PreviewManager
```

PreviewManager 现在是：

- 调度
- 统计
- 刷新
- 节流

问题：

调度逻辑属于 Application Layer
统计逻辑属于 Domain
刷新属于 UI

职责已混合。

------

## ⚠️ 4️⃣ 反射调用入口的隐患

```
EditorLauncher（静态）
```

问题：

- 静态类无法 Mock
- 无法单元测试
- 无法扩展生命周期控制

未来如果加入：

- 多实例
- 非模态
- 后台编辑

会受限。

------

# 三、Clean Architecture 审核

我们套入 Clean Architecture 四层：

```
Presentation
Application
Domain
Infrastructure
```

你现在结构大致是：

```
UI + 部分 Domain + 部分 Application
```

真正的 Domain 几乎不存在。

目前的 Domain 只有：

```
Models/
```

但这些是 DTO（数据传输对象），不是领域模型。

------

# 四、重大结构缺失（核心）

你缺：

> Document Domain Model

你现在所有逻辑围绕：

```
Markdown String
```

这是错误抽象。

正确抽象应是：

```
Document
  ├─ Block
  ├─ Heading
  ├─ Paragraph
  ├─ List
```

否则：

- 无法脱离 HTML
- 无法迁移 Blender
- 无法做精确布局

# 六、建议结构升级方案（最小代价）

不要重写。

只做 3 步。

------

## 第一步：抽出 Domain 层

新增：

```
Domain/
   ├─ DocumentModel/
   ├─ Blocks/
   ├─ LayoutEngine/
```

把：

```
PreviewHtmlRenderer
```

改为：

```
LayoutEngine + HtmlRenderer
```

拆分为：

```
MarkdownParserAdapter
LayoutEngine
HtmlRenderer
```

------

## 第二步：拆分 ViewModel

改为：

```
EditorViewModel
PreviewViewModel
ConfigViewModel
```

EditorViewModel 只协调。

------

## 第三步：PreviewManager 重构

变成：

```
IPreviewScheduler
ILayoutEngine
IPreviewRenderer
```
