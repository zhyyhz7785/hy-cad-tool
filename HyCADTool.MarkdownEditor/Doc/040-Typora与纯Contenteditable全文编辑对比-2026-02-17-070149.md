# Typora 与纯 HTML contenteditable 全文编辑对比（详细版）

## 1. 先说结论

- Typora 路线本质是：**模型驱动 + 块级增量渲染**。
- 纯 `contenteditable` 全文随便改路线本质是：**DOM 驱动 + 事后修复**。
- 在简单场景（短文、少结构）下，纯 `contenteditable` 可以很快做出“能用”的编辑器。
- 在复杂场景（分栏分页、公式、表格、稳定光标、可逆 Markdown）下，纯 `contenteditable` 维护成本会迅速上升。
- 你的项目已经有“块解析 + 布局引擎”，天然更接近 Typora 路线，应优先继续走“块级增量”而不是“全文自由 DOM”。

---

## 2. 两种路线到底差在哪

## 2.1 Typora（模型驱动）

可理解为：

```text
Markdown 文本
  -> 语法模型（AST/块树）
  -> 视图渲染（块级 DOM）
  -> 用户编辑某块
  -> 只更新受影响块（及后续少量块）
  -> 回写模型
```

核心特征：

- “真相来源”是文档模型，不是 DOM。
- 光标锚点绑定在模型位置（块 ID + offset），不是浏览器节点引用。

- 重排时尽量增量，只动必要部分。

## 2.2 纯 contenteditable 全文随便改（DOM 驱动）

可理解为：

```text
整个正文是 contenteditable
  -> 用户直接改 DOM
  -> 你再尝试把 DOM 还原为 Markdown
  -> 再做分页分栏/统计/导出
```

核心特征：

- “真相来源”实际上变成了 DOM。
- 浏览器会在编辑过程中自动注入/改写节点（`div`、`span`、`br`、样式片段）。
- 你需要大量“清洗 + 归一化 + 反向转换”逻辑。

---

## 3. 关键维度逐项对比

| 维度 | Typora 思路 | 纯 contenteditable 全文 |
|---|---|---|
| 数据主线 | 模型（AST/块树） | DOM（浏览器即时结构） |
| 光标稳定性 | 高，模型锚点可恢复 | 中/低，DOM 重建易丢光标 |
| 分栏分页重排 | 易做增量（按块顺延） | 常变全量重排，节点频繁移动 |
| Markdown 可逆性 | 强（模型可序列化） | 弱（HTML -> MD 容易丢信息） |
| 表格/列表/引用语义 | 稳定，类型明确 | 易被浏览器改写为“看起来像” |
| 撤销/重做 | 可做事务级撤销 | 多依赖浏览器原生栈，不可控 |
| 公式支持 | 作为语义节点管理 | 常被渲染节点污染，提取复杂 |
| 长文性能 | 可做局部更新 | 易出现大范围 DOM 变更 |
| 调试难度 | 中（模型可观测） | 高（DOM 状态漂移） |
| 初期开发速度 | 中 | 快 |
| 后期维护成本 | 可控 | 快速上升 |

---

## 4. 为什么“全文随便改”后期会痛

## 4.1 浏览器会帮你“改代码”

当用户按 Enter、粘贴、IME 输入时，浏览器会生成不同 DOM 结构（不同内核和时机差异明显）。  
结果是：你以为自己在编辑 Markdown，实际在追踪浏览器私有编辑行为。

## 4.2 HTML -> Markdown 不是一一映射

典型问题：

- 内联格式嵌套（粗体 + 斜体 + 代码）
- 列表缩进层级
- 表格单元格换行
- 公式节点混入渲染层 DOM

反向转换通常会出现：

- 信息丢失
- 语义偏移
- 输出不稳定（同样内容反复编辑后 diff 越来越大）

## 4.3 分栏分页场景更难

你这里不是单栏文档，而是“页 + 栏 + 尺寸约束”。  
当第一栏溢出一行，需要把后续块级联顺延到下一栏时：

- 若采用全文 DOM 自由编辑，容易触发全局重排、光标失稳。
- 若采用块级模型，能明确“谁移动、谁不动”。

---

## 5. Typora 思路真正值钱的点

- **块是原子单位**：标题、段落、列表、代码块、表格，各有边界。
- **位置可标识**：块 ID + 文本 offset，可跨重排恢复光标。
- **增量重排**：编辑块后，只让受影响块流动。
- **语义优先**：先保语义，再映射视觉，不被随机 DOM 牵着走。

这四点，正是你当前“分栏可编辑 + 溢出顺延”最需要的能力。

---

## 6. 结合你当前工程的落地判断

你当前工程已有：

- `MarkdownBlockParser.ParseTopLevelBlocks()`：块级解析
- `LayoutEngine.Distribute()`：分页分栏分配
- `PreviewHtmlRenderer`：预览渲染与交互层

这意味着你已经有 Typora 路线最难的“中台骨架”（块与布局），不应退回“纯 DOM 全文编辑”。

建议定位：

- 预览层保留 `contenteditable` 作为输入壳；
- 但内部仍按“块级单位”处理流动和回写；
- 把“全文自由 DOM”限制在最小范围（输入阶段），尽快归一到块模型。

---

## 7. 你该怎么选（实践建议）

## 7.1 推荐策略（适合当前项目）

采用“折中但偏 Typora”的方案：

1. **块级可编辑**：每栏允许编辑，但逻辑按块处理。
2. **增量级联**：溢出仅推末尾块，空位仅拉下一栏首块。
3. **统一归一化**：输入后先清洗 DOM，再回写 Markdown。
4. **稳定锚点**：维护块索引/ID，避免光标乱跳。
5. **公式特殊通道**：渲染层与源码层分离，提取时优先 TeX 源。

## 7.2 不推荐策略

- 把整页当“一个巨大 contenteditable”，再试图从最终 DOM 反推所有语义。
- 分栏重排时频繁 `innerHTML` 全量重建。
- 完全依赖 `execCommand` 作为格式主能力（浏览器兼容和可维护性都差）。

---

## 8. 一句话对比总结

- Typora：**先有文档语义，再投影成可编辑视图**。
- 纯 contenteditable 全文：**先改视图，再反推语义**。

对于“分页分栏 + 工程稳定性 + 可导出一致性”，前者明显更稳、更可持续。

---

## 9. 给你的决策建议

如果目标是“短期快出效果”，纯 `contenteditable` 很快；  
如果目标是“长期稳定演进（尤其你这种 CAD 排版一致性场景）”，应坚持 Typora 思路：**块级模型驱动，DOM 仅作表现层**。
