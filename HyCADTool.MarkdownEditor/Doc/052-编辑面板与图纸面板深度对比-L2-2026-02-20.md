# 编辑面板与图纸面板深度对比

> 目标：彻底理解两个面板的底层差异，定位光标丢失和内容回弹的根因，为后续修复提供精确的技术参考。

---

## 一、两个面板的本质区别

| 维度 | 编辑面板 (Vditor) | 图纸面板 (Flow Experience) |
|------|-------------------|---------------------------|
| 技术 | Vditor 3.10.8 (IR 即时渲染模式) | 自研 contenteditable 多栏分页系统 |
| 数据模型 | Markdown 文本（Vditor 内部维护 AST） | HTML DOM（`#source` 隐藏容器 + 可见分栏） |
| 光标管理 | Vditor 内部全权管理，宿主无需干预 | 手动 bookmark 机制（capture/restore） |
| 输入处理 | Vditor 拦截所有键盘事件，输出 Markdown | `contenteditable` 原生事件 + 手动规范化 |
| 内容提取 | `vditor.getValue()` → 纯 Markdown | `extractMarkdown()` → HTML→Markdown 逆转换 |
| 刷新方式 | 无需刷新（Vditor 自管理渲染） | `rebuildColumnsFromSource()` 重建整个分栏 DOM |

**核心矛盾**：编辑面板输出的是 Markdown，图纸面板内部操作的是 HTML DOM。两者之间的转换是有损的——Markdown→HTML→Markdown 的往返不保证幂等。

## 三、图纸面板光标管理机制详解

### 3.1 光标书签结构

图纸面板使用自研的 bookmark 机制来跨 DOM 重建保持光标位置：

```javascript
// captureCaretBookmark() → PreviewHtmlRenderer.cs:661
{
  path: [0, 2, 1],      // DOM 路径：col.childNodes[0].childNodes[2].childNodes[1]
  offset: 5,             // 文本节点内的字符偏移
  blockIndex: 3,         // data-block-index 属性值（源文档中的块序号）
  pageIndex: 0,          // 所在页码
  colIndex: 1            // 所在栏号
}
```

### 3.2 光标恢复策略（优先级从高到低）

`restoreCaretBookmark()` (PreviewHtmlRenderer.cs:698) 按以下顺序尝试恢复：

| 优先级 | 策略 | 可靠性 | 失败场景 |
|--------|------|--------|----------|
| 1 | 按 `path` 精确定位 DOM 节点 | 高 | DOM 结构变化（块被拆分/合并/移动到其他栏） |
| 2 | 按 `blockIndex` 跨栏查找 `[data-block-index=N]` | 中 | 块数量变化导致索引偏移 |
| 3 | 使用目标栏的最后一个子元素 | 低 | 光标跳到栏末尾，用户感知为"光标丢失" |
| 4 | 使用栏本身 | 最低 | 光标跳到栏开头 |

### 3.3 光标丢失的根本原因

**问题核心：`rebuildColumnsFromSource()` 会销毁并重建所有栏的 DOM。**

```javascript
// rebuildColumnsFromSource() → PreviewHtmlRenderer.cs:1506
function rebuildColumnsFromSource(){
  var blocks = collectBlocksFromSource();   // 从 #source 克隆所有块
  distributeBlocksSequential(blocks);       // 清空所有栏，重新分配块
  rebuildPreviewStats();
}
```

`distributeBlocksSequential()` (PreviewHtmlRenderer.cs:1024) 的第一步是 `resetToSinglePage()`，这会：
1. 清空所有页面的 `paper-inner`
2. 删除多余页面
3. 重新创建栏容器
4. 重新绑定事件监听器

**这意味着 bookmark 中的 `path` 指向的 DOM 节点已经不存在了。** 恢复只能依赖 `blockIndex` 回退策略，而 `blockIndex` 的精度只到块级别（段落/标题），无法精确到块内的字符位置。

### 3.4 光标丢失的触发时机

| 触发场景 | 调用链 | 光标影响 |
|----------|--------|----------|
| 用户在编辑器打字 | input → SchedulePreviewRefresh → IncrementalUpdateFlowAsync → updateSource → rebuildColumnsFromSource | bookmark 尝试恢复，但 DOM 已重建 |
| 用户在图纸中打字导致溢出 | input → debouncedColumnReflow → rebuildColumnsFromSource | 同上 |
| 配置变更（纸张大小等） | OnPropChanged → SchedulePreviewRefresh → FullNavigatePreview | NavigateToString 销毁一切 |
| 工作区模式切换 | ApplyWorkspaceMode → RefreshPreviewAsync → FullNavigatePreview | 同上 |
| 格式化操作（加粗等） | applyEditorAction → rebuildColumnsFromSource | bookmark 尝试恢复 |

## 四、内容回弹机制详解

### 4.1 什么是"回弹"

用户在图纸面板中输入文字后，内容短暂显示正确，然后突然恢复到之前的状态。

### 4.2 回弹的完整时序

```
T=0ms    用户在图纸栏中输入字符 "A"
         → input 事件触发
         → normalizeContentEditableDivs()
         → updateSourceMirrorFromColumns()  ← #source 已包含 "A"
         → debouncedColumnReflow()          ← 400ms 后检查溢出
         → notifyContentChanged()           ← 180ms 后发送到 C#

T=180ms  notifyContentChanged 触发
         → extractMarkdown()               ← 从 #source 提取 Markdown（包含 "A"）
         → hash 不同 → postHost(contentChanged)

T=180ms  C# OnPreviewWebMessageReceived()
         → TryHandlePreviewWebMessage()    ← hash 去重通过
         → ApplyMarkdownFromSource()       ← ViewModel.MarkdownText 更新（包含 "A"）
         → SyncEditorFromPreviewAsync()    ← 设置 Vditor 内容

T=180ms  ViewModel.MarkdownText 变更
         → OnPropChanged("MarkdownText")
         → RefreshOutline()                ← 仅刷新大纲，不触发图纸刷新 ✓

T=180ms  SyncEditorFromPreviewAsync()
         → _isUpdatingFromPreview = true
         → setContent(markdown)            ← Vditor 收到包含 "A" 的内容

T=~200ms Vditor input 回调触发（回声）
         → OnWebMessageReceived()
         → _isUpdatingFromPreview == true
         → ClearPendingPreviewSyncState()  ← 标志清除
         → break                           ← 不触发图纸刷新 ✓

         ★ 正常情况到此结束，不会回弹 ★
```

### 4.3 回弹发生的异常路径

**异常路径 A：Markdown→HTML→Markdown 往返不幂等**

```
T=0ms    用户输入 "A"，图纸栏 HTML: <p>Hello A world</p>

T=180ms  extractMarkdown() 输出: "Hello A world"
         → C# 收到 → ViewModel.MarkdownText = "Hello A world"

T=220ms  ★ 如果此时有其他原因触发了 SchedulePreviewRefresh ★
         （例如：OnPropChanged 中某个属性变更意外触发了 SchedulePreviewRefresh）

T=440ms  RefreshPreviewAsync(ContentInput)
         → IncrementalUpdateFlowAsync()
         → RenderFlowBodyHtml("Hello A world")
         → Markdig 输出: <p>Hello A world</p>    ← 如果一致则无问题
         → 但如果 Markdig 输出与图纸当前 DOM 有微小差异...
         → updateSource() 用 Markdig 输出替换 #source
         → rebuildColumnsFromSource()
         → 图纸内容被 Markdig 的输出覆盖
         → 如果 Markdig 丢失了某些格式 → 回弹
```

**异常路径 B：`extractMarkdown()` 的有损转换**

`blockToMarkdown()` (PreviewHtmlRenderer.cs:1365) 是一个简化的 HTML→Markdown 转换器，不支持所有 Markdown 语法：

```javascript
// 已知的有损转换：
// 1. 嵌套列表 → 只支持一级
// 2. 行内代码 → inlineToMarkdown 可能丢失反引号
// 3. 图片 alt 文本 → 可能被截断
// 4. 空行/空段落 → 使用 \u2060 占位符，可能被 Markdig 不同处理
// 5. HTML 实体 → 可能被双重编码
```

当 `extractMarkdown()` 输出的 Markdown 与原始 Markdown 不完全一致时：
1. C# 收到"不同"的 Markdown → `ApplyMarkdownFromSource` 返回 true
2. ViewModel 更新 → 可能触发 `SchedulePreviewRefresh`
3. `RenderFlowBodyHtml` 用新 Markdown 生成 HTML
4. `updateSource` 用新 HTML 替换 `#source`
5. 图纸内容被覆盖 → 回弹

**异常路径 C：快速连续输入的竞态**

```
T=0ms    用户输入 "A"
T=50ms   用户输入 "B"（notifyContentChanged 的 180ms 防抖还没触发）
T=100ms  用户输入 "C"

T=180ms  notifyContentChanged 触发
         → extractMarkdown() 输出包含 "ABC"
         → postHost(contentChanged)

T=180ms  C# 收到 → ApplyMarkdownFromSource("...ABC...")
         → SyncEditorFromPreviewAsync()
         → _isUpdatingFromPreview = true

T=200ms  用户继续输入 "D"
         → input 事件触发
         → updateSourceMirrorFromColumns()  ← #source 包含 "ABCD"
         → notifyContentChanged()           ← 180ms 后发送

T=~200ms Vditor 回声到达
         → ClearPendingPreviewSyncState()   ← _isUpdatingFromPreview = false

T=380ms  notifyContentChanged 触发
         → extractMarkdown() 输出包含 "ABCD"
         → postHost(contentChanged)

T=380ms  C# 收到 → ApplyMarkdownFromSource("...ABCD...")
         → SyncEditorFromPreviewAsync()

         ★ 到此为止正常 ★

         但如果 T=200ms 的 IncrementalUpdateFlowAsync 还在执行中...
         → updateSource() 用 T=180ms 的 "ABC" 版本覆盖了 #source
         → 图纸显示 "ABC"，用户刚输入的 "D" 丢失 → 回弹
```

### 4.4 回弹防护机制总结

| 防护层 | 位置 | 机制 | 弱点 |
|--------|------|------|------|
| JS 端哈希去重 | `notifyContentChanged()` | `simpleHash` 比较 | 32位整数哈希有碰撞风险 |
| C# 端哈希去重 | `TryHandlePreviewWebMessage()` | SHA256 比较 | 仅防重复，不防有损转换 |
| `_isUpdatingFromPreview` 标志 | `OnWebMessageReceived()` | 阻止回声触发刷新 | 依赖回声及时到达 |
| `lastSentHash` 更新 | `updateSource()` | 更新后抑制 `notifyContentChanged` | 仅在 `updateSource` 调用时生效 |
| 内容相等检查 | `ApplyMarkdownFromSource()` | 字符串精确比较 | Markdown→HTML→Markdown 不幂等时失效 |

## 六、尚未解决的问题与解决方向

### 6.1 光标定位精度不足

**现状**：`restoreCaretBookmark` 的 `path` 策略在 DOM 重建后失效，回退到 `blockIndex` 只能定位到块级别。

**解决方向**：

方案 A — **字符偏移定位**：在 bookmark 中记录光标在整个块文本内容中的字符偏移（而非 DOM 路径），恢复时用 TreeWalker 遍历文本节点定位。

```javascript
// 捕获时：
var textOffset = getTextOffsetInBlock(block, range.startContainer, range.startOffset);
bookmark.textOffset = textOffset;

// 恢复时：
var { node, offset } = resolveTextOffset(block, bookmark.textOffset);
range.setStart(node, offset);
```

方案 B — **避免不必要的 rebuildColumnsFromSource**：如果内容变更来自编辑器（而非用户在图纸中编辑），且没有溢出，可以跳过重建。

方案 C — **差量更新**：不重建整个分栏，只更新变化的块。比较旧 `#source` 和新 `bodyHtml` 的差异，只替换变化的 DOM 节点。

### 6.2 Markdown→HTML→Markdown 往返不幂等

**现状**：`extractMarkdown()` 使用简化的 `blockToMarkdown()` 转换器，不支持所有 Markdown 语法。

**解决方向**：

方案 A — **增强 `blockToMarkdown`**：补全对嵌套列表、行内代码、图片、链接等的支持。

方案 B — **保留原始 Markdown**：在每个块的 `data-*` 属性中存储原始 Markdown 文本，编辑时只更新被修改的块的 Markdown，未修改的块直接使用原始文本。

方案 C — **单向数据流**：图纸面板不再逆转换为 Markdown，而是直接操作 HTML，由 C# 端维护 Markdown↔HTML 的映射关系。

### 6.3 编辑器输入触发图纸全量重建

**现状**（已部分修复）：Flow 模式下 `ContentInput` 原因的刷新现在走 `IncrementalUpdateFlowAsync`，但 `updateSource` 内部仍然调用 `rebuildColumnsFromSource` 全量重建。

**解决方向**：

方案 A — **块级差量更新**：比较新旧 `#source` 的子元素，只替换变化的块，不重建整个分栏。

```javascript
function updateSourceDiff(newBodyHtml) {
  var temp = document.createElement('div');
  temp.innerHTML = newBodyHtml;
  var oldBlocks = Array.from(sourceRoot.children);
  var newBlocks = Array.from(temp.children);
  // 逐块比较，只替换变化的块
  // 不变的块保持原 DOM 引用 → 光标不受影响
}
```

方案 B — **仅在溢出时重建**：`updateSource` 更新 `#source` 后，检查是否有栏溢出，只在溢出时才调用 `rebuildColumnsFromSource`。

### 6.4 快速输入的竞态条件

**现状**：180ms 通知防抖 + 220ms 刷新防抖 + 400ms 重排防抖，三个定时器交错可能导致旧内容覆盖新内容。

**解决方向**：

方案 A — **版本号严格递增**：每次 `updateSource` 调用时携带版本号，JS 端拒绝低版本的更新。

方案 B — **编辑器输入不触发图纸刷新**：当图纸面板有焦点时（用户正在图纸中编辑），编辑器的 `input` 事件不触发 `SchedulePreviewRefresh`。

### 7.3 检测回弹

在 `updateSource` 的 `rebuildColumnsFromSource()` 之后，比较重建前后的文本内容：
```javascript
var before = extractMarkdown();
rebuildColumnsFromSource();
var after = extractMarkdown();
if (before !== after) {
  console.warn('[BOUNCE] content changed during rebuild!', { before: before.substring(0,100), after: after.substring(0,100) });

```
