# AutoCAD 排版路径决策与落地方案（详细版）

创建时间：2026-02-14 17:53:46  
适用项目：`hy-cad-tool`（`HyCADTool.Refactored` + `HyCADTool.MarkdownEditor`）

---

## 1. 目标与结论（先看这一节）

### 1.1 你提出的三种思路

1. AutoCAD 插件内完成排版与插入  
2. 外部先排好版，再插入 AutoCAD（你个人倾向）  
3. 选择最优路径并给出可执行实现

### 1.2 结论（推荐）

采用 **“2.5 混合架构”**：  
**外部编辑器做排版主引擎，AutoCAD 插件做轻量落图桥接。**

一句话：**以“外部排版”为主，以“CAD 内插入/回写/更新”为辅。**

---

## 2. 为什么不是纯 1 或纯 2

## 2.1 纯 AutoCAD 插件路径（方案 1）

### 优点
- 插入点、图层、样式、标注环境都在 CAD 内，交互自然。
- 用户感知为“一体化命令”，上手路径短。

### 缺点
- UI/交互开发效率低（尤其复杂编辑器、预览、回归测试）。
- 运行时依赖复杂（WebView2、热加载、DLL 搜索、版本兼容）。
- 问题定位成本高（排版逻辑与 CAD API 耦合后调试更慢）。

### 适用场景
- 文本很短、格式简单、无需复杂预览。
- 团队主要投入在 CAD 命令，不想维护独立编辑器。

---

## 2.2 纯外部排版后手工插入（方案 2）

### 优点
- 编辑体验最好（富文本、快捷键、模板、实时预览）。
- 排版引擎可独立测试，开发速度快，迭代快。
- 后续可复用到非 AutoCAD 目标（BIM、Blender、导出 PDF 等）。

### 缺点
- 若只做“手工粘贴/插入”，容易丢失 CAD 语义（图层/样式/二次编辑链路）。
- 二次编辑和批量更新体验差（文本变更后回写困难）。
- 与 CAD 图纸尺度、字宽口径容易出现偏差。

### 适用场景
- 完全把 CAD 当“最终承载容器”，无需回写与更新。

---

## 2.3 混合路径（推荐方案）

### 核心思想
- 外部：负责 **Markdown 编辑、分页/分栏计算、排版规则、回归测试**。
- 插件：负责 **插入点选择、图层/字样式绑定、XRecord 元数据、二次编辑入口**。

### 为什么更优
- 兼顾开发效率与 CAD 落图稳定性。
- 将最复杂、最常变的逻辑放在外部引擎，降低 CAD 侧改动频率。
- 能持续演进为“文档生产系统”，不止是一个命令。

## 4. 建议的目标架构（最终形态）

## 4.1 分层职责

### A. 排版核心层（Domain）
- 输入：Markdown + 配置（字号、栏数、间距、字宽参数）。
- 输出：按栏文本块 + 每栏布局统计 + 结构化元数据。
- 特点：纯 C#，不依赖 AutoCAD API，可单元测试。

### B. 编辑器应用层（MarkdownEditor）
- 负责编辑体验、预览、回归样例、配置面板。
- 输出标准化数据包（JSON 协议）。

### C. CAD 桥接层（Refactored 插件）
- 导入数据包并创建 MText。
- 统一处理图层、文字样式、插入基点、组管理、更新覆盖。
- 负责把元数据写入 XRecord。

---

## 4.2 数据协议（建议固定）

建议定义稳定协议（可命名为 `DesignSpecPackage`）：

```json
{
  "SchemaVersion": 3,
  "DocumentId": "guid",
  "Markdown": "...",
  "Config": { "...": "..." },
  "Columns": [
    { "Index": 0, "Markdown": "...", "CharsPerLine": 28 },
    { "Index": 1, "Markdown": "...", "CharsPerLine": 30 }
  ],
  "PreviewStats": { "...": "..." },
  "ContentHash": "sha256"
}
```

### 关键点
- `SchemaVersion`：后续升级兼容必备。
- `DocumentId`：跨次编辑追踪同一文档。
- `ContentHash`：检测“源码变更但未更新落图”。

## 5. 详细实施方案（按阶段）

## 5.1 Phase 1：边界收敛（1~2 天）

目标：明确“谁负责什么”，减少口径漂移。

### 任务
- 固化配置入口：`DesignSpecConfig.Normalize()` + `Validate()` 在主流程强制执行。
- 统一字宽口径：预览端与渲染端都走同一显示宽度规则。
- 明确命令职责：`hymd` 新建插入，`hymdE` 二次编辑更新。

### 验收
- 同一份 Markdown 在“预览宽度、插入宽度、更新后宽度”三处一致。

---

## 5.2 Phase 2：协议化导入导出（2~3 天）

目标：实现“外部先排版，CAD 稳定导入”。

### 任务
- 编辑器增加“导出排版包（*.hymd.json）”。
- CAD 侧新增命令（建议）：
  - `hymdI`：导入排版包并插入。
  - `hymdR`：从已选文档重渲染（不进编辑器）。
- XRecord 存储最小集合：
  - `Markdown`
  - `Config`
  - `PackageMeta`（SchemaVersion/DocumentId/Hash）
  - `GroupId`

### 验收
- 离线编辑器可独立出包。
- CAD 无编辑器依赖时，仍可导入并插图。

---

## 5.3 Phase 3：工程化增强（3~5 天）

目标：把“能用”提升为“可维护、可扩展”。

### 任务
- 建立回归样例机制（你已有 `RegressionSamples/`，继续扩展）。
- 加入差异诊断：
  - 渲染前后高度差报警
  - 栏内溢出报警
  - Hash 不一致提示
- 加“模板预设”：
  - 图纸幅面（A2/A3）
  - 企业标准字号/间距
  - 图层与样式映射

### 验收
- 发布前一键跑样例，宽度/分栏/段落映射不回退。

---

## 6. 命令层建议（用户体验角度）

建议保留 4 个核心命令，尽量简单：

1. `hymd`：打开编辑器，新建并插入  
2. `hymdE`：选中已有设计说明并编辑更新  
3. `hymdI`：导入外部排版包并插入  
4. `hymdR`：对选中说明按当前配置重排

这样可覆盖三类用户：
- CAD 内即时编辑用户
- 外部文档流用户
- 批量更新用户

## 7. 关键风险与规避

## 7.1 风险一：预览与 CAD 实际宽度不一致

### 规避
- 统一 `DisplayWidthCalculator` 规则，并把 JS 端宽度计算对齐到同算法。
- 回归样例中加入“中英混排、列表、代码块、表格”极端案例。

---

## 7.2 风险二：运行时依赖导致命令不可用（WebView2）

### 规避
- 插件层保持“导入包”兜底路径（`hymdI`），避免编辑器不可用时完全阻断业务。
- 编辑器不可用时给出明确提示，而不是吞异常。

---

## 7.3 风险三：二次编辑断链

### 规避
- 首栏实体必须写入完整元数据。
- 全部同组实体写 `GroupId`，更新时按组替换。
- 维护 `DocumentId`，避免误更新到其他组。

---

## 8. 你应当如何选择（最终建议）

你的业务是“帮助 AutoCAD 排版”，且你已在做 Markdown 体系，建议：

- **战略上**：走“外部排版主导 + CAD 插件桥接”的长期路线。  
- **短期上**：先把 `hymdI/hymdR` 补齐，形成“无编辑器也能落图”的稳定链路。  
- **中期上**：把协议与回归机制定死，减少后续反复调参的回归成本。
