# 预览与 AutoCAD 插入一致性深度研究

## 1. 目标与结论

目标：让 Markdown 编辑器预览结果与 AutoCAD 实际插入结果尽可能接近（视觉、换行、分栏、字体、特殊字符）。

结论（先给可执行答案）：

1. 当前最大偏差来源不是分栏算法本身，而是**字体体系不一致**与**MText 内联格式覆盖**。
2. 若追求“最接近预览”，推荐采用**TTF 一致性方案**（预览与插入同字体家族）。
3. 若必须保留工程 SHX，需增加“字符白名单 + 预览映射 + 不支持字符降级”三件套。
4. 现有代码中有一个高影响点：`DesignSpecService.EnsureTextStyle()` 在样式已存在时未同步更新 `FileName/BigFontFileName`，可能导致“本次配置没生效”。

---

## 2. 现状链路（代码级）

### 2.1 预览端（MarkdownEditor）

- 预览 HTML 由 `HyCADTool.MarkdownEditor/Html/PreviewHtmlRenderer.cs` 生成。
- 全局 CSS 字体当前写死：
  - `font-family:'Microsoft YaHei','Segoe UI',sans-serif`
- 预览字宽统计核心参数：
  - `TEXT_SIZE_MM`、`TEXT_X_SCALE`、`PREVIEW_SCALE`
  - `CHAR_WIDTH_MM = TEXT_SIZE_MM * TEXT_X_SCALE`
- 分栏逻辑由 JS `distribute()` 驱动（基于 DOM 高度溢出判断 + 统计回写）。

### 2.2 插入端（Refactored）

- Markdown 转 MText：`HyCADTool.Refactored/Domain/Models/Text/MarkdownToMTextRenderer.cs`
- 实体插入：`HyCADTool.Refactored/Infrastructure/AutoCAD/Services/DesignSpecService.cs`
- 文字样式来源：
  - `DesignSpecConfig.FontFileName`（默认 `tssdeng.shx`）
  - `DesignSpecConfig.BigFontFileName`（默认 `hztxt.shx`）
  - `TextXScale`

### 2.3 配置映射链路

- `EditorLoader.ConfigToContract(...)`：`DesignSpecConfig -> EditorConfig`
- `EditorLoader.ContractToConfig(...)`：`EditorResult -> DesignSpecConfig`
- 编辑器返回配置由 `EditorViewModel.BuildConfig()` 生成。

## 3. 造成“不一致”的根因清单（按影响排序）

## 3.1 根因 A：预览字体与插入字体体系不同（最高优先级）

- 预览端使用 Web 字体栈（微软雅黑/Segoe）。
- 插入端默认 SHX + BigFont（`tssdeng.shx + hztxt.shx`）。
- 这会直接导致：
  - 字形不同
  - 字宽不同
  - 同段落换行点不同
  - 特殊符号可显示性不同

## 3.2 根因 B：MText 内联格式覆盖文字样式

- 渲染器在粗体时使用 `\f` 切字体（默认 `BoldFontName = SimHei`）。
- 代码块使用 `\fConsolas|b0|i0;`。
- 这意味着同一段中可能发生字体切换；且 MText 内联覆盖优先于样式。

外部可核验资料（Autodesk Support）指出：MText 存在格式覆盖时，文本样式修改可能部分不生效。

## 3.3 根因 C：已存在样式时字体文件可能不刷新

在 `DesignSpecService.EnsureTextStyle()` 中，若样式已存在，当前仅更新：
- `TextSize`
- `XScale`

未更新：
- `FileName`
- `BigFontFileName`

影响：你改了字体配置，但图里已有样式时仍可能沿用旧字体。

## 3.4 根因 D：配置字段在编辑器回写时存在“默认值回填覆盖”

`EditorViewModel.BuildConfig()` 没有显式输出 `FontFileName/BigFontFileName/BoldFontName`，最终由 `EditorConfig` 默认值回填（`tssdeng/hztxt/SimHei`）。

影响：如果你未来想让某些图用不同字体，编辑一次后可能被默认值“带回去”。

## 3.5 根因 E：字符宽度口径存在细微差异

- 预览 JS `charDisplayUnits()` 与后端 `DisplayWidthCalculator` 在拉丁扩展段处理上不完全一致。
- 对常见中文影响较小，但对混合字符统计会出现偏差。

## 3.6 根因 F：特殊字符（如 ①②③④）受字体支持能力影响

- SHX/BigFont 对部分 Unicode 字符支持不稳定。
- 预览（Web/TTF）可见，插入（SHX）可能替代/变形/丢字。

---

## 4. 如何“保障最相近”——三层策略

## 4.1 L1（必须做）：口径对齐与样式可控

1. 修复 `EnsureTextStyle()` 的已存在分支，同步更新 `FileName`/`BigFontFileName`。
2. 预览端字体改为“由配置驱动”，不要写死微软雅黑。
3. 统一字符宽度函数（JS 与 C# 使用同一规则）。
4. 编辑器回写配置时显式携带字体字段，避免默认值静默覆盖。

## 4.2 L2（推荐做）：字符与粗体策略治理

1. 建立“不安全字符检测”：
   - 圈号数字、罕见符号、私有区字符先告警。
2. 粗体策略改为“同家族加权优先”，避免强切 `SimHei`。
3. 针对 SHX 模式，提供字符降级映射：
   - `① -> (1)`, `② -> (2)`...

## 4.3 L3（可选增强）：建立一致性回归标准

1. 增加“预览 vs 插入”回归样例集（中英混排、符号、列表、代码块、表格）。
2. 每次改动后自动生成对比报告（栏宽、换行、字符数偏差）。

## 5. 字体选型建议（你最关心）

## 5.1 方案 A：一致性优先（推荐）

适用：你最看重“预览像什么，插入就是什么”。

- 正文字体：`Microsoft YaHei UI`（或 `Microsoft YaHei`）
- 粗体：同家族 Bold（不要切到另一个字体家族）
- 代码字体：`Consolas`
- 符号兜底：`Segoe UI Symbol`

优点：
- 与 Web 预览天然接近
- Unicode 覆盖好（圈号、符号更稳）

风险：
- 图纸风格与传统 SHX 工程字有差异
- 需确保目标机器安装字体

## 5.2 方案 B：工程 SHX 优先

适用：你要兼容既有工程字体体系、历史 DWG 标准。

- 正文字体：`tssdeng.shx`
- 大字体：`hztxt.shx`（或按标准替换为 `gbcbig.shx`）
- 粗体：尽量避免跨家族切换；必要时局部 TTF

优点：
- 工程体系兼容性高

风险：
- Unicode 覆盖弱于 TTF
- 预览要做映射，否则难以做到“看起来一致”

## 5.3 方案 C：混合兼容（折中）

- 默认 SHX（工程风格）
- 对不支持字符、代码块、强调段自动切 TTF
- 预览端同时显示“字体模式标记”

适用：
- 既要工程兼容，又要减少乱码/变形

## 6. 推荐实施路线（按收益/风险）

## 阶段 1（1-2 天，低风险高收益）

1. 修复 `EnsureTextStyle()` 已存在分支字体更新。
2. 预览字体配置化（先做静态映射，不改 UI）。
3. 统一字符宽度函数（JS/C#）。

## 阶段 2（2-4 天，中风险）

1. 编辑器配置回写补齐字体字段。
2. 粗体渲染策略从“强切 SimHei”改为“同家族优先”。
3. 特殊字符检测与告警提示。

## 阶段 3（1 周，体系化）

1. 建立一致性回归样例库与验收指标。
2. 引入“字符降级规则”和报告输出。

---

## 7. 一致性验收标准（建议采用）

1. 同一文档同一参数下，预览与插入的段落换行差异 <= 1 行/每 1000 字。
2. `CharsPerColumn` 与最终落图可容纳字符偏差 <= 5%。
3. 粗体段落不出现跨行字体突变（除显式策略外）。
4. 特殊字符的“可显示率”>= 99%，不可显示字符必须有告警或降级。
5. 更换字体后，旧样式更新生效（不允许“看似修改、实际未生效”）。

---

## 8. 你可以立即执行的操作（不改代码也有效）

1. 明确你的目标模式（A 一致性优先 / B 工程 SHX 优先）。
2. 若选 A：统一全链路使用同一 TTF 家族，并禁用跨家族粗体。
3. 若选 B：尽量避免在 Markdown 使用圈号数字和非常规 Unicode。
4. 固定一套“标准测试文档”，每次发布前做 `C2 -> C1` 目检回归。
