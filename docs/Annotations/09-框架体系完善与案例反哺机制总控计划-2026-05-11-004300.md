# 09 - 框架体系完善与案例反哺机制总控计划

> 本文不是新案例，而是**整个 docs/Annotations 体系的总控文档**。
>
> **背景判断（用户原话）**：
> > "我需要的是 01-04 文档，需要框架；05-08 只是框架中的一点点内容，我需要完善框架体系，然后不断补充类似 05-08 的例子去优化框架。"
>
> 09 要回答 4 个问题：
> 1. 01-04 现有框架是什么样？哪里是支柱、哪里是缺口？
> 2. 05-08 这 4 个案例反哺出了哪些"框架级"修订点？
> 3. 接下来要建立什么"案例 → 框架"的标准反哺机制，让未来的 N 个案例自然补完框架？
> 4. 接下来 6~12 个月要写哪些文档？怎么编号？怎么写？

---

## 0. 一句话定位

> **01-04 是"四根柱子"的框架毛坯；05-08 是"贴在柱子上的瓦片"。09 的任务是：盘点柱子、清点瓦片、规定铺瓦次序、规定每片瓦上墙后必须把柱子补一颗钉子的工序——让框架与案例双向加固。**

## 1. 框架现状全景：01-04 是什么样、缺什么

### 1.1 一张图看 01-04 的关系

### 1.2 四根柱子的覆盖盘点

| 柱子 | 强项（已建立） | 缺口（待补） |
|---|---|---|
| **01 What** | 8 个软件族对比表；13 字段注释模型；7 标准映射；2D / 3D 模块清单 | **没有"模式（pattern）字典"**；只列字段，不列"哪些字段一起出现构成什么模式"；几何/属性/注释三层关系停留在表格层面 |
| **02 How / Why** | 符号学三元；Icon/Index/Symbol 三类；视觉重量铁律；L0-L5 分级；6 个 Domain 接口；生命周期 7 状态 | **接口契约没说"案例如何上提到接口"**；L0-L5 没给每级的"判定准则"；6 个接口之间的协作关系（流向图）缺失 |
| **03 Optimal** | 形式化为 \(A^*=\arg\max_{A\in\mathcal{A}(M)} Q(A;M,C,U)\)；Q 拆 6 维；约束分硬/软；S1-S4 求解阶梯；MVP 钢筋编号 | **Q 没有"原子规则字典"**——6 维太抽象，下面没有可调用的规则原子；**S1 阶梯不完整**——05 / 06 已发现 S1 还有"S1a 解析式直接派生"子型，03 表里没有 |
| **04 Roadmap** | 三个月计划；六个月目标；Step 0；ClusterPanel 第一战场；MVP 范围；评分函数草案 | **没有"反哺日志"机制**——v1.1 已经因 ClusterPanel 现状校正了一次（地脚螺栓 → 点聚类引擎），但下次案例落地时没有标准动作回头修订 04；**没有文档号段规划**——10 之后该怎么编不清楚 |

### 1.3 四根柱子之间的"接缝"

01-04 互称"互补不重叠"，但它们之间的**接缝**（同一概念在不同文档怎么连续）也有缺口：

| 接缝 | 现状 | 问题 |
|---|---|---|
| 01 §5 字段表 ↔ 02 §10 接口契约 | 字段→接口的映射隐含，不显式 | 新增字段时不知道是否要新增接口 |
| 02 §10 接口契约 ↔ 03 §3 Q 6 维 | 6 维 Q 与 6 接口同号但**不一一对应** | 容易让人误以为 `IAnnotationQualityFunction` 就负责 6 维；实际 Q 6 维分散在多个接口里 |
| 03 §5 求解阶梯 ↔ 04 §10 技术路线 | 03 列 S1-S4，04 列阶段 0-4，**两个阶段表互不对照** | 不同视角描述同一件事，读者拼不出"现在到了哪一阶段" |
| 04 §6 系统模块 ↔ 02 §10 接口 | 04 列 8 模块，02 列 6 接口，**模块 ≠ 接口** | 实施时不知道按 04 模块切还是按 02 接口切 |

→ **这 4 道接缝是 09 要修补的核心。**

### 2.2 反哺信号的元结构

通用模式：

```text
[案例 N] 解决某个具体问题 X
  ↓ 写作过程中发现
  ↓
[反哺信号] 框架文档某节 Y 的"覆盖度 / 完备性 / 准确性"出问题
  ↓ 通常表现为
  ↓
  - "X 不该归到 Y 列出的某类，因为 ..."（覆盖不全）
  - "Y 列了 N 项，但 X 表明应该是 N+1 项"（穷举不完）
  - "Y 描述方式适用于 X' 但不适用 X"（描述精度不够）
  - "Y 与 Z 节的关系，X 暴露了它们的接缝"（结构性接缝）
```

**任何案例写完，都应该交一份「反哺清单」**——这是 §3 要建立的反哺机制核心动作。

## 3. 反哺机制：让案例自动补完框架的 6 条工艺规程

### 3.1 工艺 #1：文档号段规划

```text
01 ~ 09  → 框架层（毛坯 + 总控；本号段不再扩张）
10 ~ 19  → 框架补丁层（-bis 修订；每篇对应一个具体反哺点）
20 ~ 99  → 案例层（按子领域分批；每篇用三段式：诊断 / 工单 / 验收）
100+     → 二阶整合（如"命令成熟度模型 v2"，由多个案例聚合而成）
```

| 号段 | 命名风格 | 示例 |
|---|---|---|
| 10-19 | `1X-bisYY-框架补丁主题-时间戳.md` | `10-bis03-范式表ABC修订-...md` |
| 20-99 | `XX-子领域-案例主题-时间戳.md` | `20-DimDDS-XXX-...md` / `30-Cluster-XXX-...md` / `40-Pile-XXX-...md` |

> **重点**：10-19 不是"01-09 的全面重写"，而是**单点修订补丁**。每个补丁只钉一颗钉子，让框架修订可以**渐进、可追溯、可回退**。

### 3.2 工艺 #2：案例文档三段式

任何**业务命令 / 子模块 / 算法引擎**的入框工作，都按 06 / 07 / 08 已经验证过的三段式：

| 段 | 文档类型 | 必备内容 | 输出物 |
|---|---|---|---|
| **诊断** | "深度解析" | 算法骨架 / 范式归类 / 技术债清单 / 反模式标记 | 06 |
| **工单** | "实施计划" | 范式定位 / Phase 化路线 / 接口选型 / 不变项 | 07 |
| **验收** | "对比总结" | N 维量化矩阵 / 关键决策 / 用户原话校正 / 后续路线 | 08 |

→ 三段式是**最小可入框架的案例单元**。只写"对比"不写"诊断"=空中楼阁；只写"诊断"不写"验收"=半成品。

### 3.3 工艺 #3：每篇案例必须提交"反哺清单"

强制段落（放在文档末尾「反哺清单」节）：

```markdown
## N. 反哺清单（框架修订建议）

| # | 反哺命题 | 应回填章节 | 优先级 |
|---|---|---|---|
| R-XX | 一句话命题 | 01 §X / 02 §X / 03 §X / 04 §X | P0/P1/P2 |

> 这些条目会被并入 docs/Annotations/09 的 §2.1 主清单。
```

→ 09 §2.1 表是"反哺总账"，每篇案例只增不删。

### 3.4 工艺 #4：每个 -bis 补丁的发布动作

写一个 `1X-bis...` 文档时，**同步**做 3 件事：

1. 在被补丁的原文档（01/02/03/04）末尾的「修订记录」追加一行：
   ```markdown
   - vN.M (YYYY-MM-DD)：§X.Y 已被 [10-bisXX](./10-bisXX-...md) 修订，新增范式 C 一行
   ```
2. 在 09 §2.1 反哺总账里把对应行的「当前状态」改为 **「已回填 → 见 10-bisXX」**。
3. **不删除原文档原文**——保留历史，方便看演化路径。

### 3.5 工艺 #5：案例毕业判定（来自 R8）

一个案例什么时候算"完结、可以从待办清单移除"？满足全部 4 条：

1. 三段式齐全（诊断 + 工单 + 验收）
2. 反哺清单已提交，且 09 §2.1 已收录
3. 对应代码已在生产环境跑过 ≥ 1~2 周（金标 / 用户主动反馈无问题）
4. 至少触发了 1 次框架补丁（10-19 至少新增 1 篇）

→ 不满足任意一条 → 案例处于「在途」状态，不算完结。

### 3.6 工艺 #6：每月一次"框架体检"

每月 1 号，统一动作：

- 翻一遍 09 §2.1 反哺总账，统计「已回填 / 在途 / 未回填」三栏比例
- "未回填"超过 30% → 触发"框架补丁周"，把 10-19 的待写补丁集中清空
- 翻一遍 §4 路线图，对照"做了什么 / 没做什么"，更新优先级

→ 这是防止"反哺机制空转"的兜底节奏。

## 6. 反哺工作流（标准操作图）

```text
                  ┌───────────────────┐
                  │ 用户提需求 / 改命令 │
                  └─────────┬─────────┘
                            ▼
                  ┌───────────────────┐
                  │  写诊断（XX 号段第 1 篇）  │
                  │  → 强制识别范式 (A/B/C) │
                  │  → 强制列技术债清单     │
                  └─────────┬─────────┘
                            ▼
                  ┌───────────────────┐
                  │  写工单（XX 号段第 2 篇）  │
                  │  → 强制 Phase 化         │
                  │  → 强制不变项           │
                  └─────────┬─────────┘
                            ▼
                  ┌───────────────────┐
                  │  实施（代码 + 测试）       │
                  │  → 命令行日志按 NewDDS 模板 │
                  │  → 金标基线（如适用）       │
                  └─────────┬─────────┘
                            ▼
                  ┌───────────────────┐
                  │  写验收（XX 号段第 3 篇）  │
                  │  → 强制 9 维量化矩阵     │
                  │  → 强制反哺清单 (R-XX)   │
                  └─────────┬─────────┘
                            ▼
                  ┌───────────────────┐
                  │  09 §2.1 反哺总账登记     │
                  │  → 决定是否触发 -bis 补丁 │
                  └─────────┬─────────┘
                            ▼
                  ┌───────────────────┐
                  │  生产 1~2 周 + 用户回声   │
                  │  → 满足毕业判定 → 完结    │
                  │  → 不满足 → 回到诊断      │
                  └───────────────────┘
```

→ 这条流是**强制路径**，不允许跳过任一节点（除非案例足够小，可以 1 篇文档合并三段，但必须显式标注「合并版」）。

## 8. 与未来 AI 协作的关系（接 04 §15 第 1 条）

09 反哺机制天然适配 AI 协作流：

| AI 任务 | 需要的元数据 | 09 提供的支持 |
|---|---|---|
| 写新案例诊断 | 范式表 + 反模式字典 + 代码味道字典 | 10-bis03 / 13-bis02 / 14-bis02 |
| 写新案例工单 | Phase 化模板 + 接口契约 + 不变项 | 15-bis04 / 12-bis02 |
| 写新案例验收 | 9 维矩阵 + 毕业判定 | 17-命令成熟度模型 / 16-bis04 |
| 框架审计 | 反哺总账 + 接缝映射 | 09 §2.1 / 19-接缝整合 |
| 反哺登记 | 标准模板 (R-XX 行) | §3.3 工艺 #3 模板 |

→ 任何后续 AI 写文档时，**只需读 09 + 命中的 -bis 补丁 + 该子领域已有案例**，即可遵守全套规约。这是 09 作为"总控"的关键价值——**让人和 AI 共用一套工艺规程**。

## 9. 风险与对应

| 风险 | 应对 |
|---|---|
| 框架补丁越写越多，最后 10-19 不够用 | 启用 100+ 二阶整合，把 10-19 多个 -bis 合并为 100、101 …… |

| 案例三段式太重，小命令写不动 | 显式允许"合并版"（1 篇文档分 3 节即可），但毕业判定不放宽 |
| 框架文档与 -bis 补丁冲突 | 永远以 -bis 为准；原文档的「修订记录」段是路标 |
| AI 协作时不读 09 直接写 | 把 09 设为 `.cursor/rules/` 强引用 / 在每篇新文档头部强制 `> 入框前请先读 09` |
