## 1. 核心判断

未来工程软件会被 AI 大幅改写，但替代顺序并不一样：

| 层级 | AI 替代难度 | 原因 | HyCAD 机会 |
|---|---:|---|---|
| 模型构建 | 高 | 真实世界对象复杂，设计意图不完整，输入经常模糊，错误成本高 | 先做辅助，不做完全自动 |
| 模型属性识别 | 中 | 对象一旦成型，可通过几何、图层、参数、规则推断属性 | 可作为注释生成的上游 |
| 注释 / 符号生成 | 低到中 | 约束强、标准多、目标明确、评价可计算 | 最适合作为第一突破口 |
| 图纸表现优化 | 中 | 需要兼顾可读性、标准、客户偏好、图纸密度 | 可用规则 + 搜索求近似最优 |
| 校审 / 漏标检查 | 中 | 依赖规则库和对象语义，难点在业务覆盖 | 与注释系统天然绑定 |

关键判断：

**模型一旦完成，就不再是“未知图形”，而是一组结构化数据。注释与符号不是自由创作，而是在强约束下寻找最优表达。**

这件事目前行业内做得不充分，不是因为理论上很难，而是因为大多数软件把“建模”和“出图注释”当成两个割裂环节：模型负责对象，注释负责人工表达，中间缺少一个可优化的语义层。

## 2. 对未来软件的定义

未来工程软件不应只是 CAD、BIM、CAE 或三维建模器，而应是一个“客观世界表达系统”：

```text
客观世界
  ↓ 采集 / 设计 / 建模
模型数据：几何 + 属性 + 关系 + 状态 + 不确定性
  ↓ 规则 / AI / 优化
表达数据：注释 + 符号 + 标签 + 表格 + 视图
  ↓ 图纸 / 三维场景 / 报告 / 审查
人类决策
```

软件的核心能力不再是“画出对象”，而是：

1. 把客观对象变成可计算模型。
2. 把模型属性变成可读表达。
3. 把表达效果在不同客户、规范、图纸条件下优化到接近最优。
4. 让表达结果可追溯、可校核、可重生成。

其中第 3 点就是 HyCAD 的切入点。

---

## 3. 为什么注释 / 符号比建模更适合先做

建模阶段存在大量开放问题：

- 对象可能未知：软件不知道用户想表达梁、板、钢筋、螺栓、设备、道路还是临时构造。
- 设计意图不完整：几何只是结果，不一定包含为什么这样设计。
- 输入噪声大：旧 DWG、手工图层、块名混乱、线段断裂、比例不统一。
- 责任风险高：AI 直接生成结构模型，错误会进入设计本体。

注释 / 符号阶段则不同：

- 模型已经存在，对象边界和属性大多已知。
- 注释目标明确：让人看懂、施工、审核、统计。
- 规范约束强：字高、线宽、图层、符号、编号、引线、标注位置都有规则。
- 可评价：是否重叠、是否漏标、是否过密、是否符合客户样式，都能写成评分函数。
- 可人工兜底：系统给推荐结果，用户可局部调整，不会破坏模型本体。

因此，HyCAD 的第一阶段不应追求“AI 自动建模一切”，而应追求：

**给定已有模型，自动生成并优化注释 / 符号 / 表格。**

## 4. 形式化定义：注释生成是一个优化问题

可以把注释系统定义为：

```text
输入：
M = 模型数据（几何、属性、关系、状态）
V = 视图上下文（比例、范围、剖切、图纸空间、打印要求）
R = 规则集（国家规范、行业标准、客户标准、项目约定）
P = 偏好集（客户偏好、设计院习惯、图纸风格）
C = 客观条件（图纸密度、空间冲突、对象数量、阅读优先级）

求：
A* = 最优注释集合

目标：
A* = argmax Score(A | M, V, R, P, C)

约束：
1. 注释必须绑定正确对象。
2. 注释必须符合符号和制图标准。
3. 注释不得遮挡关键几何。
4. 同类信息必须风格一致。
5. 图纸密度必须可读。
6. 用户修改后系统必须能追踪来源。
```

这说明注释生成不是“让 AI 随便画”，而是一个强约束布局和表达优化问题。

AI 的位置应放在三个地方：

1. **识别语义**：从混乱 DWG 或旧图中猜测对象类型和属性。
2. **补全规则**：根据客户样例推断偏好，如引线方向、编号格式、表格样式。
3. **解释冲突**：告诉用户为什么某个标注无法自动放置，或为什么建议调整。

真正落地时，核心仍应是确定性规则、评分函数和可复现的布局算法。

## 5. 核心产品目标

HyCAD 的目标不是再做一个“标注命令合集”，而是做一个：

**面向工程模型的注释与符号优化引擎。**

它的最小闭环：

```text
选择对象 / 识别对象
  ↓
读取几何 + 属性
  ↓
匹配注释意图
  ↓
套用符号模板
  ↓
自动布局 / 避让 / 排序
  ↓
评分
  ↓
写入 DWG + 语义绑定
  ↓
对象变化后可校核 / 可重生成
```

用户感知到的功能可以很简单：

- “给这些钢筋自动编号并避让。”
- “给这些地脚螺栓自动生成编号、引线和统计表。”
- “给设备基础自动生成轴线、尺寸、坐标和螺栓表。”
- “按甲方 A 的风格出图。”
- “检查这张图哪里漏标、重叠、样式不统一。”

底层却是同一套模型：

`ObjectGraph + AnnotationIntent + SymbolTemplate + StyleRule + LayoutOptimizer + AnnotationStore`

## 6. 系统模块

| 模块 | 职责 | 第一阶段落地方式 |
|---|---|---|
| `ObjectGraph` | 统一描述对象、属性、关系 | 从现有 DWG Entity / XData / 命令结果抽取 |
| `AnnotationIntent` | 描述“需要表达什么” | 编号、尺寸、材料、标高、坐标、状态 |
| `SymbolTemplate` | 标准化符号模板 | 标高、轴号、钢筋、螺栓、剖切、详图索引 |
| `StyleRule` | 客户和项目样式 | 字高、线宽、颜色、图层、箭头、比例 |
| `LayoutOptimizer` | 自动放置与避让 | 先做 2D 候选点评分，不做复杂 AI |
| `AnnotationStore` | 持久化语义绑定 | DWG Entity + XData + JSON 镜像 |
| `Validator` | 校核与冲突检测 | 漏标、重叠、孤儿注释、样式冲突 |
| `PreferenceLearner` | 客户偏好学习 | 初期手工配置，后期由样例图归纳 |

## 6.5 现状审计：ClusterPanel 已经覆盖了哪些模块（v1.1 新增）

### 6.5.1 模块覆盖度

| 模块 | ClusterPanel 现状 | 覆盖度 | 缺口 |
|---|---|---:|---|
| `ObjectGraph` | `ClusterInputService` 按图层语义识别 5 类点 + 轴线 | 70% | 仅 5 类点；新对象类型需要硬编码图层规则 |
| `AnnotationIntent` | "X 向尺寸 / Y 向尺寸"两类隐式意图 | 30% | 意图未抽象成对象；无法增加"编号 / 标高 / 引线"等其他意图 |
| `SymbolTemplate` | `RotatedDimension` + 图层 + DimStyle | 50% | 只有尺寸一种符号；轴线圆 / 区域文字是 hard code |
| `StyleRule` | 图层名走 `UserLayerNameResolver`、字高走 Scale | 40% | 客户样式未参数化；仅"方案 1/2/3"三套预设 |
| `LayoutOptimizer` | DBSCAN 长方形邻域聚类 + `FilterDuplicateDimensions` 去重 | 60% | 无评分函数；无候选位置选择；无避让度量 |
| `AnnotationStore` | 直接写 Dimension 实体 | 10% | **未写 XData 绑回点集**；无对象 → 注释反查能力 |
| `Validator` | 命令行最后输出"完成" | 5% | 漏标 / 重叠 / 孤儿注释一概不报 |
| `PreferenceLearner` | 方案 1/2/3 手工配置 | 20% | 无命名语义；无样例归纳；无反馈学习 |

**结论**：`LayoutOptimizer` 已是雏形，`AnnotationStore` / `Validator` / `PreferenceLearner` 是最薄弱环节，正好对应 03 §3 提到的 Quality 评分、生命周期管理、Profile 化三个突破口。

### 6.5.2 算法语义校正

| 项 | 文档/代码现状 | 实际语义 | 建议处置 |
|---|---|---|---|
| `Domain/Services/ClusteringService.cs` | 注释写"BFS（广度优先搜索）"，提供 `ClusterByPointDistance`（圆形邻域 maxDistance） | **未被任何调用方使用，是死代码** | 标记 `[Obsolete]` 或删除；保留概念到 doc 即可 |
| `ClusterFactoryService.GetNeighborIndices` | 注释笼统写"DBSCAN" | 实际是 **DBSCAN with 长方形邻域**（`|dx|≤εx/2 ∧ |dy|≤εy/2`） | 改注释为"长方形邻域 DBSCAN"，避免把它和经典圆形 DBSCAN 混淆 |
| `ClusterConfig.EpsilonX/EpsilonY` | UI 上"X方向聚类参数: EpsilonX / EpsilonY"+"Y方向聚类参数: EpsilonX / EpsilonY"，名字撞车 | 实际是"邻域宽 / 邻域高"，X 向方案是宽长方形（找水平共线点），Y 向方案是高长方形（找垂直共线点） | UI 改名"水平半径 / 垂直半径"或"行内容差 / 列内容差"；ClusterConfig 加 XML 注释明确"邻域是长方形而非圆形" |
| `MinPoints` | UI 默认 1，等于关闭噪声过滤 | DBSCAN 核心点判断真的工作（`pointClusterMap[i] = -1`） | 默认改为 2 或 3；加提示文案"低于此值视为噪声点不形成簇" |
| `FilterDuplicateDimensions` | 同行/同列偏置接近的标注保留 First() | **粗暴去重，可能保留短的丢长的** | 改为按 `XLine1Point ↔ XLine2Point` 距离的最大者优先；保留被淘汰列表写入诊断日志 |

### 6.5.3 链路总结（已打通的部分）

```text
选择集
  ↓ ClusterInputService.GatherInput            [对象识别]
5 类点 + 轴线
  ↓ AxisAnalysisService.AnalyzeAxes            [轴线分析 + 区域划分 + 点分区]
PointsMap (按区域分组)
  ↓ ClusterFactoryService.CreateClusters       [DBSCAN 长方形邻域，X 向 / Y 向各一遍]
ClusterResult[]  (含 Envelope / ExpandedEnvelope / ConvexHull / AuxiliaryPoints)
  ↓ DimensionService.BuildDimensionsByRegion   [按方向连续标注 + 跨区域去重]
RotatedDimension[]
  ↓ ClusterDrawService.Draw                    [按开关写入 DWG]
DWG 实体
```

这条链路已经对应 04 §5 的 7 个步骤里的前 5 个。差的两步（"评分"和"写 XData 绑回 + 重生成"）正是 v1.1 要补的核心。

## 7. 第一战场选择

不建议一开始做通用注释平台。第一战场应满足四个条件：

1. 对象类型明确。
2. 注释规则强。
3. 当前人工工作量高。
4. 生成效果容易评价。

推荐优先级：

| 优先级 | 场景 | 原因 |
|---:|---|---|
| 1 | 地脚螺栓编号 + 引线 + 表格 | 对象明确，已有 XData 基础，符号规则强 |
| 2 | 钢筋编号 / 钢筋尺寸标注 | 已有命令多，重复劳动高，适合上提成规则 |
| 3 | 设备基础轴线 / 坐标 / 螺栓表 | 表格和注释联动价值高 |
| 4 | 标高 / 剖切 / 详图索引 | 符号标准化强，但业务闭环较小 |
| 5 | 通用图纸漏标检查 | 价值大，但依赖前面对象语义积累 |

建议第一版 MVP 选择：

**地脚螺栓注释优化器。**

原因：

- 已有 `AnchorBolt` 和 `ExtensionDictionaryService`，对象语义比普通线段清楚。
- 编号、引线、表格是天然的注释系统闭环。
- 可以快速验证“对象数据 → 注释生成 → 表格 → 校核 → 重生成”的完整路线。
- 客户差异主要体现在编号格式、表格字段、引线样式，适合做 `StyleRule`。

## 8. MVP 范围

### 8.1 MVP 不做什么

第一版明确不做：

1. 不做全图 AI 自动理解。
2. 不做通用自然语言出图。
3. 不做 3D 注释。
4. 不做所有符号库。
5. 不强行改造所有旧命令。
6. 不追求一次生成完全完美。

### 8.2 MVP 必须做什么

第一版必须形成闭环：

1. 读取一组已知对象。
2. 生成对象级注释意图。
3. 根据样式规则生成候选符号。
4. 根据评分函数选择放置位置。
5. 写入 AutoCAD Entity。
6. 写入 XData 或 JSON 绑定来源。
7. 支持重新生成。
8. 支持基础校核：漏标、重叠、孤儿注释。

### 8.3 MVP 成功标准

成功不是“AI 很智能”，而是：

| 指标 | 标准 |
|---|---|
| 人工点击次数 | 比现有流程减少 50% 以上 |
| 注释一致性 | 同类对象编号、引线、图层、字高完全一致 |
| 可重生成 | 修改样式后可批量刷新 |
| 可追溯 | 每个注释知道来自哪个对象 |
| 可校核 | 能列出漏标、重叠、孤儿注释 |
| 可扩展 | 第二个业务场景不需要重写底层 |

## 9. 评分函数草案

布局优化的关键不是一开始用复杂算法，而是先定义“什么叫好”。

一个可执行的评分函数：

```text
Score = 
  30% 对象绑定正确性
+ 20% 可读性
+ 15% 避让效果
+ 15% 样式一致性
+ 10% 客户偏好匹配
+ 10% 图纸紧凑度
- 冲突惩罚
- 遮挡惩罚
- 超出视图惩罚
- 引线穿越惩罚
```

第一版可用简单候选点搜索：

1. 对每个对象生成若干候选注释位置。
2. 排除明显非法位置。
3. 对候选位置打分。
4. 按对象优先级逐个放置。
5. 放置后更新占用区域。
6. 若冲突不可避免，标记为“需人工确认”。

这已经足以超过大量人工标注流程。

## 10. 技术路线

### 阶段 0：统一概念

产出：

1. `AnnotationIntent`：表达需求。
2. `AnnotationCandidate`：候选结果。
3. `AnnotationScore`：评分明细。
4. `AnnotationBinding`：注释与对象绑定。
5. `ClientStyleProfile`：客户样式配置。

目标：先把“要表达什么”和“怎么画出来”分离。

### 阶段 1：地脚螺栓试点

产出：

1. 螺栓对象读取。
2. 自动编号规则。
3. 引线候选点生成。
4. 表格字段规则。
5. 一键生成 / 重生成。
6. 漏标和孤儿注释检查。

目标：跑通对象到注释的完整闭环。

### 阶段 2：钢筋试点

产出：

1. 钢筋对象识别或拾取。
2. 编号、尺寸、间距、锚固文字自动派生。
3. 钢筋注释避让。
4. 同类钢筋合并标注。

目标：验证复杂图纸密度下的布局能力。

### 阶段 3：客户样式系统

产出：

1. 客户配置文件。
2. 样式切换后批量重绘。
3. 样例图偏好提取。
4. 项目级样式锁定。

目标：把“不同客户表现效果”变成可配置、可求解的问题。

### 阶段 4：AI 辅助

产出：

1. 从旧图识别对象类型。
2. 从客户样例归纳样式偏好。
3. 对冲突结果给解释和建议。
4. 自动生成规则草案，由用户确认。

目标：AI 不替代规则引擎，而是降低建模、配置、校核的门槛。

## 11. 关键护城河

真正的壁垒不是“会调用大模型”，而是：

1. **工程对象库**：螺栓、钢筋、标高、轴线、设备基础等对象语义积累。
2. **符号模板库**：每类工程符号的参数化模板。
3. **客户样式库**：不同单位、项目、地区的表达偏好。
4. **评价函数库**：什么叫清楚、规范、紧凑、好看。
5. **语义绑定能力**：注释不是死图元，而是对象表达的一个视图。
6. **重生成能力**：改模型、改规则、改客户样式后能稳定更新。

这些能力一旦积累，通用 AI 很难直接替代，因为它缺少项目内部的对象语义、客户偏好和历史表达数据。

---

## 12. 为什么现在值得做

现在切入有三个现实优势：

1. HyCAD 已经积累了大量工程命令，不是从空白开始。
2. AutoCAD 图纸仍是工程交付核心，注释自动化有直接价值。
3. AI 正在降低语义识别和规则归纳成本，但工程表达仍需要确定性系统兜底。

最佳策略不是等 AI 完全成熟，而是先建立：

```text
确定性注释引擎
  + 工程对象语义
  + 客户样式规则
  + 可评分布局
  + AI 辅助识别 / 归纳 / 解释
```

这条路线既不冒进，也不会错过 AI 带来的窗口期。

## 13. 三个月核心计划

### 第 1 个月：抽象与试点准备

1. 定义注释引擎最小 Domain 模型。
2. 选择地脚螺栓作为试点。
3. 梳理现有 `AnchorBolt` 数据来源。
4. 定义编号、引线、表格的 `AnnotationIntent`。
5. 写第一版 `ClientStyleProfile`。

交付物：能从螺栓对象生成结构化注释意图。

### 第 2 个月：自动生成与布局

1. 实现候选点生成。
2. 实现避让和评分。
3. 写入 MLeader / Text / Table。
4. 写入 XData 绑定关系。
5. 支持一键重生成。

交付物：一键生成螺栓编号、引线、表格。

### 第 3 个月：校核与产品化

1. 漏标检查。
2. 重叠检查。
3. 孤儿注释检查。
4. 样式切换后重绘。
5. 面板化配置。
6. 与现有 C1 测试入口打通。

交付物：一个可演示的“地脚螺栓注释优化器”。

## 14. 六个月目标

六个月内不追求大而全，而追求形成平台雏形：

1. 地脚螺栓注释优化器可用。
2. 钢筋编号 / 引线 / 尺寸进入同一注释引擎。
3. 至少支持 2 套客户样式。
4. 支持注释重生成。
5. 支持基础校核报告。
6. 老命令保持可用，新命令逐步走注释引擎。

达到这一步后，HyCAD 将不再只是命令集合，而开始具备“规则化出图平台”的雏形。

---

## 15. 最重要的原则

1. **先规则，后 AI**：AI 负责降低输入成本，不负责不可解释地决定工程表达。
2. **先对象，后注释**：没有对象语义，就没有可靠注释。
3. **先一个闭环，后多个场景**：地脚螺栓跑通后再扩钢筋、标高、轴线。
4. **先可重生成，后智能优化**：不能重生成的自动标注只是一次性画图命令。
5. **先客户样式，后通用平台**：不同客户的表达偏好是产品价值，不是边角配置。
6. **先评分函数，后复杂算法**：先定义什么叫好，再谈搜索、AI 或优化。
7. **先允许人工确认，后追求全自动**：工程软件的第一目标是可靠，不是炫技。

---

## 16. 一句话路线

HyCAD 的未来注释系统应从“画符号的工具”升级为：

**给定工程模型和客户约束，自动求解最优工程表达的规则化注释平台。**

这条路的起点不是通用 AI 建模，而是先把模型完成后的注释、符号、编号、表格、校核做成可规则化、可评分、可重生成的系统。
