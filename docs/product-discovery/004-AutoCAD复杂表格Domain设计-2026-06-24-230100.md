# AutoCAD 复杂表格工具 Domain 设计与实现路径

> 文档编号：004  
> 生成日期：2026-06-24  
> 输入样例：`h:\person\环宇\20251010——人员基本情况表(1).doc`（旧 `.doc` 二进制格式，本次未解析正文，仅作为复杂表格样例来源）  
> 目标：设计一个以 Domain 为核心的复杂表格系统，可应用于 Markdown、AutoCAD，并可与 Excel 转换。

---

## 0. 核心结论

这不是一个单纯的 AutoCAD 表格插件，而应当先做成一个**平台无关的复杂表格 Domain 引擎**。

它的核心能力分为两层：

- **表格结构层**：像 Word 一样支持复杂表格，包括合并、拆分、斜线表头、嵌套式视觉分区、复杂边框。
- **表格数据层**：像 Excel 一样支持基础数据填充、简单公式、批量复制、序列填充、导入导出。

AutoCAD、Markdown、Excel 都不直接拥有“最终真相”。真正的真相是 Domain 中的 `TableDocument / TableGrid / Cell` 模型，各个平台只是不同的渲染器与适配器。

---

## 1. 产品定位

### 1.1 一句话定位

为工程制图人员提供一个**Word 级复杂表格排版 + Excel 级基础数据处理 + AutoCAD 图形化落地**的统一表格工具。

### 1.2 为什么不能只做 AutoCAD 原生表格增强

AutoCAD 原生 Table 更接近“绘图实体”，不适合作为复杂编辑的核心数据模型：

- 编辑体验不适合密集录入。
- 复杂合并、斜线表头、分割单元格、跨平台导出都难以统一表达。
- 一旦把 AutoCAD Table 当作核心模型，Markdown 与 Excel 适配会被 AutoCAD 的限制反向绑住。

所以应当反过来：

> **Domain 是真表格；AutoCAD 只是其中一个显示/编辑外壳。**

## 2. 总体架构

```text
                 ┌────────────────────────┐
                 │   Table Domain Core     │
                 │  结构 + 数据 + 规则      │
                 └───────────┬────────────┘
                             │
        ┌────────────────────┼────────────────────┐
        │                    │                    │
┌───────▼────────┐   ┌───────▼────────┐   ┌───────▼────────┐
│ Markdown Adapter│   │ AutoCAD Adapter │   │ Excel Adapter   │
│ md/html table   │   │ lines/text/Table│   │ xlsx/csv        │
└────────────────┘   └────────────────┘   └────────────────┘
        │                    │                    │
        ▼                    ▼                    ▼
 Markdown 文档        AutoCAD 图形/表格        Excel 文件
```

### 2.1 Domain 层负责什么

- 表格的行、列、单元格、合并、拆分、斜线分割。
- 单元格值、显示值、公式、格式、边框、对齐。
- 表格操作规则：插行、删行、合并、拆分、复制、填充、排序、简单计算。
- 将视觉复杂表格规整成稳定的数据结构。

### 2.2 Adapter 层负责什么

- Markdown Adapter：输出 Markdown 表格、HTML 表格或扩展语法。
- AutoCAD Adapter：输出 AutoCAD 线框、文字、块属性、原生 Table，或混合图元。
- Excel Adapter：读写 `.xlsx` / `.csv`，处理合并单元格、样式、公式。

### 2.3 Presentation 层负责什么

- WPF 表格编辑器：像 Excel 一样编辑。
- AutoCAD 表格编辑模式：允许用户用 CAD 基本操作画线、移动、复制、修剪，系统自动识别表格。
- 命令入口：进入编辑模式、退出编辑模式、导入、导出、刷新、识别。

## 3. Domain 的核心对象

### 3.1 TableDocument

表示一个完整表格文档，可包含一个或多个表格。

适用场景：

- 一个 Word 人员情况表中可能有主表、附表、签字栏。
- 一个 AutoCAD 图纸中可能同时存在多个表格。
- 一个 Markdown 文档中可能需要多张表。

建议字段：

```text
TableDocument
- Id
- Name
- Tables
- Metadata
- SourceInfo
```

### 3.2 TableGrid

基础表格单位。它是 Domain 的核心。

```text
TableGrid
- Rows
- Columns
- Cells
- Merges
- Styles
- Borders
- Layout
```

### 3.3 Cell

单元格本体。注意：**合并之后原始 Cell 仍然存在**，只是显示层把它们视为一个区域。

```text
Cell
- RowIndex
- ColumnIndex
- RawValue
- DisplayValue
- Formula
- Style
- Border
- DiagonalParts
- Role
```

### 3.4 CellSpan

表示一个视觉合并区域。

```text
CellSpan
- AnchorCell
- RowStart
- RowEnd
- ColumnStart
- ColumnEnd
- DisplayMode
- ValuePolicy
```

关键原则：

- 合并只是**显示合并**，不是删除被覆盖单元格。
- 被合并区域内的原始 Cell 仍然存在。
- 值可以统一，也可以各自保存。

这样做有三个好处：

- 还原/拆分时不会丢数据。
- Excel 导入导出更稳定。
- AutoCAD 识别到复杂表格时，可以保留更多原始结构信息。

## 4. 基础表格单位与复杂单元格

### 4.1 基础单位：规则网格

所有复杂表格都先落到一个规则网格上：

```text
行 × 列 = 最小单元格矩阵
```

即使视觉上有大合并格、斜线格、跨行跨列，本质上仍然落到这个矩阵中。

这样做是为了：

- Excel 容易映射。
- Markdown/HTML 容易输出。
- AutoCAD 线框容易识别。
- 后续公式、填充、统计可以按行列坐标工作。

### 4.2 斜线分割单元格

斜线单元格不是简单地把一个 Cell 真正切成两个 Cell，而是给一个 Cell 增加 `DiagonalParts`。

```text
DiagonalCell
- BaseCell
- SplitLine: TopLeftToBottomRight / BottomLeftToTopRight
- Parts:
  - PartA: text, alignment, area
  - PartB: text, alignment, area
```

这适合复杂表头，例如：

```text
        项目
姓名  /
```

这里视觉上是两个独立语义区，但底层仍是一个基础 Cell，便于 Excel 与 Markdown 降级处理。

### 4.3 斜线格的降级策略

不同平台支持能力不同：

| 平台 | 推荐表达 |
|---|---|
| AutoCAD | 一条斜线 + 两段文字，精确表达 |
| Excel | 单元格斜线边框 + 两段文本，近似表达 |
| Markdown | 用 HTML 或文本约定降级，如 `姓名 / 项目` |

## 5. 合并与拆分原则

### 5.1 合并不删除原单元格

你的第 4 条思路非常关键，应作为核心设计原则：

> 合并后的单元格，记录仍然可以是原来的多个单元格，只是显示为一个。

推荐做法：

- 逻辑网格不变。
- 新增一个 `CellSpan` 描述显示区域。
- AnchorCell 负责显示。
- 被覆盖单元格仍保存值、公式、样式或空值。

### 5.2 合并区域的值策略

合并区域可以有多种值策略：

| 策略 | 说明 | 用途 |
|---|---|---|
| AnchorOnly | 只显示左上角单元格值 | Excel 默认行为 |
| SameValue | 所有单元格保存相同值 | 方便拆分后保持内容 |
| PreserveEach | 每个单元格保留原值，只显示 Anchor | 复杂数据保真 |
| Composite | 显示时把多个值组合 | 人事表、说明表等复杂表格 |

MVP 建议先支持：

- `AnchorOnly`
- `SameValue`

后续再支持 `PreserveEach` 与 `Composite`。

### 5.3 拆分

拆分时根据 `ValuePolicy` 决定被还原单元格的值：

- `AnchorOnly`：只有 Anchor 有值，其它为空。
- `SameValue`：所有格复制 Anchor 值。
- `PreserveEach`：恢复合并前各自的值。
- `Composite`：需要人工确认或按规则拆分。

## 6. 表格主要功能：结构完成 + 值填充

这个工具的主功能应拆成两条线，而不是混在一起。

### 6.1 第一部分：完成表格结构

目标：把复杂表格的“骨架”快速搭好。

必须支持：

- 创建规则表格。
- 插入/删除行列。
- 调整行高列宽。
- 合并/拆分单元格。
- 斜线表头。
- 边框控制。
- 样式模板。
- 从 AutoCAD 线框识别表格结构。

### 6.2 第二部分：完成值的填充

目标：让表格从“空壳”变成有数据的工程表。

必须支持：

- 手动输入。
- 粘贴 Excel 区域。
- 序列填充。
- 批量替换。
- 简单公式。
- 从图形对象提取值。
- 与 Excel 导入/导出。

### 6.3 为什么要分开

复杂表格经常是先定版式，再填数据：

- Word 复杂表常先画结构。
- Excel 常先填值。
- AutoCAD 中常先画线框，再补文字。

如果 Domain 把“结构”和“值”分开，就能同时适应这三种工作流。

## 7. AutoCAD 编辑模式设计

### 7.1 两种模式

AutoCAD 中建议有两种模式：

| 模式 | 作用 | 行为 |
|---|---|---|
| 表格编辑模式 | 允许用户自由画线、修剪、移动、复制、补文字 | 像普通 CAD 绘图 |
| 表格定稿模式 | 系统识别表格并锁定结构 | 像 AutoCAD Table 一样操作 |

### 7.2 打开表格编辑模式

进入编辑模式后，用户可以使用 AutoCAD 基本操作：

- 画线。
- 偏移。
- 修剪。
- 延伸。
- 移动。
- 复制。
- 删除。
- 写文字。

系统不强迫用户一开始就用“表格命令”。用户仍然按 CAD 习惯画。

这很重要，因为复杂表格在 AutoCAD 中经常不是一步生成，而是工程师边画边调整。

### 7.3 系统如何自动识别表格

关闭编辑模式时，系统扫描编辑范围内的线和文字：

```text
选择范围
  → 识别水平线/竖直线/斜线
  → 合并近似共线线段
  → 生成网格交点
  → 判断最小行列
  → 分配文字到单元格
  → 判断合并区域
  → 判断斜线单元格
  → 生成 TableGrid Domain
```

### 7.4 识别规则

推荐规则：

- 水平/竖直线允许微小误差。
- 端点距离小于容差时吸附为同一交点。
- 缺少内部线的区域推断为合并单元格。
- 单元格内若有斜线，生成 `DiagonalParts`。
- 文字根据包围盒中心点归属到 Cell。
- 一个 Cell 内多个文字时，按位置排序并组合。

### 7.5 关闭编辑模式

关闭后有两种落地方式：

| 方式 | 说明 | 推荐阶段 |
|---|---|---|
| 保持线+文字组合 | 最接近用户手工表，表达复杂表格最强 | MVP |
| 转 AutoCAD 原生 Table | 便于后续原生操作，但复杂斜线/特殊边框会丢能力 | V1/V2 |

MVP 建议优先用**线+文字组合 + Domain 元数据**，不要急着转原生 Table。

理由：

- AutoCAD 原生 Table 对复杂斜线、分割、局部边框不够自由。
- 线+文字最接近工程图实际表达。
- Domain 元数据可以通过 XData 或扩展字典绑定，后续仍可回到编辑器。

## 8. Markdown 与 Excel 适配

### 8.1 Markdown 适配

Markdown 原生表格能力弱，不适合复杂合并和斜线。

推荐输出策略：

| 表格复杂度 | 输出 |
|---|---|
| 简单规则表 | 原生 Markdown 表格 |
| 有合并/斜线/复杂边框 | HTML table |
| 极复杂工程表 | 图片/HTML 预览 + JSON 元数据 |

### 8.2 Excel 适配

Excel 是最接近 Domain 的外部格式。

必须支持：

- 读写 `.xlsx`。
- 合并单元格映射到 `CellSpan`。
- 斜线边框映射到 `DiagonalParts`。
- 基础样式：字体、边框、对齐、行高列宽。
- 基础公式：保留公式文本，必要时只计算简单表达式。

MVP 不建议做完整 Excel 公式引擎。

推荐策略：

- Excel 已有公式：导入时保留公式文本。
- Domain 内简单公式：只支持 `SUM`、四则运算、单元格引用。
- 导出 Excel 时尽量还原公式。

## 9. MVP 范围

### 9.1 MVP 必做

- Domain：`TableDocument`、`TableGrid`、`Cell`、`CellSpan`、`DiagonalParts`。
- WPF：基础网格编辑器。
- AutoCAD：编辑模式开关、线框识别、文字归属、生成 Domain。
- 渲染：Domain → AutoCAD 线+文字。
- 操作：合并、拆分、斜线格、插入/删除行列。
- 值填充：手动输入、复制粘贴、简单序列填充。

### 9.2 MVP 暂不做

- 完整 Excel 公式引擎。
- 高级条件格式。
- 多人协同。
- 与 Word 原生 `.doc/.docx` 双向转换。
- 对外商业授权。
- 多 CAD 平台适配。

### 9.3 验收标准

- 能复刻“人员基本情况表”这类复杂表格的结构。
- 斜线表头可编辑、可显示、可导出。
- 合并格拆分后不丢基础单元格结构。
- CAD 中手工画线框后，系统能识别出可编辑表格。
- Domain 可以同时输出到 AutoCAD 与 HTML/Markdown。

## 10. 实施路线

### 阶段 A：Domain 先行

目标：不依赖 AutoCAD，先把复杂表格的数据模型做稳。

交付：

- 表格模型。
- 合并/拆分规则。
- 斜线单元格模型。
- 简单公式和值填充模型。
- JSON 序列化。

验收：

- 用单元测试构造复杂表格。
- 合并、拆分、斜线、填值后结构不乱。
- 可序列化/反序列化。

### 阶段 B：Markdown/HTML 渲染

目标：先用最轻的出口验证 Domain 表达能力。

交付：

- 简单表输出 Markdown。
- 复杂表输出 HTML table。
- 斜线格用 HTML/CSS 或文本降级表达。

验收：

- 不进 AutoCAD 也能预览复杂表格。
- 复杂表格结构能肉眼校验。

### 阶段 C：AutoCAD 编辑模式

目标：实现你第 5 条提到的核心工作流。

交付：

- 进入表格编辑模式。
- 用户用 AutoCAD 原生命令画线/文字。
- 关闭编辑模式时自动识别 TableGrid。
- Domain → AutoCAD 线+文字渲染。

验收：

- 手工画的表格可识别。
- 识别结果可回到 WPF 编辑器。
- 修改后可重新写回 AutoCAD。

### 阶段 D：Excel 转换

目标：和 Excel 互导，服务数据填充。

交付：

- `.xlsx` 导入为 Domain。
- Domain 导出 `.xlsx`。
- 支持合并格、基础样式、简单公式保留。

验收：

- Excel 中的合并格进入 Domain 后不丢结构。
- Domain 表格导出 Excel 后基本可编辑。

## 11. 技术风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| AutoCAD 原生 Table 表达不了复杂表格 | 斜线、局部边框、复杂合并失真 | MVP 用线+文字组合，不急着转原生 Table |
| 自动识别线框误判 | 表格结构错乱 | 引入容差、预览确认、人工修正 |
| Excel 公式太复杂 | 自研公式引擎成本失控 | 只保留公式文本，MVP 只计算基础公式 |
| Markdown 原生表格能力弱 | 无法表达复杂表 | 简单表用 Markdown，复杂表用 HTML |
| Domain 过早绑定 AutoCAD | 后续无法复用到 Markdown/Excel | Domain 项目保持平台无关，不引用 AutoCAD API |
| WPF + PaletteSet 资源坑 | 面板崩溃或样式异常 | 遵守项目 PaletteSet/WPF 资源规则，主题局部合并 |

## 12. 最终建议

第一步不要做 AutoCAD 命令，也不要先做 Excel 导入。

**第一步应当只做 Domain：**

```text
复杂表格结构模型
  + 合并/拆分
  + 斜线格
  + 值填充
  + JSON 保存
  + HTML 预览
```

原因：

- Domain 做对了，AutoCAD、Markdown、Excel 都只是适配器。
- Domain 做错了，后面所有平台都会被迫返工。
- 复杂表格最难的是结构表达，不是画线。

推荐的第一期目标：

> 用 Domain 构造并预览一个“人员基本情况表”级别的复杂表格，证明模型能表达 Word 式复杂表格；再进入 AutoCAD 编辑模式开发。
