## 一、现状盘点 — HYFEA.Core v0.1 事实模块

当前(`P0.v0.1`,G01-G04 已通过)的实际目录:

| # | 目录 | 文件数 | 内容定位 | 与"双轨可替换"关系 |
|---|------|:-----:|---------|------------------|
| 1 | `Model/` | 7 | `FemProblem` + 5 类 ID + 节点 / 单元定义 | **核心 IR**(双轨共享) |
| 2 | `Geometry/` | 2 | `Point2D` / `Vector2D` | 算法工具(非可替换) |
| 3 | `Dofs/` | 2 | `DofType` / `DofLayout` | **核心 IR**(双轨共享) |
| 4 | `Materials/` | 1 | `MaterialDefinition`(线弹性占位) | 可双轨 |
| 5 | `Sections/` | 1 | `SectionDefinition`(轴向/梁) | 可双轨(常与 Material 联合) |
| 6 | `Elements/` | 2 | `Spring1DContribution` / `Truss2DContribution` | **可双轨**(单元库) |
| 7 | `Loads/` | 1 | `NodalLoad` | 可双轨(暂简单) |
| 8 | `Boundary/` | 1 | `FixedSupport` | 可双轨 |
| 9 | `Assembly/` | 2 | `Assembler` / `AssembledLinearSystem` | **可双轨**(Dense → CSR) |
| 10 | `LinearAlgebra/` | 2 | `DenseMatrix` / `DenseVector` | **可双轨**(Dense → Sparse → GPU) |
| 11 | `Solvers/` | 1 | `DenseLinearSolver` | **可双轨**(对标 004 M06) |
| 12 | `Analysis/` | 1 | `LinearStaticAnalysis` | 编排层(暂单实现) |
| 13 | `Results/` | 1 | `FemResult` | **核心 IR**(双轨共享) |
| 14 | `Validation/` | 1 | `GoldenCase` | 跨模块横切 |
| 15 | `Diagnostics/` | 2 | `FemError` / `SolveDiagnostics` | 跨模块横切 |
| 16 | `Internal/` | 1 | `IsExternalInit`(C# 编译适配) | 非业务 |

**事实观察**:

1. **15 业务目录是合理粒度**——既不过细(每个目录至少 1 个明确职责),也不过粗(没有"杂项"目录)。
2. **`FemProblem` 已经是聚合根**——它把 Nodes / Elements / Materials / Sections / Supports / LoadCase 6 类聚合进单一 record,这是核心 IR 的事实形态。
3. **缺一类:Mesh(网格生成)**——P0 用手写网格,不建 Mesh 目录是正确选择;但长期蓝本(004 M01)有这一类,需在 §八 演化路径中明确何时建。
4. **缺一类:NumberingScheme(自由度编号策略)**——目前 `DofLayout` 隐含了顺序编号;未来如要做带宽优化(RCM)或对称化处理,需要单独的策略对象。

## 二、已有三份方案对比

把 004 / 005 / 00 三份文档对模块的划分摆在一起,直观看出差异来源:

| 视角 | 文档 | 模块数 | 站位 | 包含外壳? | 包含 AI/UI? |
|------|------|:-----:|------|:---------:|:----------:|
| **主控发行版** | 004 §3 | **13**(M01-M13) | 整个 hy-cad-tool 产品 | ✓ | ✓ |
| **HYFEA+集成** | 005 §四 | **22**(M00-M22) | HYFEA 内核 + HyCADTool 集成 | ✓ | ✓ |
| **高度抽象** | 00 计划 | **9** | HYFEA.Core 算法主体 | ✗ | ✗ |
| **事实(当前)** | v0.1 代码 | **15** 目录 | HYFEA.Core 算法主体 | ✗ | ✗ |

**为什么数字不一样?三个站位混在一起**:

- 004 把"AI 副本 / RAG / 报告生成"也算成模块(M11/M12/M13) → 这些**不在 HYFEA.Core**,属于 HyCADTool 外壳层。
- 005 把"UI / 命令 / 桥接 / 性能基准"也算成模块(M20-M22) → 同样**不在 HYFEA.Core**,属于集成/工具链层。
- 00 计划用 9 个粗粒度名词,**只是抽象指代**,不是真实代码层级。
- 当前 v0.1 的 15 个目录是**算法内核唯一真实事实**。

> **关键洞察**:三份方案没有矛盾,只是粒度与边界不同。本调研要做的事是"**把这三份对齐到 HYFEA 三层(Core / Adapters / Integration)的模块清单**"。

## 三、国际开源 FEA 项目模块划分参考

挑 5 个最相关的开源项目,看它们的事实模块切法(只看核心库,不看 GUI):

| 项目 | 核心目录/命名空间 | 模块数 | 关键观察 |
|------|----------------|:-----:|---------|
| **deal.II** | `Triangulation / DoFHandler / FE / Quadrature / Mapping / LinearAlgebra / LAC / AffineConstraints / DataOut` | ~12 | 把"自由度处理"作为独立类(`DoFHandler`)与"网格"分开;`AffineConstraints` 单独切出主从约束 |
| **MFEM** | `Mesh / FiniteElementSpace / FiniteElement / BilinearForm / LinearForm / GridFunction / LinearAlgebra / Solvers` | ~10 | 用"形式语言"(BilinearForm / LinearForm)替代手写装配 |
| **OpenSees** | `Domain / Element / Material / Section / Constraint / Pattern / Numberer / Solver / Analysis` | **9**(七件套+) | 经典土木抽象,与 HYFEA 最贴近 |
| **CalculiX**(从 `.inp` 反推) | `Node / Element / Material / Section / Step / Load / Boundary / Output` | ~8 | 极扁平,无独立"装配"概念(装配藏在 Solver 内) |
| **Code_Aster**(从 `.comm` 反推) | `Maillage / Modèle / Matériau / Caractéristiques / Chargement / CL / Solveur / Postraitement` | ~8 | 把"网格"和"模型(单元-节点关联)"分作两层 |

**5 个开源项目的最大公约数**(出现频率 ≥ 4):

1. **Mesh / Triangulation**(网格)
2. **Element / FiniteElement**(单元)
3. **Material**(材料)
4. **Section**(截面)
5. **Boundary / Constraint**(约束)
6. **Load / Pattern**(荷载)
7. **Assembly / Form**(装配)
8. **Solver / Analysis**(求解 / 分析)
9. **DOF / Numberer**(自由度)
10. **Output / DataOut**(结果)

加上 HYFEA 已经做的:
11. **Model / Domain**(聚合根 IR)
12. **Validation**(金标准验证 — 这一项**多数开源项目作为外部测试套件,不在核心**;HYFEA 把它内化是正确选择)
13. **Diagnostics**(错误与残差报告 — **多数开源项目散落在 Solver 内**;HYFEA 集中化是正确选择)

> **结论**:HYFEA 当前 15 个目录在国际同类项目中处于**中等粒度**,既不像 CalculiX 那么扁平(藏太多),也不像 deal.II 那么精细(单人维护负担大)。

## 四、HYFEA 自身的 4 个独特约束

| 约束 | 含义 | 对模块划分的影响 |
|------|------|----------------|
| ①**单人 + AI 协作** | 现阶段只有 1 个人 + Cursor 协助 | 模块总数 ≤ 15(否则维护爆炸) |
| ②**.NET / C# 11** | 项目主语言 | 用 `record` 表达 IR,用 `interface` 表达双轨,目录映射 namespace |
| ③**与 HyCADTool 集成** | 最终要被 AutoCAD 插件消费 | Core 必须**完全平台无关**(不引用 Autodesk.\* / WPF) |
| ④**双轨可替换从第一天起** | 即便 P0 只有一个实现,接口形状要为双轨预留 | 求解器 / 装配 / 单元 / 材料 / 网格 这 5 个模块**优先双轨化** |

> 约束①最关键:**14-16 模块是单人 + AI 的甜区**。少于 10 个会"什么都混在一起"(类似 CalculiX 那样),多于 20 个会"找不到东西在哪里"(类似 004 的 13 主控模块再展开成 22 子模块就是上限)。

## 五、模块划分的 7 条原则(本调研沿用 004 §3.1 + 加 3 条;v1.1 新增⑥⑦)

| # | 原则 | 来源 | HYFEA 应用 |
|---|------|------|-----------|
| ① | **输入输出可量化** | 004 §3.1 | 每个模块必须有明确的"输入类型"与"输出类型"(用 `record` 或 `interface` 表达) |
| ② | **至少存在 2 个潜在候选** | 004 §3.1 | 这是"可替换"的前提;不满足则**不立为独立模块**(如"Internal 辅助"就不立) |
| ③ | **有金标准验证用例** | 004 §3.1 | 至少 1 个 G 系列 case 能验证该模块(若做不到,该模块还未成熟到该独立) |
| ④ | **与其他模块解耦** | 004 §3.1 | 替换 A 模块不影响 B 模块的代码(只通过 IR 传递) |
| ⑤ | **HYFEA 新增:粒度匹配单人维护** | 本调研 | 模块总数 ≤ 15,每个模块代码量 P0 ≤ 500 行;过大则继续切分,过小则合并 |
| ⑥ | **v1.1:调用人体工学优先** | 用户补充 | 提供"3 层入口"(高层 Facade / 流式 Builder / 直接 record);命名空间深度 ≤ 3 级;详见 §十三 |
| ⑦ | **v1.1:初少后细(TreeView 渐进)** | 用户补充 | 启动期模块扁平;触发条件成立后,某模块内部可细分为 TreeView 形态;**不预创空目录**;详见 §十四 |

## 六、HYFEA 推荐模块清单(本调研核心结论)

按"**三层归属**"组织:Core(内核)/ Adapters(适配)/ Integration(集成)。

### 6.1 HYFEA.Core 推荐 13 模块(P0-P3 渐次启用)

| # | 模块 | 命名空间 | 职责 | 主要输入 → 输出 | 可替换性 | Track A 候选 | Track B 自研 | P0 状态 |

### 6.2 HYFEA.Adapters.\* 推荐适配模块(P1+ 新建)

适配模块只在需要接入外部资源时才创建。每个适配模块**对应 Core 内某一个可替换模块的 Track A 候选**。

| # | 适配模块 | 项目名 | 适配 Core 模块 | 协议 | 接入方式 | P 阶段 |
|---|---------|--------|--------------|------|---------|:----:|
| **A01** | CSparse 适配 | `HYFEA.Adapters.CSparse` | C11 Solvers + C10 LinearAlgebra(CSR) | LGPL | NuGet | P1 |
| **A02** | MUMPS 适配 | `HYFEA.Adapters.MUMPS` | C11 Solvers | CeCILL-C | P/Invoke 或子进程 | P2 |
| **A03** | Gmsh 适配 | `HYFEA.Adapters.Gmsh` | (新增 C00 Mesh,见 §九) | GPL | 子进程 | P2 |
| **A04** | Triangle.NET 适配 | `HYFEA.Adapters.Triangle` | C00 Mesh(2D) | LGPL | NuGet | P1 |
| **A05** | CalculiX 适配 | `HYFEA.Adapters.CalculiX` | 整体求解(C09-C13 整体替代) | GPL | 子进程 + .inp/.frd | P2 |

> **关键约束**:Adapter 模块**只能依赖 HYFEA.Core 的 IR(C01 Model / C13 Results)**,不能反向依赖 HyCADTool。

## 十三、调用人体工学(v1.1 新增,对应原则⑥)

### 13.1 三层调用入口(给 80% / 15% / 5% 用户)

| 层 | 受众 | 调用形态(示意,不写代码) | 适用 |
|----|------|-----------------------|------|
| **L3 Facade** | 80% 普通用户(AutoCAD 工程师) | `FemFacade.SolveCantilever(polyline, q, supports)` 一行出结果 | MVP 阶段最常见的"挡墙单宽梁元" |

| **L1 Record** | 5% 高级用户 + 内部测试 | `new FemProblem(nodes, elements, ...)` 直接构造 | 性能基准 / 序列化往返 / 测试 |

> **关键设计**:L3 → L2 → L1 是"包装关系",底层只有一份 `FemProblem` IR。**任何高层入口最终都生成同一个 record**,所以可被序列化、可被金标准 case 对比、可被双轨同时跑。

### 13.2 命名空间深度约束

| 规则 | 反例 | 正例 |
|------|------|------|
| 公开 API 命名空间 ≤ 3 级 | `HYFEA.Core.Elements.Linear.Beam.EulerBernoulli.EulerBernoulliBeam2D` ❌ | `HYFEA.Core.Elements.EulerBeam2D` ✅ |
| 内部实现可深(用 `Internal`) | — | `HYFEA.Core.Internal.Assembly.Coo` |
| Facade 单一入口 | 用户要 using 5 个命名空间才能建模 ❌ | `using HYFEA.Core;` 一行覆盖 90% 场景 ✅ |

### 13.3 "5 分钟跑通第一个算例"门槛

任何外部贡献者(或半年后回来的自己),应满足:

| 时间 | 应能做到 |
|------|---------|
| 5 分钟 | `git clone` + `dotnet build` + `dotnet test` 全绿 |
| 15 分钟 | 在 `HYFEA.Examples` 复制一个 golden case,改参数,跑出新结果 |
| 1 小时 | 用 L2 Builder 写一个自己的小算例,与解析解对比 |
| 1 天 | 加一个新单元类型(从 Truss2D 复制改造) |

> 这是 §五 原则⑥的可证伪检验。任何 PR 让"5 分钟门槛"退化,自动判负。

### 13.4 选开源框架的"调用人体工学"加分项

在 §六 6.2 选 Adapters 时,**接口友好度**作为决定因素之一:

| 候选 | 加分项 | 减分项 |
|------|--------|--------|
| Triangle.NET(C# 原生) | ✅ NuGet / 强类型 / IntelliSense 完整 | — |
| Gmsh(子进程 + .geo) | — | ❌ 用户要学 .geo 脚本(违反"内置 IDE 智能") |
| CSparse.NET | ✅ NuGet / .NET 友好 | — |
| MUMPS(P/Invoke) | — | ❌ 调用方要自己管 IntPtr / 内存 |
| CalculiX(子进程 + .inp) | ✅ 对用户透明(被 Adapter 包装) | ❌ 对 HYFEA 开发者需理解 .inp 格式 |

**结论**:相同 Fitness 下,**优先选 C# 原生 NuGet 候选**(Triangle.NET / CSparse.NET / MathNet.Numerics);其次是有 P/Invoke C ABI 的(MUMPS / Eigen);最后是子进程类(Gmsh / CalculiX)。
