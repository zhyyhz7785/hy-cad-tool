# ❶ **最大风险：你的 Domain 正在变成“几何算法库”，而不是“领域模型”**

### 现象

你现在的 Domain：

```
Entities（少）
ValueObjects（极多）
Algorithms（极多）
DCEL（底层结构）
```

👉 **这不是 DDD Domain，这叫 Computational Geometry Core**

这会导致：

| 后果                  | 说明                                  |
| --------------------- | ------------------------------------- |
| 业务语义消失          | “桩”“墙”“板”只是几何容器              |
| 未来 Blender 迁移困难 | Blender 关心 Mesh/BMesh，不是算法细节 |
| 逻辑难测试            | 业务规则与算法强耦合                  |

------

### ✅ 优化方案：**拆出 Geometry Kernel（几何核心层）**

你需要一个**新层**：

```
Domain（业务语义）
↑
GeometryKernel（纯几何核心）
↑
Infrastructure（AutoCAD/NTS/Clipper 适配）
```

### ✔ 重构规则

| 现在位置             | 应迁移到       |
| -------------------- | -------------- |
| DCEL                 | GeometryKernel |
| PolygonOffsetService | GeometryKernel |
| ConvexHullAlgorithm  | GeometryKernel |
| ClusteringService    | GeometryKernel |
| SpatialIndexService  | GeometryKernel |

Domain 只保留：

| 应留下            | 原因     |
| ----------------- | -------- |
| PileLayoutService | 业务规则 |
| ElevationParser   | 业务语义 |
| ReinParameters    | 领域概念 |
| WallThickness     | 领域属性 |

👉 **Domain = 工程语义，而不是数学实现**

------

# ❷ **DI 容器正在变“上帝对象”（God Container）**

你注册了 14 阶段服务。

这是大型插件死亡信号。

### 问题

```csharp
ServiceLocator.Resolve<XXX>()
```

这在 **Presentation** 出现 = 违反依赖倒置。

后果：

| 问题         | 结果              |
| ------------ | ----------------- |
| 隐式依赖     | 类无法测试        |
| 生命周期混乱 | 事务对象被复用    |
| 服务爆炸     | 300+ 服务不可维护 |

------

### ✅ 优化方案

| 原做法              | 正确做法                              |
| ------------------- | ------------------------------------- |
| ServiceLocator      | 构造函数注入（Constructor Injection） |
| UI 直接 Resolve     | CommandHandler 注入                   |
| 大量 SingleInstance | 改为 Scoped（每命令周期）             |

👉 **每条 AutoCAD 命令 = 一个 DI Scope**

------

# ❸ **Command 正在向“流程脚本”退化**

例如：

```
DrawPilesCommand
  → Selection
  → Algorithm
  → Drawing
```

如果继续写，你会得到 500 行的“命令脚本”。

------

### ✅ 解决：引入 Application Layer（你现在没有）

你现在是：

```
Presentation → Domain + Infrastructure
```

应该变成：

```
Presentation → Application → Domain
                           ↓
                     Infrastructure
```

### Application 层负责：

| 职责     | 示例                  |
| -------- | --------------------- |
| 事务边界 | AutoCAD Transaction   |
| 工作流   | “选桩→优化→绘制”      |
| 异常转换 | CAD 异常 → 用户提示   |
| DTO 转换 | UI 参数 → Domain 对象 |

------

# ❹ **几何精度灾难（未来 100% 出问题）**

你现在：

| 系统       | 精度              |
| ---------- | ----------------- |
| AutoCAD    | double            |
| NTS        | double + 拓扑容差 |
| Clipper2   | int64（缩放）     |
| 自定义几何 | double            |

这是**灾难组合**。

------

### ✅ 必须建立统一几何策略（Geometry Strategy）

在 GeometryKernel 中定义：

$$
\epsilon = 10^{-6}
$$

| 符号                         | 含义         |
| ---------------------------- | ------------ |
| $\epsilon$                   | 全局几何容差 |
| $d$                          | 点间距离     |
| 若 $d < \epsilon$ → 视为同点 |              |

建立：

```
IGeometryTolerancePolicy
```

统一管理：

- 点相等
- 线平行
- 多边形闭合
- NTS 输入前 Snap

------

# ❺ **ViewModel 越界风险**

如果 ViewModel 直接：

```csharp
_call DomainService
_call Infrastructure
```

那你只是换皮 MVVM。

### 正确结构：

```
ViewModel → ApplicationService → Domain
```

------

# ❻ **AutoCAD 事务分散管理 = 未来随机崩溃**

你现在：

- DatabaseService
- DrawingService
- LayerService

都可能自己开事务。

这就是 eLockViolation 根源。

------

### ✅ 统一事务边界

```
ICommandScope
 ├── BeginTransaction()
 ├── Commit()
 └── Rollback()
```

由 Application 层控制。

------

# ❼ **配置系统正在变“魔法规则堆”**

大量：

```
PileConfiguration
ReinforcementConfiguration
GlobalConfig
```

如果它们进入 Domain 计算 = 规则污染。

------

### 正确：

```
Configuration → Application DTO
Application → 转换 → Domain ValueObject
```

Domain 不感知配置来源。
