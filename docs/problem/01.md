# 🔥 问题 1：**Domain 层已经开始“结构失重”**

### 现象

你现在的 Domain：

```
Entities
ValueObjects
Services (20+)
GeometryAlgorithms
MathAlgorithms
OffsetAlgorithms
Utilities
DataStructures
```

这已经不再是 DDD 中的 **Domain**，而是：

> **Geometry Engine + Algorithm Library + Business Rules 混合体**

这会导致：

| 现象                   | 结果                    |
| ---------------------- | ----------------------- |
| 所有算法都放进 Domain  | Domain 变得无法理解     |
| Service 没有统一范式   | 未来无法维护            |
| 业务逻辑和数学逻辑混合 | 迁移 Blender 时整体崩塌 |

------

## ✅ 正确结构（你现在必须进化到的阶段）

你缺失了一层：

```
Domain  ❌（现在过重）
   ↓
Core Geometry Kernel  ← 你缺这个
   ↓
Application / UseCase
   ↓
Infrastructure
```

### 🔧 建议新增层：

```
HyCAD.Core.GeometryKernel   ⭐⭐⭐⭐⭐
HyCAD.Domain                ⭐⭐
HyCAD.Application           ⭐⭐⭐
HyCAD.Infrastructure
HyCAD.Presentation
```

------

### 🧩 为什么？

你现在的：

- DCEL
- PolygonOffset
- Intersection
- SpatialIndex
- GeometryUtils
- Clustering

这些 **不是“领域逻辑”**，它们是：

> **几何计算内核（Geometry Kernel）**

这相当于：

| 领域    | 对应结构          |
| ------- | ----------------- |
| Revit   | Geometry Engine   |
| Blender | BMesh + Mathutils |
| AutoCAD | AcGe / AcDb 内核  |

而你现在把它们塞进 Domain，导致：

> **Domain = 业务模型 + 几何引擎混合层**

这是架构级隐患。

------

# 🔥 问题 2：Service 类数量已到“认知崩溃临界点”

当前：

> **Domain Services 20+**
> **Infrastructure Services 30+**

人类对抽象结构的稳定认知上限 ≈ **50 个核心对象**

你现在正在走向：

> **“每加一个功能，新增 2 个 Service” 的死亡螺旋**

------

## ✅ 优化方案：**Service → Engine 化**

你现在是：

```
PolygonAlgorithmService
LineAlgorithmService
PointAlgorithmService
CurveIntersectionService
CurveBreakService
...
```

应改为：

```
GeometryEngine
    ├─ Intersection
    ├─ Offset
    ├─ Simplification
    ├─ Topology (DCEL)
```

### 好处

| 现在          | 重构后      |
| ------------- | ----------- |
| 40 个 Service | 5 个 Engine |
| 横向散乱      | 纵向分层    |
| 难维护        | 模块化      |

------

# 🔥 问题 3：你缺失 **Application 层（UseCase 层）**

现在命令直接调用：

```
Command → DomainService → Infrastructure
```

这不是 Clean Architecture，这是：

> **Command = UseCase = Controller 混合层**

未来会出现：

- 命令逻辑重复
- UI 与业务逻辑纠缠
- Blender 迁移时命令全部推倒重来

------

## ✅ 解决：增加 Application 层

```
Presentation (Command)
   ↓
Application (UseCase)
   ↓
Domain
```

例如：

```
DrawPilesCommand
   ↓
DrawPilesUseCase
   ↓
PileLayoutService
```

------

# 🔥 问题 4：DI 容器已经成为“隐形单例系统”

你有：

```
ServiceLocator
Autofac 全局 Resolve
PanelManager 从容器取
Command 从容器取
```

这会导致：

> **所有依赖关系在代码中不可见**

后果：

- 调试困难
- 生命周期混乱
- Blender 迁移时彻底崩盘

------

## ✅ 规则（强制）

| 层             | DI 使用方式       |
| -------------- | ----------------- |
| Presentation   | 构造函数注入 ONLY |
| Application    | 构造函数注入 ONLY |
| Domain         | 禁止 DI           |
| Infrastructure | 注册，不 Resolve  |

删除 ServiceLocator 是下一阶段的硬任务。

------

# 🔥 问题 5：几何算法还停留在“CAD 脚本思维”，不是“几何引擎思维”

你现在算法大多是：

> 操作点、线、多段线

而 Blender/三维世界是：

> Mesh / Topology / HalfEdge / Surface

你虽然有 DCEL，但它只是“工具”，不是“核心数据模型”。

------

## ✅ 未来必须演化到：

```
Topology First
    ↓
Geometry As Derived Data
    ↓
CAD Entity As Projection
```

否则你未来做：

- 力学网格
- 医学曲面
- 3D 参数化

全部要重写。

------

# 🚨 最关键一句话

> 你现在的架构，**在 AutoCAD 插件层面已经非常优秀**
> 但如果目标是 “Blender + 几何引擎级平台”
> 那你目前还停留在 **大型插件架构，而不是平台架构**
