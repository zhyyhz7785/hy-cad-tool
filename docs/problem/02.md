这是一个非常专业且结构清晰的项目重构文档。你采用 **Clean Architecture（整洁架构）** + **DDD（领域驱动设计）** 来重构 AutoCAD 插件，这是一个非常有野心但也非常正确的方向，特别是考虑到未来迁移 Blender 的需求。

基于你提供的 v3.1 文档，我模拟了一次深度代码审查（Code Review），找出了潜在的 **5 大核心风险** 和 **4 个架构优化建议**。

------

### 🚨 核心风险与潜在问题

#### 1. "造轮子"陷阱：自定义几何库 vs. NetTopologySuite (NTS)

- **问题现状**：在 `Domain/ValueObjects/Geometry` 中，你定义了大量的 `Point2D`, `Line2D`, `Polygon2D`，并在 `Services/GeometryAlgorithms` 中实现了 `Intersection`, `Offset`, `Boolean` 等算法。同时，依赖列表中又出现了 `NetTopologySuite` 和 `Clipper2`。
- **潜在风险**：
  - **维护负担**：几何算法（特别是涉及浮点数精度的布尔运算、多边形偏移）极难写对。维护一套自定义的几何库会消耗大量精力。
  - **性能/兼容性**：自定义几何对象与 NTS 或 Clipper2 交互时，需要频繁转换（Custom ↔ NTS ↔ Clipper），造成性能损耗。
- **优化方案**：
  - **Domain 层直接采用 NTS 类型**：NetTopologySuite 是纯 .NET Standard 库，完全平台无关。建议直接使用 `NTS.Geometries.Point`, `Polygon` 作为你的领域对象，或者让你的 ValueObject 内部持有 NTS 对象。
  - **移除冗余算法**：除非有极特殊的业务需求，否则删除 `GeometryAlgorithms` 中与 NTS 重叠的算法（如凸包、交点、缓冲），直接封装调用 NTS/Clipper。

#### 2. "转换层"的性能瓶颈 (The Mapping Overhead)

- **问题现状**：架构强制要求 `Infrastructure (AutoCAD Entity)` ↔ `Domain (Entity)`。
- **潜在风险**：
  - **大图纸卡顿**：如果用户执行“所有桩位自动编号”，涉及 10,000 个图元。你需要：
    1. 从 AutoCAD 读 10k 个 Entity。
    2. `new` 10k 个 Domain 对象（内存分配）。
    3. 运行算法。
    4. 结果转换回 AutoCAD Entity 或修改原 Entity。
  - **状态同步**：Domain 对象修改后，如何高效更新回 AutoCAD？全量删除重绘是最低效的。
- **优化方案**：
  - **引入 `LazyProxy` 或 `Handle` 机制**：Domain 对象不要存储所有几何数据，对于未修改的数据，仅存储 AutoCAD 的 `ObjectId` 或 `Handle`。
  - **按需转换**：不要一次性转换所有图元。使用 `IEnumerable<T>` 流式处理。
  - **脏标记（Dirty Flag）**：Domain 对象需记录是否被修改，Infrastructure 层只更新被修改的对象。

#### 3. 跨平台迁移的语言障碍 (C# vs Blender/Python)

- **问题现状**：目标提到“为 Blender 迁移做准备”。Blender 的原生 API 是 Python。
- **潜在风险**：
  - **C# 无法直接在 Blender 运行**：除非你打算在 Blender 中嵌入 .NET Runtime (如 pythonnet)，否则这一套 C# Domain 代码在 Blender 中完全不可用，需要重写为 Python。
  - **API 差异**：Blender 的 BMesh 结构与 AutoCAD 的 Database 差异巨大。
- **优化方案**：
  - **明确迁移策略**：
    - *方案 A（重写）*：Domain 层逻辑保持清晰，作为伪代码参考，在 Python 中重写。
    - *方案 B（IPC/Interop）*：将核心算法编译为 DLL/Console App，Blender 通过 Python 调用外部进程或 DLL（这是保留 C# 代码的唯一方式）。
  - **推荐方案**：如果是复杂算法（如 Voronoi 桩位优化），采用 **方案 B**。将 Domain 层独立发布为 NuGet 包或 CLI 工具，AutoCAD 和 Blender 都只是这个核心库的“UI 前端”。

#### 4. 测试体系的缺失 (The "To Be Established" Gap)

- **问题现状**：测试覆盖率为“待建立”，且 `Test/` 目录下只有 AutoCAD 内部的集成测试 (`TestCommand`)。
- **潜在风险**：
  - **Domain 层的价值未体现**：Clean Architecture 的最大优势是 **Domain 层可以脱离 AutoCAD 进行单元测试**。如果只在 AutoCAD 里测 (`C1` 命令)，不仅慢，而且无法覆盖边界条件。
- **优化方案**：
  - **立即添加 xUnit/NUnit 项目**：在解决方案中添加 `HyCADTool.Tests`。
  - **测试 Domain 纯逻辑**：例如 `PileLayoutService`，不需要启动 AutoCAD，直接在单元测试中 `new Pile(...)` 并断言结果。这才是重构的核心价值。

#### 5. 依赖注入与 AutoCAD 的静态特性冲突

- **问题现状**：使用了 Autofac。AutoCAD 的命令 (`[CommandMethod]`) 是静态入口，且 AutoCAD 自身有大量的静态上下文 (`Application.DocumentManager...`)。
- **潜在风险**：
  - **Scope 管理**：`Transaction` 是短生命周期的。如果将其注入到 Singleton 的 Service 中，会引发致命错误（eLockViolation）。
- **优化方案**：
  - **UnitOfWork 模式**：不要将 `Transaction` 注入 Service。Service 方法应该接收 `IUnitOfWork` 或在方法内部开启 Scope。
  - **Func<Owned<T>>**：在静态命令入口，使用 Autofac 的 `ILifetimeScope` 显式开启一个新的 Scope 来处理单次命令执行。

### 🛠️ 架构优化方案建议

#### 优化 1：调整目录结构（按功能而非层级）

目前的结构是按技术层级分（所有 Entity 在一起，所有 Service 在一起）。建议 **按特性（Feature）垂直切分**，更符合 DDD。

**建议结构：**

Plaintext

```
Domain/
├── Core/                # 基础几何、通用接口
└── Features/
    ├── Piles/           # 桩相关的所有内容
    │   ├── Pile.cs
    │   ├── PileLayoutService.cs
    │   ├── IPileRepository.cs
    │   └── PileConfig.cs
    ├── Reinforcement/   # 钢筋相关
    │   ├── Rebar.cs
    │   └── ...
    └── Clustering/      # 聚类相关
```

*好处：当你要修改“桩”功能时，不需要在 5 个文件夹之间跳来跳去。*

#### 优化 2：完善热重启机制 (Hot Reload+)

目前的 `C2` 卸载/加载 DLL 机制在 AutoCAD .NET 中非常不稳定（AppDomain 卸载难）。

**建议：**

- 如果不涉及 UI 变更，仅算法变更：将 **Domain 层独立为一个 DLL**。
- AutoCAD 插件 (Loader) 只有极薄的一层，通过反射加载 Domain DLL。
- 这样每次 `C2` 只需要释放 Domain DLL 的文件句柄，比卸载整个插件更安全。

#### 优化 3：引入 "Specification" 模式用于选择过滤

你有一个 `SelectionFilterService`。建议升级为 **Specification Pattern**。

**代码示例：**

C#

```
// Domain 层定义规格
public class RedLinesOnLayer0Spec : Specification<Entity> 
{
    public override bool IsSatisfiedBy(Entity entity) => 
        entity.Color == Colors.Red && entity.Layer == "0";
}

// Infrastructure 层将其翻译为 AutoCAD SelectionFilter
// 这样业务逻辑依然在 Domain，但执行利用了 AutoCAD 的高性能过滤。
```

#### 优化 4：数据结构优化 (DCEL)

- **观察**：你自己实现了 DCEL (`HalfEdge`, `Vertex`, `Face`)。
- **建议**：如果主要用于多边形拓扑，DCEL 是对的。但要注意内存。C# 的 Class 对象开销大。如果处理数万个网格，建议改用 `struct` 配合数组索引（类似 Unity Mesh 的处理方式），或者直接使用 `NetTopologySuite.Geometries.Graph`。
