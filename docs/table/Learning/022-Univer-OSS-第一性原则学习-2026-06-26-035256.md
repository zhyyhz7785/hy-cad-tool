## 概览

**Univer OSS（Univer Open Source Software，Univer 开源软件）** 是 dream-num 团队维护的全栈、同构（Isomorphic）办公 **SDK（Software Development Kit，软件开发工具包）**：用 **TypeScript（一种 JavaScript 超集 / a typed superset of JavaScript）** 编写，以 **插件（Plugin）** 组合能力，以 **Facade API（外观应用程序接口 / Facade Application Programming Interface）** 对外简化调用。它解决的核心问题是：**在不自建 Excel/Word 级编辑器的前提下，把表格/文档/演示能力嵌入自有产品**——浏览器、**Node.js（服务端 JavaScript 运行时 / server-side JavaScript runtime）**、**Web Worker（浏览器后台线程 / browser background thread）** 共用同一套架构。

对本项目而言，Univer 是 020 调研中的 **方案 C（WebView2 + Univer OSS）** 的技术内核；HyCAD 已通过 `HyCADTool.UniverEditor` 做 PoC（概念验证 / Proof of Concept），用 **WebView2（微软嵌入式 Chromium 控件 / Microsoft embedded Chromium control）** 承载前端，`TableGrid` 经 JSON 快照桥接。

## 历史脉络

| 时间 | 节点 | 为何出现 | 用在何处 |
|------|------|----------|----------|
| ~2020 | **Luckysheet** 等 Web 表格 | 浏览器内 Excel 体验需求 | 在线表格、轻量 BI |
| 2023 | **Univer** 立项（同团队） | Luckysheet 架构难支撑文档/幻灯片/同构/server | 统一 Office SDK |
| 2024–2025 | 微内核 + 插件 + **DI（Dependency Injection，依赖注入）** + 命令系统定型 | 30 万+ 行 TS、297+ DI 模块，手工装配不可行 | 可裁剪 bundle、可测、可扩展 |
| 2025–2026 | v0.25+、Preset/Plugin 双模式、Headless Univer | AI/自动化要在 Node 读写 workbook | SaaS、内部工具、HyCAD 类嵌入 |
| 持续 | **Univer Pro（商业版）** 与 OSS 分轨 | 协作 OT、xlsx 导入导出、图表等商业化 | 企业 SaaS；OSS 仍覆盖核心编辑 |

**逻辑顺序（非严格编年）**：电子表格 UI 需求 → 单页表格库瓶颈 → 插件化微内核 → 同构（UI 与计算分离）→ Facade 降复杂度 → Pro 补协作与格式生态。

## 符号约定

本主题以架构关系为主；下列式子描述「快照同步」抽象，非 Univer 内部实现公式。

\[
S_{\mathrm{host}} \xrightarrow{\;\mathrm{loadSnapshot}\;} S_{\mathrm{univer}}
\quad\text{且}\quad
S_{\mathrm{univer}} \xrightarrow{\;\mathrm{exportSnapshot}\;} S_{\mathrm{host}}'
\]

**符号说明**：

- \(S_{\mathrm{host}}\)：宿主（HyCAD `TableGrid` / `HyCadGridSnapshot`）侧表格状态。
- \(S_{\mathrm{univer}}\)：Univer 工作簿（Workbook）内存快照（单元格值、合并、行列尺寸等）。
- \(S_{\mathrm{host}}'\)：编辑后回写宿主的状态；理想情况下与用户在 Univer 中的编辑语义一致。
- \(\xrightarrow{\text{load/export}}\)：经 JSON + WebView2 `postMessage` 的序列化桥，非 Univer 原生协作协议。

## 核心概念

### 1. 对象：Univer 是什么

- **对象**：可嵌入的 **Office 体验构建框架**，不是开箱即用的独立 SaaS 产品；核心是 `@univerjs/*` 包族 + 插件注册 +（可选）React UI。
- **痛点**：自研网格 + Ribbon + 公式 + 渲染，长期 polish 难达 Excel 级（020 方案 A 加权 2.7）；纯 .NET 控件（ReoGrid）观感上限低于 Canvas 方案。

#### 最小定义/公理/假设

1. **插件优先**：一切能力以插件注册；未注册即不存在（无「隐式默认全家桶」）。
2. **分层单向依赖**：Model → Service → Command → Controller → View；上层不得反向引用下层（官方架构约束）。
3. **状态变更走命令**：持久化数据改动必须经 **MUTATION（变更 / state mutation）**；可撤销栈与协作以 MUTATION 为最小单元。
4. **同构假设**：同一 `@univerjs/sheets` 等数据插件可在浏览器与 Node 加载；UI 插件（`*-ui`）仅在需要 DOM/Canvas 的环境加载。
5. **OSS 边界**：Apache-2.0 开源核心 + 一等方插件；实时协作、完整 xlsx/docx、图表等属 Pro/商业能力（README 对照表）。

**定义的内核解释**（非专业语言）：  
就像搭乐高，必须先声明「这块是轮子、那块是引擎」，拼错了整套就不转。Univer 规定：功能要一块块插件装上去；改表格内容不能偷偷改内存，必须走「命令登记处」，这样撤销、协作、日志才跟得上。

**定义的结构工程类比**：  
插件像 **框架（Frame）里的梁、柱**：梁（数据 `@univerjs/sheets`）和柱（UI `@univerjs/sheets-ui`）分开制造，Node 工地只运柱梁中的「梁」，浏览器工地才装「柱+梁」。这样同一套结构图纸（代码）能在不同场地（运行时）施工——**贴切**，因为同构正是「受力路径一致、构件按场裁剪」。

#### 主结论与推理纲要

**结论 1（可组合应用）**：给定插件集合 \(P\) 与实例类型（Sheet/Doc/Slide），Univer 实例 \(U = \mathrm{Compose}(P)\) 提供与该集合匹配的编辑/计算/渲染能力；裁剪 \(P\) 可减小体积与内存。

**推理纲要**：

1. 注册 `UniverRenderEnginePlugin`、`UniverFormulaEnginePlugin`、`*Sheets*` 等 → 依赖图由 **redi（Univer 使用的 DI 库）** 解析实例化。
2. `createUnit(UniverInstanceType.UNIVER_SHEET, workbookData)` → 触发 Sheet 类插件生命周期（Starting → Ready → Rendered → Steady）。
3. `FUniver.newAPI(univer)` → Facade 暴露 `getActiveWorkbook()`、`getRange()`、事件等，隐藏 DI 与命令细节。

**结论 2（命令三分法）**：

| 类型 | 是否入快照 | 可派发子命令 | 典型用途 |
|------|------------|--------------|----------|
| **COMMAND** | 间接（编排 MUTATION） | 是 | 业务逻辑、选区判断、异步流程 |
| **MUTATION** | **是** | 否（同步） | 改单元格、插删行列、合并——协作冲突最小单元 |
| **OPERATION** | 否 | 否（同步） | 滚动、侧栏、选区 UI 状态 |

**结论的内核解释**：  
改「表格里写了什么」和改「屏幕滚到哪」要分开登记：前者要存档、能撤销、多人编辑时要对得上；后者只是界面姿势，不必写进文件。

**结论的结构工程类比**：  
**MUTATION** 像 **永久荷载**（进设计模型）；**OPERATION** 像 **施工临时支撑**（现场需要，不入竣工图）。COMMAND 是 **荷载组合规则**——决定哪些永久改动一次提交——**贴切**，因协作 OT 只需对永久改动做变换。

#### 常见误区与边界

| 误区 | 事实 |
|------|------|
| 「装了 `@univerjs/sheets` 就有 Excel 界面」 | 还需 `sheets-ui`、`ui`、`engine-render` 等；Node headless 故意不装 UI 插件 |
| 「Facade 任意时刻可调」 | 部分 API 需 `LifecycleStages.Rendered/Steady`；改数据 API 常返回 **Promise（异步结果对象）** |
| 「OSS = 完整 Office」 | 协作、导入导出、图表等多为 Pro；OSS 是 SDK 骨架 + 核心编辑 |
| 「Preset 与 Plugin 可随意混装」 | 同一能力重复注册会冲突；版本必须全体 `@univerjs/*` 对齐 |
| 「HyCAD 可直接用 Univer 文件格式当真相源」 | 020 约定 **HyCAD.Tables / TableGrid 为真相源**；Univer 只是视图+编辑壳 |

**误区的内核解释**：  
容易以为买一个「Excel 盒子」就全能；其实 Univer 卖的是「零件和说明书」，UI、公式、协作要按清单自己装，装重复还会打架。

**误区的结构工程类比**：  
把 **OSS 当整栋精装房** 会塌期望——它实际是 **结构框架 + 机电预埋**；精装（Pro 协作、格式）要另签——**贴切**，与 020 中方案 C「稳定/可靠分低于 ReoGrid」一致。

### 2. 插件与同构

- **对象**：功能模块边界 + 运行时适配策略。
- **痛点**：浏览器要 Canvas/DOM；Node 要无头计算；Worker 要 RPC——若三套代码则维护爆炸。

#### 最小定义/公理/假设

1. **环境分裂规则**：凡依赖 DOM/Canvas 的模块 → `*-ui` 插件；纯数据/公式 → 核心 `sheets` / `engine-formula`。
2. **实例类型**：`UNIVER`（核心）、`UNIVER_SHEET`、`UNIVER_DOC`、`UNIVER_SLIDE` 生命周期独立，延迟到首次 `createUnit` 才启动非 UNIVER 插件。
3. **抽象依赖**：如 `IClipboardService`、`IRPCChannelService` 多实现，屏蔽 Browser / Mobile / Worker / Node 差异。

**定义的内核解释**：  
同一套「算账规则」可以在办公室算（浏览器），也可以在仓库算（Node），但「装修展示」只在有人看的地方做。

**定义的结构工程类比**：  
**墙元/板元（有限元单元）** 在整体模型里方程相同，但边界条件随支座而变——Univer 用接口换边界，**贴切**。

#### 主结论

**结论**：通过插件矩阵 \( \text{Plugin} \times \text{Runtime} \)，Univer 实现 **一份业务逻辑、多运行时部署**；重计算可 offload 到 Worker/Node（RPC），主线程保交互。

**结论的内核解释**：  
重活交给后台，前台只负责流畅滑动——和餐厅前台点菜、后厨做菜分工一样。

**结论的结构工程类比**：  
**剪力墙（Shear Wall）** 抗侧向、 **框架** 抗竖向——计算与展示解耦，避免主线程「侧向超载」——**贴切**。

---

### 3. Facade API 与宿主集成

- **对象**：对外的稳定、类型化薄层（`FUniver`、`univerAPI`）。
- **痛点**：直接操作 `ICommandService` + Injector 学习曲线陡；嵌入方（HyCAD C#）只需「读写的格子」。

#### 最小定义/公理/假设

1. Plugin 模式需手动 `import '@univerjs/sheets/facade'` 等 side-effect 挂载；Preset 模式自动挂载。
2. 宿主桥接假设：**JSON 可序列化** 的消息（WebView2 `postMessage`），命令参数亦要求可序列化（官方 `ICommandInfo`）。

#### 主结论

**结论**：嵌入方应优先 Facade + 自定义 bridge 插件/脚本，而非 fork 内核。HyCAD 的 `univer-bridge.ts` 即：`loadSnapshot` / `exportSnapshot` + `hyCadBridge` 全局 + Ribbon 菜单 `postMessage` 回 C#。

**结论的内核解释**：  
跟外国客人说话请翻译，不要逼客人学内部黑话——Facade 和 bridge 就是翻译。

**结论的结构工程类比**：  
**节点（Node）** 处用 **预埋件** 连接异种构件（TS 编辑器 ↔ C# 宿主）——**贴切**。

## 关键例子

### 例 1：HyCAD Plugin 模式最小启动（验证「插件组合 = 可用表格 UI」）

本仓库 `src/HyCADTool.UniverEditor/Web/src/main.ts` 与官方 Plugin 模式一致：

```typescript
const univer = new Univer({ locale: LocaleType.ZH_CN, locales: { ... } });
univer.registerPlugin(UniverRenderEnginePlugin);
univer.registerPlugin(UniverFormulaEnginePlugin);
univer.registerPlugin(UniverUIPlugin, { container: 'app' });
// ... sheets / formula / numfmt 等
univer.createUnit(UniverInstanceType.UNIVER_SHEET, DEMO_WORKBOOK_DATA);
const univerAPI = FUniver.newAPI(univer);
installHyCadBridge(univerAPI);
postHostMessage({ type: 'ready' });
```

- **验证点**：未使用 Preset，但手动注册顺序与 CSS 导入顺序满足官方约束；`ready` 消息驱动 C# 侧 `UniverSessionLifecycle` 状态机。

**内核解释**：  
像按说明书先装地基再装墙再装窗，顺序对了房子才站得住；这里先渲染引擎再 UI 再表格，最后告诉 C#「可以送数据了」。

**结构工程类比**：  
**分层施工**：地基（render/formula）→ 主体（sheets）→ 装修（sheets-ui）→ 竣工验收（ready）——**贴切**。

---

### 例 2：`HyCadGridSnapshot` 双向桥（验证真相源边界）

C# `TableGrid` → JSON → JS `loadSnapshot`：

1. 调整行列数、像素高宽（由 mm 启发式换算）；
2. 清除旧合并，按 `cells[]` 写值并 `merge()`；
3. 编辑后 `exportSnapshot` 回 C#，再 `UniverGridSnapshotMapper.ApplyTextValues` 写入 OpLog。

- **验证点**：Univer 内部 workbook 状态不必与 `HyCAD.Tables` 字段一一对应；**快照映射层**才是集成契约。

**内核解释**：  
两个不同品牌的积木，中间要用「转接头」才能拼一起；快照就是转接头，不是把一种积木强行改名成另一种。

**结构工程类比**：  
**后浇带** 连接新旧混凝土：允许两侧收缩不同，但钢筋要对接——**贴切**。

---

### 例 3：命令监听扩展协作（边界：OSS 不含 OT 引擎）

官方模式：插件监听 `ICommandService`，收集 **MUTATION** 广播给其他客户端再 `executeCommand`。OSS 提供钩子；**Pro** 提供 OT 与冲突解决。

- **反例**：在 HyCAD PoC 中若只 `SheetValueChanged` 事件而未走完整 OpLog，会与「TableGrid 真相源 + 撤销」策略不一致。

**内核解释**：  
电话会议要 everyone 听同一份会议记录；自己记小本本（单点事件）和别人用官方会议系统（MUTATION 流）会对不上。

**结构工程类比**：  
**整体模型协同** 必须用同一 **荷载工况组合**；局部私自改荷载组合会得到不同内力——**贴切**。

## 常见误区（汇总深化）

### 误区 1：WebView2 + Univer 可完全替代 ReoGrid 路径

020 加权：ReoGrid 混合 **4.4**，Univer **4.2**（稳定/可靠更低）。Univer 强在观感与公式生态；HyCAD 还要付 **npm 构建链、Web/dist 部署、焦点/主题** 成本（见 `wpf-webview2-pitfalls` skill）。

**内核解释**：  
最好看的衣服不一定最耐脏；工地表格还要考虑 AutoCAD 里折腾稳不稳。

**结构工程类比**：  
**高强混凝土** 观感好，但 **养护条件**（WebView2 环境）苛刻，否则开裂——**贴切**。

### 误区 2：在 C# 里反射调用 Univer 程序集

Univer 是 TS/JS；正确边界是 **HyCADTool.UniverEditor（WPF+WebView2）** 与主工程 JSON 协议，而非 NuGet 引用 Univer。

**内核解释**：  
不能指望把外国引擎直接焊在中国车架上，中间要有变速箱（WebView2 + 消息协议）。

**结构工程类比**：  
异种材料连接必须 **专用连接器**，不能对焊——**贴切**。

## 用途小结

| 场景 | Univer OSS 是否合适 |
|------|---------------------|
| 嵌入 SaaS / 内部工具表格 | **强**：Apache-2.0、Facade、插件裁剪 |
| Node/AI 批量读写在库表 | **强**：Headless + 公式引擎 |
| HyCAD 工程表格（CAD 落图、FieldKey） | **中**：作 PoC/备选 C；真相源仍 TableGrid |
| 离线 AutoCAD 插件、无 Node 构建 | **弱**：需附带 Web/dist 与 WebView2 运行时 |
| 实时多人协作 | **Pro**；OSS 仅提供 MUTATION 监听扩展点 |

**HyCAD 当前策略（020/实施）**：主路径 ReoGrid + Fluent.Ribbon；Univer 为 **N38 / OpenUniverTableEditorCommand** 试验线，验证快照桥与 Ribbon 扩展，不替换 HyCAD.Tables。
