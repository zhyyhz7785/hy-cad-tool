# HyCAD 与 DWG 平行的增量几何存储系统

> 配套阅读：`01-AutoCAD几何数据传递给AI的方案对比与推荐-2026-04-27-022600.md`
>
> 01 解决"一次性把当前选区结构化交给 AI"，本篇解决"长期、增量、可版本、二进制紧凑、可合并的几何持久层"。

---

## 1. 为什么需要一个和 DWG 平行的存储系统

DWG 痛点（站在工程化与 AI 协作视角）：

1. **每次保存都重写整个文件**：100k 实体改 1 条线，落盘几十 MB。
2. **没有版本图**：UNDO 是内存级，软件关掉就没了。
3. **协同只能整文件互发**：无法做对象级 diff / merge。
4. **黑盒二进制 + 闭源 schema**：第三方工具受限。
5. **无层叠合成**：xref 是文件级，不是对象级。
6. **AI 不可读**：必须先转 hygeom JSON 才能分析。
7. **回归测试无入口**：算法层依赖 AutoCAD API，难脱机测试。

我们想要的特性：

| 想要 | 来源参考 |
|---|---|
| 二进制紧凑（每种 entity 字段固定，不带字段名） | DWG / USD Crate |
| 自描述与 schema 版本化（避免格式锁死） | USD / Protocol Buffers |
| 内容寻址、增量、共享、压缩 | Git |
| 提交历史 DAG、分支、合并 | Git |
| 多层合成、原文件只读 + 修改写新层 | USD |
| 路径寻址（人类可读） | USD SDFPath |
| 与 DWG 平行存在，不替代 | 设计原则 |

结论方向：**DWG 继续承担"权威渲染源"的角色，旁边挂一个 HyCAD 自己的对象数据库，承担版本、增量、合并、AI、回归测试**。

## 2. DWG / DXF / USD / Git 各自怎么存

### 2.1 DWG 怎么存

DWG 是 Autodesk 私有二进制格式，公开整理来自 Open Design Alliance 的规范。

物理结构（简化）：

```text
File Header
Section Locator Records
Sections:
  - Header Variables       系统变量
  - Class Definitions      类型注册表
  - Object Map             handle -> file offset 索引
  - AcDb:Handles           handle 表
  - AcDb:Objects           真正的对象二进制段
  - AcDb:Template
  - AcDb:Preview
  - AcDb:AppInfo / AuxHeader / Security ...
压缩 + 部分加密
```

每个对象在 Objects 段内：

```text
[ handle (变长) ]
[ size ]
[ type code ]
[ payload: 按该 type 的 schema 紧密打包 bit fields ]
```

要点：

- **二进制紧凑**：字段顺序 + 类型固定，不存字段名。
- **schema 隐式**：靠 type code 索引内置 schema，外部工具不知道也能读不容易。
- **handle 全局唯一**：可作为对象身份标识。
- **整文件重写**：每次 save 重打整张表，**不增量**。
- **私有 + 闭源**：版本演进受 Autodesk 控制。
- **无版本图**：没有 commit、没有 history。
- **无层叠合成**：xref 是文件级，不是对象级。

给我们的启示：保留"二进制紧凑 + handle 索引"，避开"全量重写 + 闭源 + 无历史"。

### 2.2 DXF 怎么存

DXF 是 Autodesk 提供的开放交换格式，分 ASCII 与 Binary 两种。ASCII 版本一行一个 token，奇数行是 group code，偶数行是 value。

物理结构：

```text
SECTION HEADER
SECTION CLASSES
SECTION TABLES (LAYER, LTYPE, STYLE, DIMSTYLE, ...)
SECTION BLOCKS
SECTION ENTITIES
SECTION OBJECTS
SECTION THUMBNAILIMAGE
EOF
```

一段 Line 的实际样子：

```text
0
LINE
8
HY-WALL
10
0.0
20
0.0
30
0.0
11
1000.0
21
0.0
31
0.0
```

要点：

- **文本可读**：AI / 工具友好。
- **group code 自描述**：`8` 表示 layer，`10/20/30` 表示起点 X/Y/Z。
- **冗余巨大**：每个值都拖一个 group code 行，文件比 DWG 大数倍。
- **整文件重写**：跟 DWG 一样不增量。
- **二进制 DXF 存在**：只是把 group code 编成 short，仍然不增量。

给我们的启示：自描述 + 工具友好的思路保留，但 group code 这种"字段名都写一遍"的低密度形式不要。

### 2.3 USD 怎么存

USD（Universal Scene Description, Pixar）是这套设计中最值得借鉴的。它本身就是为"很多人共同编辑同一个庞大场景，但每个人只改一小部分"而生。

核心概念：

| 概念 | 说明 |
|---|---|
| Prim | 场景中的节点，例如 `/World/Geom/Cube` |
| Property | Prim 上的字段（attribute / relationship） |
| Layer | 一个 .usda（文本）/ .usdc（二进制 Crate）/ .usdz（zip 包）文件 |
| Stage | N 个 Layer 按顺序叠加合成出来的最终视图 |
| Composition Arcs | subLayers / references / payloads / inherits / specializes / variantSets |
| Sparse Override | 每层只写"我改了什么"，原层不动 |

合成顺序（强弱）：**LIVRPS** = local → inherits → variant → references → payload → specializes。

意味着：

- 原始资产 `asset.usd` + 修改层 `shot_001.usd` + 个人修改 `my_edit.usd`，打开时合成
- "原文件只读 + 修改写到新层"是**核心范式**
- 每个 Layer 内部其实是全量重写，跨 Layer 之间靠合成实现增量

USD Crate（.usdc）二进制特点：

- **mmap 友好**：文件结构允许直接 memory-map 用
- **string token 表**：所有字符串建索引共享
- **field/value 去重**：相同字段值只写一份
- **path token 表**：SDFPath 不存全字符串，只存 token id
- **schema-based**：Prim 与 attribute 类型有正式 schema

给我们的启示：

- Layer 合成范式直接拿来
- Crate 的 token 表 + 字段去重直接借鉴
- SDFPath 风格的路径寻址（`/entities/by-handle/3F2A`）比 GUID 友好

USD 不是的：

- 不是 content-addressable（不是 git）
- Layer 内部不天然共享，靠 token 表局部共享
- 文件级版本仍要靠外部 git/Perforce/SVN 配合

### 2.4 Git 怎么存

Git 是版本系统的事实标准，物理结构非常干净。

```text
.git/
  HEAD                                当前分支
  config
  refs/
    heads/<branch>                    分支指针 -> commit hash
    tags/<tag>                        标签指针
  objects/
    <hh>/<hash[2..]>                  zlib 压缩的对象
    pack/<id>.pack + <id>.idx         打包后的 delta 共享
```

四类对象：

| 对象 | 内容 |
|---|---|
| blob | 原始文件字节流 |
| tree | 目录快照（mode + name + hash） |
| commit | parent + tree + author + message |
| tag | 带签名的指针 |

存储原则：

- **content-addressable**：内容 SHA 哈希作名字
- **快照而非 diff**：每次 commit 是完整 tree，相同内容自动共享
- **packfile delta**：在 pack 阶段对相似 blob 做 delta 压缩
- **DAG**：commit 形成有向无环图，分支只是指针，merge 自然

要点：

- 每次提交是不可变快照
- 重复内容只存一份（同 hash 共享）
- 路径与内容解耦：blob 不知道自己叫什么，由 tree 命名

给我们的启示：**对象级 content-addressable + tree + commit + pack delta** = 版本系统的最优解。

### 2.5 综合对比

| 维度 | DWG | DXF | USD | Git | HyCAD 目标 |
|---|---|---|---|---|---|
| 物理形态 | 二进制私有 | 文本 / 二进制 | 文本 .usda + 二进制 .usdc | 二进制对象库 | 二进制对象库 |
| 自描述 | 否（schema 隐式） | 是（group code） | 是（schema） | 是（type 字段） | 隐式 schema + 版本号 |
| 紧凑度 | 高 | 低 | 高 | 高（pack 后） | 高 |
| 增量保存 | 否 | 否 | 是（layer 维度） | 是（commit + pack） | 是（commit + pack） |
| 内容寻址 | 否（handle） | 否 | 否（path） | 是（hash） | 是（hash） |
| 历史 / 版本 | 无 | 无 | 文件级靠外部 | DAG | DAG |
| 分支 / 合并 | 无 | 无 | 文件级靠外部 | 内建 | 内建 |
| 多层合成 | 无 | 无 | 内建 LIVRPS | 无 | 借鉴 USD |
| 字符串去重 | 否 | 否 | 是（Crate token 表） | 否 | 是 |
| AI 友好 | 差 | 中 | 中 | 好 | 好 |
| 与 DWG 关系 | 自身 | 互导 | 不直接 | 不直接 | **平行** |

## 3. HyCAD 设计：hyob 对象库

命名建议：**HyCAD Object Base**，简称 `hyob`。

设计原则：

1. **二进制紧凑**：取 DWG / USD Crate 的"schema 隐式 + 字段无名"。
2. **内容寻址**：取 Git 的 SHA 哈希作对象名。
3. **DAG 历史**：取 Git 的 commit / tree / parent 模型。
4. **层叠合成**：取 USD 的 Layer + Sparse Override。
5. **路径寻址**：取 USD SDFPath 风格命名空间。
6. **schema 显式版本化**：避免 DWG 的"格式锁死"，每个对象头里带 type_id + version。
7. **平行 DWG，不替代**：DWG 渲染、hyob 演进。

### 3.1 数据模型

四级抽象：

```text
Stage  = compose(Layer*, order)
Layer  = sequence of Commits
Commit = { parent*, tree, author, message, time, command }
Tree   = { name -> (kind, hash) }
Object = bytes (typed by header)
```

类比：

| HyCAD | Git | USD |
|---|---|---|
| Object | blob | (无对应) |
| Tree | tree | (无对应) |
| Commit | commit | (无对应) |
| Layer | branch | Layer |
| Stage | working tree | Stage |

### 3.2 Object 二进制格式

每个对象（Line / Polyline / Arc / Circle / Text / MText / BlockRef / Dim / LayerDef / Style / 自定义业务类型...）都是一个独立的 blob：

```text
[ magic         : 2 bytes  = "HO" ]
[ schema_ver    : 1 byte             该 type 的 schema 版本号 ]
[ type_id       : 2 bytes            HyCAD 类型码 ]
[ flags         : 1 byte             压缩 / 编码标志 ]
[ payload_len   : 4 bytes ]
[ payload       : payload_len bytes  按 schema 紧密打包 ]
[ checksum      : 4 bytes  CRC32 ]
```

**不存字段名**。原因：

- type_id + schema_ver 唯一确定 schema
- schema 内字段顺序与类型固定
- 这是 DWG 节省体积的核心，对 HyCAD 一样适用
- 字符串值（layer 名、文字内容、块名）走单独的 String/Token 对象类型，Tree 引用 hash，避免重复存储——跟 USD Crate 的 token table 一致，也跟 Git blob 共享一致

举例 Line v1（type_id = 0x0001）：

```text
double  start_x
double  start_y
double  start_z
double  end_x
double  end_y
double  end_z
hash32  layer_ref       <- 引用 Object(LayerDef) / String
uint8   color_kind      <- 0=ByLayer 1=Index 2=TrueColor
( uint8 r, uint8 g, uint8 b )    if color_kind == TrueColor
hash32  linetype_ref
```

举例 Polyline v1：

```text
uint8   flags           <- bit0=closed bit1=hasBulge bit2=has3D
uint32  vertex_count
loop vertex_count:
  double x
  double y
  if flags.has3D : double z
  if flags.hasBulge : float bulge
hash32  layer_ref
...
```

举例 String v1（用于 layer 名 / 文字内容 / 块名等）：

```text
uint32  byte_len
bytes   utf8_bytes
```

字符串自身也是 content-addressable，相同 layer 名只存一次。

### 3.3 Tree 结构

借 USD SDFPath 风格的命名空间：

```text
/
  meta/
    units            -> hash of Object(Units)
    extents          -> hash of Object(Extents)
    document         -> hash of Object(DocumentMeta)
  layers/
    HY-WALL          -> hash of Object(LayerDef)
    HY-ROAD-CENTER   -> hash of Object(LayerDef)
  styles/
    HY-TEXT          -> hash of Object(TextStyle)
    HY-DIM           -> hash of Object(DimStyle)
  blocks/
    ANCHOR_BOLT      -> hash of Tree(BlockDef)
  entities/
    by-handle/
      3F2A           -> hash of Object(Line)
      3F2B           -> hash of Object(Polyline)
    by-layer/
      HY-WALL        -> hash of Tree(...)
  spaces/
    model            -> hash of Tree(...)
    layout-1         -> hash of Tree(...)
```

Tree 节点二进制格式：

```text
[ entry_count : 4 bytes ]
loop entry_count:
  [ kind     : 1 byte    1=Object 2=Tree ]
  [ name_len : 2 bytes ]
  [ name     : utf-8 bytes ]
  [ hash     : 32 bytes   SHA-256 ]
```

### 3.4 Commit 结构

```text
{
  parents : [hash, hash?],     // 0 = 初始；1 = 普通；2 = merge
  tree    : hash,
  author  : string,
  email   : string?,
  time    : iso8601,
  command : string?,           // 触发该 commit 的 HyCAD 命令名
  message : string,
  meta    : { ... }            // 命令参数、选择集 handles 等
}
```

Commit 自身也是一个 Object（type_id = Commit）。

### 3.5 Layer（USD 风格）

每一层是一个独立的 commit 链：

```text
{
  name      : "shot_001",
  head      : <commit hash>,
  base      : <layer name>?,    // sub-layer 引用
  strength  : int,               // 合成强度
  visible   : bool,
  readonly  : bool
}
```

合成规则（简化 LIVRPS）：

```text
StrongerLayer.override  >  WeakerLayer.original
```

每层独立维护一条 Git-style DAG。

### 3.6 Stage 合成

Stage 是当前打开的视图，由若干 Layer 顺序叠出来：

```text
Stage:
  layers: [
    { name: "base.dwg",      kind: "dwg-mirror", strength: 1 },
    { name: "shot_001.hyob", kind: "hyob",       strength: 5 },
    { name: "my_edit.hyob",  kind: "hyob",       strength: 9 }
  ]
```

按 path（`/entities/by-handle/3F2A`）查找时，强层优先，弱层提供基础。

## 4. 物理布局

DWG 文件本体不动，旁边挂一个 `.hyob/` 目录：

```text
<DWG-FILE>.dwg                          AutoCAD 权威文件
<DWG-FILE>.hyob/                        HyCAD 平行存储
  HEAD                                  当前 layer 名
  config
  objects/
    <hh>/<hash[2..]>                    每个对象 zstd 压缩
  trees/
    <hh>/<hash[2..]>
  commits/
    <hh>/<hash[2..]>
  pack/
    <id>.pack                           批量打包 + delta
    <id>.idx
  refs/
    heads/main
    heads/shot_001
    heads/my_edit
  layers/
    main.layer
    shot_001.layer
  stage.json                            当前 stage 合成定义
  index/
    handle-to-hash.bin                  加速 handle -> hash 查询
    spatial.bin                         可选包围盒空间索引
  log/
    operations.jsonl                    命令日志
```

跟 git 几乎一一对应：

| Git | hyob |
|---|---|
| `.git/` | `.hyob/` |
| `HEAD` | `HEAD` |
| `objects/` | `objects/` + `trees/` + `commits/` |
| `refs/heads/` | `refs/heads/` |
| `pack/` | `pack/` |

## 5. 增量与压缩

### 5.1 内容寻址 = 天然增量

每次保存：

- 没改的对象 → hash 不变 → 不重写
- 只改了 10 个 entity → 只新写 10 个 object + 1 个 tree + 1 个 commit
- 跟 Git 完全一样

例子：100k 实体、改 1 条线：

| 方案 | 落盘量 |
|---|---|
| DWG 重写 | 几十 MB |
| DXF 重写 | 几百 MB |
| USD sparse override | 几 KB |
| **hyob commit** | **几 KB** |

### 5.2 Pack delta

到达阈值（如 loose objects > 5000 个）后：

1. 把同 type 的对象排序
2. 选 base + 计算 xor / lz delta
3. 整体 zstd 压缩，写 `.pack` + `.idx`
4. 删除已打包的 loose objects

跟 Git pack 一致，也跟 USD Crate 的 field dedup 思路一致。

### 5.3 多层合成增量

新建设计分支：

- 不复制 base 层任何对象
- 只在新 layer 写 override
- 切回原版只需要把该 layer 拿掉

跟 USD 完全一致。

## 6. 与 DWG 协同（平行而不是替代）

```text
保存时：
  AutoCAD 写 example.dwg          所有人能打开
  HyCAD   写 example.hyob/        给版本系统、AI、回归测试

打开时：
  AutoCAD 读 example.dwg
  HyCAD   读 example.hyob/
  reconcile：
    handle <-> hash 索引一致
    冲突时 dwg 是渲染权威，hyob 是版本权威
```

reconcile 策略：

| 场景 | 处理 |
|---|---|
| 用户在 AutoCAD 改了图但没经过 HyCAD 命令 | HyCAD 启动时扫描 DWG，发现 hash 不一致的对象，自动 commit 一个 `external-edit` 提交 |
| 用户在 HyCAD 命令里改了图 | 命令负责同步写 DWG + hyob commit |
| 写 DWG 失败 | hyob 仍记录提交，标记 `dwg-pending`，下次启动重试同步 |
| 用户在另一台机器拷走 .dwg 没拷 .hyob/ | hyob 历史本地保留，不丢；返回时按 handle 重新 reconcile |

## 7. 与 01 文档（hygeom）的关系

| 用途 | 推荐格式 |
|---|---|
| 一次性几何分析交给 AI | **01 hygeom JSON 快照** |
| 长期版本演进 | **02 hyob 对象库** |
| 命令回归测试输入 | hyob commit 序列导出 |
| 协同合并 | hyob layer + merge |
| 灾难恢复 | hyob commit 历史 |
| 出图 / 互导 / 给非 HyCAD 用户 | DWG / DXF |

hygeom 可以由 hyob 一键导出：

```text
hyob commit
  -> 选择 /entities/by-handle/*
  -> 解码每个 Object
  -> 输出 hygeom JSON
```

也就是说：

- **hyob 是引擎**
- **hygeom 是某个时刻的 AI 视图**
- **DWG 是渲染产物**

## 8. C# API 草案

```csharp
public sealed class HyobRepository
{
    public static HyobRepository Open(string dwgPath);
    public static HyobRepository Init(string dwgPath);

    public Layer CurrentLayer { get; }
    public Commit Head => CurrentLayer.Head;

    public Hash WriteObject(IHyobObject obj);
    public IHyobObject ReadObject(Hash hash);

    public Hash WriteTree(Tree tree);
    public Tree ReadTree(Hash hash);

    public Commit Commit(Hash tree, string message, IDictionary<string, object> meta);

    public void Checkout(string layer);
    public Layer CreateLayer(string name, string baseLayer);

    public DiffResult Diff(Hash from, Hash to);
    public MergeResult Merge(string source, string target);
    public Stage Compose(IEnumerable<Layer> layers);
}
```

每个 HyCAD 命令的执行模板：

```csharp
using var tx = repo.BeginTransaction();
var stage    = repo.LoadStage();
var modified = command.Apply(stage);
var newTree  = repo.WriteTree(modified);
repo.Commit(newTree, $"{commandName} {args}", meta);
tx.Complete();
```

执行完一个 HyCAD 命令 = 一次 hyob commit。这就让"命令历史"等价于"git log"。

| 阶段 | 目标 | 内容 |
|---|---|---|
| 0 | 接力 01 | 把多次 hygeom snapshot 用 commit 串成一条简化历史，验证用户体验 |

每个阶段都能独立交付价值，1 阶段就已经能用作 AI 分析底盘。

## 10. 关键设计原则

1. **DWG 是渲染权威，hyob 是版本权威**：双轨并行，互不替代。
2. **二进制紧凑 + 内容寻址 = 天然增量**：无需手写 diff 算法。
3. **schema 显式版本化**：每个 Object 头里带 type_id + schema_ver，避免 DWG 闭格式陷阱。
4. **path 寻址用 USD SDFPath 风格**：可读、可命名空间、可分块查询。
5. **数据模型与 git 同构**：开发者直接复用心智模型，工具链可以借 git 套路。
6. **Layer 合成借鉴 USD**：原文件只读、修改写新层、合成出最终视图。
7. **不重新发明字段语义**：直接复用 HyCAD Domain 类型，schema 与 Domain 一一对应。
8. **AI / 测试 / 历史共用一套底盘**：hygeom、回归测试、版本浏览都从同一个 hyob 出。

## 11. 一句话总结

> hyob = DWG 的二进制紧凑 + USD 的层叠合成 + Git 的内容寻址与 DAG，挂在每张 .dwg 旁边，专门负责 HyCAD 自己的版本、增量、合并、AI 与回归测试。
