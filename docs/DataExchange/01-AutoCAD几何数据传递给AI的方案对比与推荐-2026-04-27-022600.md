# 01 - AutoCAD 几何数据传递给 AI 的方案对比与推荐

> 解决"DWG 是私有二进制，AI 不能直读"这个工程瓶颈。
> 给出主路 / 旁路 / 通道三层组合方案，沿用 HyCAD 已验证的 `.roaddesign.json` 模式。

---

## 0. 一句话结论

**主路 = Drawing Snapshot JSON（DWG 同级 `.hycad-snapshot.json`）；旁路 = 同名 SVG 缩略图；通道 = 文件落盘 → 后期升级 MCP。**

第一步只做一件事：在 AutoCAD 里写一个 `hyAiExport` 命令，把当前选择集（或当前视口）按规范化 JSON 写盘到 DWG 同级目录，AI 用 `Read` 读取即可。其余通道、双向回写、MCP 都是这一步的渐进升级。

---

## 1. 问题定义

```text
现状：
  AutoCAD ──[DWG 私有二进制]──> 用户   AI 看不见
  AutoCAD ──[命令行文字]────> 用户   AI 拿不到几何

目标：
  AutoCAD ──[规范化文本] ──> AI ──[结构化指令]──> AutoCAD
  + 可视预览（人 / AI 都能看图）
  + 可追溯（每个实体有稳定 ID）
  + 可分包（大图不爆 token）
  + 可双向（AI 改完能写回 DWG）
```

需要同时满足：

| # | 需求 | 必要性 |
|---|---|---|
| 1 | AI 文本可读，无需特殊解码 | 强必要 |
| 2 | 几何完整性（点/线/弧/多段线/块/文字/标注/填充） | 强必要 |
| 3 | token 紧凑（1 千实体不撑爆 200K 上下文） | 强必要 |
| 4 | 从 AutoCAD 导出成本低（用现成 API） | 强必要 |
| 5 | AI 改完能写回 DWG | 中等必要（Stage 2） |
| 6 | 人类可视化调试 | 中等必要 |
| 7 | 可与现有 `.roaddesign.json` / `XData` 对齐 | 强必要 |

## 2. 候选方案矩阵

按"AI 可读性 / 几何完整性 / token 紧凑度 / 生成成本 / 反向应用 / 可视化"6 维评分（★★★★★=5 分，×=不满足）。

| 方案 | AI 可读 | 几何完整 | token | 生成 | 反向应用 | 可视化 | 综合 | 适用 |
|---|:---:|:---:|:---:|:---:|:---:|:---:|:---:|---|
| **A. DXF（AutoCAD ASCII 原生）** | ★★ | ★★★★★ | ★ | ★★★★★ | ★★★ | × | 中 | 全量备份 |
| **B. 自研 JSON Snapshot** | ★★★★★ | ★★★★ | ★★★★ | ★★★★ | ★★★★★ | × | **高** | **主推** |
| C. GeoJSON | ★★★★ | ★★★ | ★★★ | ★★★ | ★★★ | ★★★★ | 中 | 仅 2D 平面，可作 B 的子集 |
| **D. SVG** | ★★ | ★★ | ★★ | ★★★ | ★ | ★★★★★ | 中 | **可视旁路** |
| E. Mermaid / 自然语言 | ★ | ★ | ★★★★★ | ★★ | × | ★★★ | 低 | 仅口头说明 |
| F. 截图 PNG/JPG | × | × | × | ★★★★★ | × | ★★★★★ | 低 | 配菜（视觉模型） |
| G. STEP / IFC | ★ | ★★★★ | ★ | × | ★ | ★★ | 低 | 错域（3D 制造 / BIM） |
| H. WKT / WKB | ★★★ | ★★ | ★★★ | ★★★ | ★★★ | × | 中 | GIS 子集 |
| I. 自定义 token 序列 | ★★★ | ★★★ | ★★★★★ | ★★ | ★★ | × | 中 | 极致紧凑实验 |
| J. 直接喂 ObjectId 列表 | × | × | × | ★★★★★ | × | × | 极低 | 完全无效 |

### 各方案要点

**A. DXF**
AutoCAD 自带导出，几何最完整，但同一个圆要 10+ 行 group code，token 极度浪费；字段名是 `10` `20` `40` 这种数字代码，AI 需要 DXF 字典才能读懂。**仅作全量备份兜底。**

**B. 自研 JSON Snapshot**（主推）
字段名英文语义化（`type:"line"` `geom:[[0,0],[100,0]]`），AI 一眼能读；可按业务自由裁剪（比如不传 lineweight 节省 token）；可直接对应 Domain 模型；与 `.roaddesign.json` 同模式。

**C. GeoJSON**
开放标准、工具链多，缺点是 spec 严格只覆盖点/线/面，没有圆弧/块/文字/标注，需要扩展 properties 才能放 CAD 特有信息——本质上扩展后就退化成 B。

**D. SVG**
浏览器可直开，AI 视觉模型可吃图，几何用 `<line>` `<path>` 表达；缺点是文字 / 标注 / 块语义会丢，反向写回成本高。**与 B 配对作旁路最佳。**

**E. Mermaid / 自然语言**
"图上有 3 条线，从原点到 X 方向 100"——只能描述拓扑，无法描述坐标精度，**仅用于人对人讲方案**。

**F. PNG/JPG 截图**
AI 视觉模型能识别，但数不清坐标、改不动几何。**仅作辅助视觉，不能作主路。**

**G. STEP / IFC**
错域。STEP 是 3D 机械装配交换，IFC 是 BIM 构件交换，AutoCAD 2D 图纸用这两个就是大炮打蚊子。

**H. WKT / WKB**
`POINT(0 0)` `LINESTRING(0 0, 100 0)`——GIS 习惯，纯几何很紧凑，但同样不带块/标注/XData，是 B 的纯几何子集。

**I. 自定义 token 序列**
类 G-code、类 PostScript：`L 0,0 100,0; C 50,50 r10` 之类。极致紧凑，但每个项目要重新教 AI 一次语法，违反"零样本可读"原则。**实验性。**

**J. 直接给 ObjectId 列表**
完全没有上下文。AI 不知道每个 Id 对应什么，等于给一堆指针让外人解引用——**无效方案，提到只是为了排除。**

## 3. 主推方案：三层组合

```text
┌─────────────────────────────────────────────────┐
│  Layer A  主路    JSON Snapshot                  │  AI 读 + 写
│           DWG 同级 *.hycad-snapshot.json         │
├─────────────────────────────────────────────────┤
│  Layer B  旁路    SVG Thumbnail                  │  AI 看 / 人调试
│           DWG 同级 *.hycad-snapshot.svg          │
├─────────────────────────────────────────────────┤
│  Layer C  通道    传输方式                       │
│   Stage 1: 文件落盘 + AI Read                    │  ← MVP
│   Stage 2: MCP Server in HyCAD                  │  ← 进阶
│   Stage 3: 增量 Diff + 选择性查询                │  ← 大图优化
└─────────────────────────────────────────────────┘
```

### 3.1 Layer A：JSON Snapshot Schema v1

设计原则：**"几何 + 属性 + 业务 + 视图" 四块分离，引用而非嵌套**。

```text
{
  "schemaVersion": "hycad/cad-snapshot/v1",
  "drawing": {
    "fileName": "xxx.dwg",
    "exportTime": "2026-04-27T02:26:00Z",
    "units": "mm",
    "extents": { "min": [0,0], "max": [10000,8000] },
    "scale": 40
  },
  "viewport": { "active": "ModelSpace", "center": [...], "size": [...] },

  "layers": [
    { "name": "0",      "color": 7, "lineWeight": 0.25, "frozen": false },
    { "name": "钢筋",   "color": 1, "lineWeight": 0.35, "frozen": false }
  ],

  "blocks": [
    { "name": "AnchorBolt-M24",
      "basePoint": [0,0],
      "entities": [ ... ] }
  ],

  "entities": [
    { "id": "E1", "handle": "1A2",
      "type": "line",
      "layer": "0",
      "geom": [[0,0],[100,0]] },

    { "id": "E2", "handle": "1A3",
      "type": "polyline",
      "layer": "钢筋",
      "geom": { "vertices": [[0,0],[100,0],[100,80]],
                "closed": false,
                "bulges": [0,0] } },

    { "id": "E3", "handle": "1A4",
      "type": "circle",
      "layer": "螺栓",
      "geom": { "center": [50,50], "radius": 12 } },

    { "id": "E4", "handle": "1A5",
      "type": "blockRef",
      "layer": "螺栓",
      "geom": { "name": "AnchorBolt-M24",
                "position": [200,200],
                "scale": [1,1,1],
                "rotation": 0,
                "attributes": { "TAG": "M24-01" } } },

    { "id": "E5", "handle": "1A6",
      "type": "text",
      "layer": "TEXT",
      "geom": { "position": [10,10], "content": "EL ±0.000",
                "height": 3.5, "rotation": 0 } },

    { "id": "E6", "handle": "1A7",
      "type": "dimension",
      "subType": "rotated",
      "layer": "DIM",
      "geom": { "p1": [0,0], "p2": [1000,0],
                "dimLine": [500,200], "rotation": 0 },
      "text": "1000" },

    { "id": "E7", "handle": "1A8",
      "type": "hatch",
      "layer": "HATCH",
      "geom": { "loops": [ [...] ], "pattern": "ANSI31", "scale": 1 } }
  ],

  "xdata": [
    { "entityId": "E4",
      "appName": "HYAB",
      "fields": { "diameter": 24, "anchorageLength": 500 } }
  ]
}
```

实体 `type` 枚举（v1 必含）：

```
line, polyline, circle, arc, ellipse, spline,
text, mtext,
dimension (rotated/aligned/radial/diametric/angular/ordinate),
mleader, leader,
hatch, solid,
blockRef
```

未列入的（v2 再补）：xref、表格 Table、3D Solid、Surface、点云。

### 3.2 Layer B：SVG 旁路

目的：

1. AI 视觉模型能直接"看图"，弥补纯文本对空间布局的弱感知。
2. 人类调试时浏览器直开，比 DWG 启动快 100 倍。

约束：

- 仅几何骨架（line / polyline / circle / arc / text 占位框），**不画填充、不画箭头、不画图层颜色**。
- 一个实体一个 `<g id="E1">`，与 JSON 的 `entities[].id` 一一对应——AI 在 SVG 看到坐标后能反查 JSON 拿全量属性。
- 文字仅占位（`<rect>` 表达包围盒 + `data-content`），不真渲染——避免字体兼容问题。
- viewBox 与 JSON `drawing.extents` 一致。

### 3.3 Layer C：传输通道

#### Stage 1（MVP）：文件落盘

- HyCAD 写：`<dwg目录>/<dwg名>.hycad-snapshot.json` + `.svg`
- AI 读：`Read` 工具直读
- 优点：零基础设施，与 `.roaddesign.json` 同模式
- 缺点：每次手动 export → 改动 → 重新 export

#### Stage 2：MCP Server in HyCAD

- HyCAD 进程内开 MCP Server（gRPC over stdio 或 HTTP localhost）
- 暴露三个 tool：

  | tool | 输入 | 输出 |
  |---|---|---|
  | `cad.snapshot` | filter（图层 / 选择集 / 视口） | JSON Snapshot |
  | `cad.query` | 几何条件 / ID 列表 | 子集 JSON |
  | `cad.applyPatch` | RFC 6902 JSON Patch | 应用结果 + 新 ID 表 |

- 优点：实时；AI 能按需拉子集，省 token
- 缺点：要做进程间通信、并发控制、AutoCAD 单线程访问规则

#### Stage 3：增量 Diff + LOD

- 大图（万级实体）一次全量必爆 token
- 策略 A：**LOD 分级查询**——先只传 `{id, type, bbox}` 让 AI 看大局，再按 ID 拉详细
- 策略 B：**Diff 同步**——首次全量，后续只传变更
- 策略 C：**视口裁剪**——只传当前 viewport 内的实体
- 策略 D：**业务分包**——按图层（"只拿钢筋层"）、按选择集（"只拿用户选中的"）

### 3.4 双向往返：JSON Patch 协议

AI 要改图时，**不让 AI 直接重新生成整张 JSON**，而是输出 RFC 6902 增量 Patch：

```text
[
  { "op": "replace",
    "path": "/entities/E3/geom/radius",
    "value": 15 },

  { "op": "add",
    "path": "/entities/-",
    "value": { "id": "E99", "type": "text",
               "layer": "TEXT",
               "geom": { "position": [100,100],
                         "content": "M24-02", "height": 3.5 } } },

  { "op": "remove",
    "path": "/entities/E7" }
]
```

HyCAD 侧由 `CadPatchApplier` 解析：

| op | 对应 AutoCAD 操作 |
|---|---|
| add | 在对应 BlockTableRecord 创建新 Entity |
| replace | 在事务内修改既有 Entity 属性 |
| remove | 在事务内 erase Entity |
| move/copy | 复合操作 |
| test | 仅校验当前值（用于乐观锁） |

**ID 稳定性是协议核心**——AI 拿到的 `E1`/`E2` 必须能稳定映射回 AutoCAD `Handle`。Snapshot 导出时用 `Handle` 字符串作 `id`，不用临时序号。

## 4. token 估算与分包策略

### 4.1 体积估算

| 实体数 | JSON 字节 | 大致 token | Claude 200K 占比 |
|---:|---:|---:|---:|
| 100 | ~5 KB | ~1.5 K | 0.7% |
| 1,000 | ~50 KB | ~15 K | 7% |
| 10,000 | ~500 KB | ~150 K | 75% |
| 100,000 | ~5 MB | 爆 | 必须分包 |

经验值：**1 万实体以下可一次喂；上万必须 LOD / 分包**。

### 4.2 分包优先级

```
1. 选择集    selectionSet  ── 用户选中即圈定范围（最可控）
2. 图层      byLayer       ── 业务相关层只拿一次
3. 视口      byViewport    ── 当前能看到的才传
4. 几何范围  byBoundingBox ── 给一个矩形框
5. 类型      byType        ── 只要钢筋线、只要标注
```

### 4.3 紧凑写法约定

- 坐标统一保留 3 位小数（mm 级别精度足够）：`[100.123, 200.456]`
- 默认值省略：`color` 等于图层默认时不写
- 默认 layer "0" 可省
- 数组优先于对象：line 直接 `[[x1,y1],[x2,y2]]`，不写 `{from, to}`
- 单位声明一次（`drawing.units`），实体内不重复

## 5. 与 HyCAD 现有体系对接

### 5.1 已有的"子集"

`.roaddesign.json` / `.roadproject.json`（参见 `RoadJsonExportService.cs`）已实现：

- DWG 同级目录、同 stem 命名
- 命令收尾时同步落盘（`SaveForDocument`）
- Newtonsoft 序列化、UTF-8 indented
- IsoDate / InvariantCulture
- 空 / 路径不可解析时静默跳过

新方案的 `.hycad-snapshot.json` 沿用全部约定。**不是另起炉灶，而是把领域专用的扩展为通用的。**

### 5.2 新建切片：`Features/AiBridge`

```
Features/AiBridge/
├── Domain/
│   ├── CadSnapshot.cs           聚合根
│   ├── CadEntityDto.cs          实体 DTO
│   ├── CadPatch.cs              RFC 6902 Patch 模型
│   └── ...
├── Infrastructure/
│   ├── CadSnapshotSerializer.cs    AutoCAD Entity → DTO（Stage 1 核心）
│   ├── SvgPreviewWriter.cs         DTO → SVG（Layer B）
│   ├── CadPatchApplier.cs          Patch → AutoCAD API（Stage 2 核心）
│   └── ...
├── Commands/
│   ├── ExportSnapshotCommand.cs    [hyAiExport]   导出当前选择集
│   ├── ApplyPatchCommand.cs        [hyAiApply]    应用 AI 给的 patch
│   └── OpenAiBridgePanelCommand.cs [hyAiPanel]    可视化面板
└── Views/
    └── AiBridgePanel.xaml          Stage 3 才做
```

### 5.3 ID 持久化

- 默认 Snapshot.id = AutoCAD Handle（dwg 内稳定，对外可用）
- 跨 dwg 引用需要时，再加业务 GUID 写到 `ExtensionDictionary`（复用 `ExtensionDictionaryService`）

### 5.4 与 ClusterPanel / AnchorBolt 联动

- Cluster 跑完点聚类后，可调 `CadSnapshotSerializer` 把"聚类结果 + 候选标注位置 + 评分"导出成 JSON 给 AI 复审
- AI 给 Cluster 反馈：哪个标注位置不好、应换到哪
- AnchorBolt 同理：`AnchorBolt[]` + `BoltData` 是天然的 `entities + xdata` 子集

## 6. 实施分阶段

| Stage | 工期估算 | 必交付 | 可放后 |
|---|---|---|---|
| **0. 决策** | 0.5 天 | Schema v1 字段冻结、命名约定确认 | — |
| **1. MVP** | 1~2 周 | `CadSnapshotSerializer` 覆盖 line/polyline/circle/arc/text/blockRef/dimension/hatch；`hyAiExport` 命令；SVG 旁路；选择集模式 | xdata、xref、table |
| **2. 双向回写** | 2~4 周 | `CadPatchApplier`；handle 稳定 ID；冲突检测（patch 时图被改过） | merge 算法、合并冲突 UI |
| **3. MCP** | 2~4 周 | HyCAD 进程内 MCP Server；3 个 tool；线程模型 | 远程 MCP、多文档 |
| **4. 闭环** | 4~8 周 | 与 ClusterPanel / AnchorBolt 业务联动；AI 注释生成 → 应用 → 校核报告 | 全图 AI 自动化 |

每个 Stage 的产出独立可用，**Stage 1 跑通就能立刻给项目带来价值**（手动 export 也比当前"AI 完全瞎"强一个数量级）。

## 7. 决策点（动手前必须确认）

| # | 决策 | 默认值 | 备选 |
|---|---|---|---|
| D1 | 是否含 XData / 扩展字典 | 含 | 不含（节省 token） |
| D2 | 默认导出范围 | 选择集 | 全图 / 当前视口 |
| D3 | 单位 | mm（实际） | scaled mm |
| D4 | 坐标精度 | 3 位小数 | 6 位 |
| D5 | 文件后缀 | `.hycad-snapshot.json` | `.cad.json` / `.dwgview.json` |
| D6 | 文件位置 | DWG 同级目录 | 临时目录 / 内嵌 DWG XData |
| D7 | SVG 是否带文字 | 仅占位框 | 真渲染 |
| D8 | 块定义全量 vs 引用 | 全量（首次）+ 引用（后续） | 永远引用（AI 看不到内部） |
| D9 | Schema 演进策略 | `schemaVersion` 字段 + 兼容层 | hard break |
| D10 | 大图分包阈值 | 5,000 entities | 1 万 / 不分 |

## 8. 反例（不要走的路）

| ❌ 反例 | 为什么不行 |
|---|---|
| 直接 `entity.ToString()` 输出 | 丢几何坐标、丢 XData、格式杂乱 |
| 全量 DXF 喂 AI | token 爆炸；group code 0/2/8/10 无语义 |
| 仅给截图 PNG | AI 数不清坐标、改不动 |
| 让 AI 直接生成 DXF | 一行错全废，调试地狱 |
| 不带 ID 的实体列表 | 改回时 AI 不知道指代谁 |
| 把 SettingsPanel / WPF 控件 / ResourceDictionary 序列化进来 | 跨语义层泄漏，B10 / B11 同款坑 |
| 给 AI 喂 ObjectId 数值 | 跨进程后 ObjectId 失效；要用 Handle |
| 在 `Domain` 层引用 AutoCAD API 序列化 | 违反分层；序列化必须落 `Infrastructure` |
| 把 Snapshot 写在 DWG XData 里 | XData 长度受限，且会污染 DWG |
| 完全用自然语言描述图 | 不可机器再解析，无法回写 |

---

## 9. 一句话路线

> **第一步：定 Schema v1 → 写 `CadSnapshotSerializer` → 写 `hyAiExport` 命令 → 让 AI 用 `Read` 工具读到结构化 JSON。**
>
> 这一步走通，"AI + AutoCAD" 才算从"瞎子"升级为"开了眼睛但还没长手"；后续 Stage 2 让 AI 长手（双向回写），Stage 3 让 AI 长神经（MCP 实时通道）。
