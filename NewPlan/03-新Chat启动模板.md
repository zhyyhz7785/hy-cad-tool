## 🎯 通用提示技巧

### 1. 提供充分上下文

✅ **好的提示**:
```
我要继续 HyCADTool.Refactored 项目的阶段 4。
当前阶段 1-3 已完成，测试 11/11 通过。
请先阅读 NewPlan/00-项目总览与导航.md 了解背景，
然后分析 HyCADtool/HelpClass/ 目录...
```

❌ **不好的提示**:
```
继续开发
```

### 2. 明确指定参考文档

✅ **好的提示**:
```
请参考 NewPlan/阶段3-ZTools架构拆分方案.md 的设计模式，
为 HelpClass 层制定类似的拆分方案。
```

❌ **不好的提示**:
```
做一个设计方案
```

### 3. 说明期望输出

✅ **好的提示**:
```
期望输出:
1. 详细设计文档（类似阶段 3）
2. 代码实现
3. 测试代码
4. 完成报告
```

❌ **不好的提示**:
```
帮我做
```

### 4. 指定架构约束

✅ **好的提示**:
```
设计要求:
- Domain 层必须 100% 平台无关
- 遵循 SOLID 原则
- 避免过度工程化
- 添加自动化测试
```

❌ **不好的提示**:
```
随便做
```

## 💡 最佳实践

### ✅ DO（推荐做法）

1. **提供清晰的上下文**
   - 项目背景
   - 当前状态
   - 具体需求

2. **引用具体文档**
   - `NewPlan/00-项目总览与导航.md`
   - 相关阶段的文档

3. **说明架构要求**
   - Clean Architecture
   - DDD
   - SOLID

4. **明确期望输出**
   - 设计文档
   - 代码实现
   - 测试代码

### ❌ DON'T（避免做法）

1. **过于简短的提示**
   - ❌ "继续"
   - ❌ "做"

2. **缺少上下文**
   - ❌ 不说明项目状态
   - ❌ 不指定参考文档

3. **模糊的需求**
   - ❌ "帮我做点什么"
   - ❌ "改进一下"

4. **忽略架构原则**
   - ❌ 不遵循 Clean Architecture
   - ❌ 破坏分层
