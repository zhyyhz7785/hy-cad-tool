## 一句话结论

`HyCADTool.Refactored` 已经从“旧命令搬运区”进入“可持续演进的 AutoCAD 插件平台骨架”阶段。

当前重点已经不是证明重构方向对不对，而是：

1. 继续迁移剩余高价值命令
2. 收口过渡态代码
3. 统一已有模式，减少风格混乱

---

## 一、先记住这 6 件事

### 1. 项目已经有明确分层

- `Domain`：纯数据、算法、值对象、接口
- `Infrastructure`：AutoCAD 适配、绘图、数据库、扩展字典、配置实现
- `Presentation`：命令、面板、ViewModel、插件入口
- `Test`：热重载联调入口，不是传统单元测试

### 2. 当前最成熟的重构模块

- 钢筋命令整组
- 底板配筋整套流程
- 标高命令整组
- 尺寸标注独立命令
- 地脚螺栓整组
- 设备基础命令组
- 桩基 / 聚类 / DCEL 基础能力

### 3. 当前最重要的统一入口

- 正式命令入口：`Presentation/Commands/CommandRegistry.cs`
- 插件启动入口：`Presentation/PluginInitializer.cs`
- 统一面板入口：`hy`
- 测试入口：`Test/TestCommand.cs`

### 4. 现在的主配置源不是 `config.json`

真正高频使用的是：

- `SettingsPanelViewModel`
- `%APPDATA%\HyCADTool\hy-settings.json`

它负责：

- `Scale`
- 样式参数
- 钢筋参数

`config.json` 现在更像辅助配置，主要给桩基/容差/路径等少数模块使用。

### 5. 面板按钮不能直接碰 AutoCAD 业务

统一模式是：

`ViewModel -> PendingCommand -> _HyExec -> AutoCAD 命令线程`

也就是说，涉及选择、绘图、数据库写入的按钮，默认都应该走命令路由，不要直接在 WPF 点击事件里做。

### 6. 当前开发联调规则非常简单

只记住：

`改代码 -> VS 编译 -> C2 -> C1`

并且切换测试命令时：

- 只改 `HyCADTool.Refactored/Test/TestCommand.cs`

## 二、这次重构真正完成了什么

不要把当前项目理解成“已经重写完了所有命令”。

更准确的理解是：

### 1. 你已经把项目主干搭起来了

已经形成了这些稳定外壳：

- 命令统一注册
- 插件统一初始化
- 面板统一管理
- 配置统一主源
- 测试统一入口
- 多文档 ViewModel 切换

这意味着以后继续迁移新模块，不需要每次重新设计基础设施。

### 2. 你已经形成了一套可复制的迁移模式

推荐的工作路径已经比较清楚：

1. 先把旧逻辑拆开
2. 纯规则和算法放 `Domain`
3. AutoCAD 实现细节放 `Infrastructure`
4. 命令和 UI 编排放 `Presentation`
5. 最后接入 `CommandRegistry` 和 `TestCommand`

### 3. 你已经解决了几个 AutoCAD 插件里最容易失控的问题

- 命令入口分散
- WPF 与 AutoCAD 命令线程边界混乱
- 样式与参数来源不统一
- 联调路径不固定

这些问题一旦解决，项目后续维护难度会显著下降。

## 三、当前项目状态怎么理解

### 不是“还在起步”

不是。

主框架已经成型，多个核心业务模块已经迁完，说明方向已经跑通。

### 也不是“已经彻底收口”

也不是。

目前还存在明显过渡态：

- 部分命令仍依赖 `ServiceLocator`
- 部分位置仍直接 `new Service()`
- 某些模块还是静态服务风格
- 配置系统仍是双轨并存
- 局部还保留 `TODO` / `NotImplementedException`

### 所以当前最准确的判断是

项目处在：

**“主干已经稳定，正在从功能迁移转向架构收口”**

## 五、现在不要再混淆的几个关键判断

### 1. `Scale` 以谁为准？

以 `SettingsPanelViewModel.Current.Scale` 为主。

### 2. 新参数优先加哪？

优先考虑 `SettingsPanelViewModel`。  
如果是底板配筋专用参数，再考虑 `BaseReinforcementConfig`。

### 3. 测试入口改哪？

只改 `Test/TestCommand.cs`。

### 4. 重构时最重要的顺序是什么？

`Domain -> Infrastructure -> Presentation`

### 5. 什么叫“好迁移”？

不是把旧代码复制过来，而是：

- 参数来源清楚
- 命令足够薄
- AutoCAD 依赖被压到 `Infrastructure`
- 能通过 `C2 -> C1` 稳定联调

## 六、未来要做的事情

这里不追求“列全”，只保留最值得做、最能降低混乱的事情。

### P0：收口过渡态

这是当前最重要的事情。

目标：

- 减少命令里直接 `new Service()`
- 减少静态服务式调用
- 保持新代码继续靠近 DI 和分层边界
- 让“新迁移模块”和“成熟模块”风格越来越一致

如果这一层不做，项目会长期停留在“两套写法并存”。

### P1：继续迁移剩余高价值命令

优先迁那些：

- 实际常用
- 和现有基础设施能直接复用
- 迁完后能明显补齐一条业务链

比起“多迁几个低频命令”，更有价值的是把关键链路补完整。

### P2：补齐未闭环能力

重点看：

- 钢筋标注剩余能力
- 配置写回未完成处
- 几何算法层遗留 TODO

这些通常不是大功能，但会影响“完成度感”。

### P3：扩大统一面板覆盖面

已经稳定的模块，后面可以逐步纳入统一面板，而不是长期保留“有些只能敲命令”。

目标不是 UI 漂亮，而是：

- 入口统一
- 参数统一
- 测试统一
- 后续维护统一
