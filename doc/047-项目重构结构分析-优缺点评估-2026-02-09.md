## 一、整体架构概览

项目采用 **Clean Architecture + DDD** 分层，总计约 **200 个 C# 文件**：

| 层 | 文件数 | 职责 | 平台依赖 |
|---|---|---|---|
| **Domain** | 72 | 领域模型、纯算法、接口定义 | 无 (99.2%) |
| **Infrastructure** | 74 | AutoCAD 适配器、DI 配置 | AutoCAD API |
| **Presentation** | ~50 | 命令、WPF 面板、ViewModel | AutoCAD + WPF |
| **Test** | 3 | 热重启测试 | AutoCAD |

依赖方向：`Presentation → Infrastructure → Domain`（符合 Clean Architecture）

## 三、优点分析（7 项）

### 3.1 Domain 层平台无关性极高（99.2%）

**这是项目最大的亮点。** 72 个文件中仅 `ISelectionFilterService.cs` 一个文件引用了 AutoCAD 命名空间。所有核心算法（LineOverKill、CurveBreak、DCEL、聚类、凸包等）都是纯 C# 实现，可直接迁移到 Blender Python。

值对象设计优秀：`Point2D`、`Line2D`、`Polygon2D` 等几何类型用 struct/class 封装，不可变性好，运算符重载完整，是 AutoCAD `Point3d` 的平台无关替代。

### 3.2 丰富的领域算法库

Domain/Services 包含 41 个服务文件，涵盖：
- 线段去重合并（`LineOverKillService`，1683 行，含空间索引和扫描线算法）
- 曲线打断（`CurveBreakService`）
- DCEL 双连通边表构建
- 凸包、聚类、多边形偏移
- 标高解析和三维计算

这些都是**可复用的几何算法资产**，是项目最有价值的部分。

### 3.3 实体设计遵循 DDD 规范

- 抽象基类 `BuildingElement`（Id、Name、Elevation 等通用属性）
- 工厂方法创建实体（`Wall3D.CreateNormalWall()`、`Slab3D.Create()`）
- 聚合根模式（`SurfaceBasedModel` 包含 TopSurface、BottomSurface、WallSolid、SlabSolid）
- 业务逻辑内聚（`Pile.CalculatePileArea()` 封装在实体内部）

### 3.4 Infrastructure 适配器模式清晰

- `GeometryConverter` 负责 Domain ValueObject ↔ AutoCAD 类型的双向转换
- `DrawingService`、`LayerService` 等正确实现 Domain 接口
- 构造函数注入做得好（如 `DrawingService(ILayerService layerService)` 带 null 检查）
- 选择过滤系统设计完善（7 种过滤器 + Builder 模式）

### 3.5 开发体验优秀

- **热重启机制**（C2/C1）避免反复重启 AutoCAD，开发效率提升约 50%
- `TestCommand.cs` 一行代码切换测试目标，极其方便
- `SimpleLogger` 提供标准化耗时测量（`INFO: 操作名 耗时 xx 毫秒`）
- 极简输出原则（常用命令 1-3 行），用户体验好

### 3.6 MVVM 面板已具规模

6 个面板配套 ViewModel 和 WPF 视图，完成了 UI 基础设施：
- ReinPanel（钢筋参数面板）
- FilterPanel（过滤器面板）
- BaseReinPanel（基础配筋面板）
- PilePanel（桩基面板）
- ClusterPanel（螺栓聚类面板）
- SettingsPanel（设置面板）

### 3.7 配置系统设计完善

- 强类型配置（`GlobalConfiguration`、`ReinforcementConfiguration` 等 13 个配置类）
- JSON 配置加载/保存
- 全局配置与模块配置分离
- 配置值对象封装（`ScaleConfig`、`TextStyleConfig`、`DimensionStyleConfig` 等）

## 四、缺点与问题分析（7 项）

### 4.1 ⚠️ ISelectionFilterService 违反平台无关原则（严重）

```csharp
// Domain 层直接引用了 AutoCAD 类型！
using Autodesk.AutoCAD.DatabaseServices;
using Autodesk.AutoCAD.EditorInput;

public interface ISelectionFilterService
{
    SelectionFilter Build(...);                              // AutoCAD 类型
    SelectionFilter BuildFromEntity(Entity prototype, ...);  // AutoCAD 类型
}
```

**影响**：这个接口放在 Domain 层，破坏了整个 Domain 的平台独立性。

**建议**：
- 方案 A：将接口移到 `Infrastructure/AutoCAD/Interfaces/`
- 方案 B：创建平台无关的 `ISelectionCriteria` 抽象，在 Infrastructure 层转换为 AutoCAD `SelectionFilter`

### 4.2 ⚠️ 命令层 DI 模式不一致（中等）

三种模式并存，缺乏统一规范：

| 模式 | 示例命令 | 问题 |
|---|---|---|
| ServiceLocator 解析 | `OverKillCommand`、`BreakCurvesCommand` | ✅ 可接受的妥协 |
| 双构造函数 | `DCELCommand` | ❌ DI 构造函数被忽略 |
| 直接 new | `SurfaceBasedElevation3DCommand` | ❌ 完全绕过 DI |

`DCELCommand` 的双构造函数尤其成问题——AutoCAD 只会调用无参构造函数，而无参构造函数直接 `new CurveSegmentExtractor()`，Autofac 注册的配置完全无效。

**建议**：统一为 ServiceLocator 模式（AutoCAD 约束下的最佳实践）：
```csharp
public DCELCommand()
{
    _curveExtractor = ServiceLocator.Resolve<ICurveSegmentExtractor>();
    _dcelBuilder = ServiceLocator.Resolve<IDCELBuilderService>();
    _dcelRenderer = ServiceLocator.Resolve<IDCELRenderer>();
}
```

### 4.3 ⚠️ 缺少 Application 层（架构缺陷）

标准 Clean Architecture 是四层：

```
Presentation → Application → Domain
                    ↑
              Infrastructure
```

当前项目缺少 **Application 层**（Use Cases / Application Services），导致：
- 命令文件直接承担了编排逻辑（本应在 Application 层）
- 业务流程难以跨命令复用
- 跨平台迁移时编排逻辑需要重写

**建议**：对于复杂命令（如基础配筋全流程 `hyb5a`），考虑引入 Application Service 封装编排逻辑。简单命令可不需要。

### 4.4 ⚠️ 单元测试为零（严重）

Test 目录只有 3 个文件，全部是集成测试基础设施。缺少：
- 单元测试项目（`HyCADTool.Refactored.Tests`）
- Domain 层算法的自动化测试
- Mock/Stub 基础设施

对于 41 个 Domain 服务和 43 个值对象，零测试覆盖率意味着重构时没有安全网。

**建议**：
1. 创建 `HyCADTool.Refactored.Tests` 项目（.NET Framework 4.8 + xUnit/NUnit）
2. 优先为 `LineOverKillService`、`CurveBreakService`、`DCELBuilderService` 编写单元测试
3. 值对象（`Point2D`、`Polygon2D`、`Elevation`）的相等性和运算符测试

### 4.5 部分代码被注释排除编译（隐患）

`.csproj` 中多个面板文件被注释掉：
- ReinPanel、BaseReinPanel、PilePanel、ClusterPanel 的部分 ViewModel/View
- `ShowMainPanelCommand.cs`
- 基础配筋服务文件

约 30% 的 Presentation 层代码实际不参与编译，可能存在编译错误而不自知。

**建议**：要么恢复编译，要么明确标记为"待迁移"并从项目中移除。

### 4.6 Domain 层服务组织略显混乱

- `Services/` 根目录直接放了 18 个文件（`IReinService.cs`、`DCELSettings.cs` 等）
- `GeometryAlgorithms/` 下混合了接口和实现（`IClusteringService.cs` 与 `ClusteringService.cs` 同目录）
- Domain 接口分散在两处：
  - `Domain/Interfaces/`（12 个）
  - `Domain/Services/GeometryAlgorithms/`（6 个）

**建议**：统一策略——要么接口全部放 `Interfaces/`，要么与实现紧邻放置（推荐后者，按功能聚合）。

### 4.7 ServiceLocator 全局静态（已知妥协）

虽然团队已记录这是 AutoCAD 约束下的妥协，但需注意：
- 全局静态状态使并发测试不可能
- 容器生命周期管理不够精细
- 未来 AutoCAD .NET 6+ 版本可能支持原生 DI
