## 二、当前项目的真实状态（代码实证）

### 2.1 架构完成度

```
Domain       (78 文件)  ✅ 几何值对象、算法服务基本完整
Infrastructure (87 文件)  ✅ AutoCAD 封装、扩展方法丰富
Presentation   (40+ 文件) ⚠  命令迁移约 30%，面板系统已跑通
Test           (3 文件)   ✅ 热重启测试流程正常工作
```

### 2.2 DI 使用现状（问题核心）

当前项目存在 **四种** 获取依赖的方式，这是最大的混乱源：

| 方式 | 出现位置 | 问题 |
|------|---------|------|
| ① `ServiceLocator.Resolve<T>()` | ShowPanelCommand、OverKillCommand 等 15+ 文件 | 经典反模式，隐藏依赖 |
| ② `new XxxCommand()` | SettingsPanelViewModel、PilePanelViewModel | 完全绕过 DI |
| ③ `new XxxService()` | DrawPilesCommand、DCELCommand | 同上，绕过 DI |
| ④ `ViewModel.Current` 静态属性 | SettingsPanelViewModel、PilePanelViewModel、ClusterPanelViewModel | 全局状态，相当于另一种 ServiceLocator |

**根本原因**：AutoCAD 插件的命令入口是静态方法（`[CommandMethod]`），无法直接构造函数注入。项目选择了 ServiceLocator 作为妥协，但随后又在更多地方直接 new，导致 DI 容器注册了大量服务却未被使用。

### 2.3 Domain 层纯净度（有破坏）

Domain 层 78 个文件中，发现 **2 个文件** 直接引用了 `Autodesk.AutoCAD`：

1. **`Domain/Models/Cluster/ClusterResult.cs`**：
   - 使用 `Point3d`（应使用 Domain 自己的 `Point2D`/`Point3D`）
   - 使用 `Polyline`（应使用 `Polygon2D` 或仅存储坐标数组）
   - 使用 `Extents3d`（应使用 `BoundingBox`）

2. **`Domain/Interfaces/ISelectionFilterService.cs`**：
   - 使用 `SelectionFilter`、`Entity`、`LineWeight`
   - 这个接口本不该在 Domain 层（选择过滤是 AutoCAD 特有概念）

其他 76 个文件经验证**纯净**，说明污染是局部的、可修复的。

### 2.4 命令实现模式

当前命令分两种写法，差异很大：

**写法 A（较好）—— 通过 DI 获取服务**：
```csharp
// OverKillCommand.cs
var lineService = ServiceLocator.Resolve<LineOverKillService>();
var editorService = ServiceLocator.Resolve<IEditorService>();
```
虽然用了 ServiceLocator，但至少服务是容器管理的。

**写法 B（问题大）—— 直接 new**：
```csharp
// DrawPilesCommand.cs
var layoutService = new PileLayoutService();
var drawingService = new PileDrawingService();
```
完全绕过 DI，服务的依赖关系不可见。

**写法 C（问题更大）—— ViewModel 中 new Command**：
```csharp
// SettingsPanelViewModel.cs
CmdGj = new RelayCommand(() => SendCommand(
    () => new Commands.DrawReinforcementCommand().Execute()));
```
Command 在 ViewModel 构造函数中被 new 出来，既绕过 DI，又让 ViewModel 承担了命令工厂的职责。

### 2.5 好的方面（值得保留）

| 方面 | 现状 |
|------|------|
| 几何值对象体系 | 21 个 Geometry ValueObject，设计优秀（Point2D/Line2D/Polygon2D/DCEL） |
| 扩展方法 | EntityExtensions、MLeaderExtensions 等，封装到位 |
| 面板系统 | PanelManager + PaletteSet + 多文档支持，完成度高 |
| 热重启机制 | C2/C1 工作流稳定，开发效率高 |
| 命令路由 | SendCommand → C1 → AutoCAD 命令线程，正确解决了 WPF 线程问题 |
| 配置系统 | config.json + 分层加载 + 面板覆盖，灵活够用 |

## 三、行动方案（按优先级排序）

### Phase 1：修 Domain 层污染（1-2 小时）

**目标**：让 Domain 层重新回到 100% 平台无关。

#### 任务 1.1：修复 ClusterResult.cs

将 AutoCAD 类型替换为 Domain 自有类型：

```
Point3d         → Point2D（Domain/ValueObjects/Geometry/Point2D.cs）
Polyline        → List<Point2D>（或 Polygon2D）
Extents3d       → BoundingBox（Domain/ValueObjects/Geometry/BoundingBox.cs）
```

在 Infrastructure 的 ClusterFactoryService 或 ClusterDrawService 中做转换。

#### 任务 1.2：移动 ISelectionFilterService

`ISelectionFilterService` 整个接口搬到 `Infrastructure/AutoCAD/Interfaces/`：
- 选择过滤是 AutoCAD 特有概念，不属于 Domain
- 如果有 Domain 服务需要"选择"能力，定义一个平台无关的 `IEntitySelector` 接口

### Phase 2：统一命令获取依赖的方式（2-3 小时）

**目标**：所有命令通过 DI 容器获取依赖，消除直接 new。

**策略**：不强求删除 ServiceLocator（AutoCAD 静态入口的妥协是合理的），但要确保 **服务永远从容器获取，不直接 new**。

#### 任务 2.1：修复命令中的 new Service()

```csharp
// DrawPilesCommand.cs 修改前
var layoutService = new PileLayoutService();
var drawingService = new PileDrawingService();

// DrawPilesCommand.cs 修改后
var layoutService = ServiceLocator.Resolve<PileLayoutService>();
var drawingService = ServiceLocator.Resolve<PileDrawingService>();
```

同样修复：`PileVoronoiOptimizationCommand`、`SurfaceBasedElevation3DCommand`、`DCELCommand`。

确保 AutofacModule 中已注册这些服务（`PileDrawingService` 当前未注册，需补充）。

#### 任务 2.2：修复 ViewModel 中的 new Command()

**方案**：ViewModel 不 new Command，改为通过 lambda 延迟执行 + ServiceLocator 获取：

```csharp
// SettingsPanelViewModel 修改前
CmdGj = new RelayCommand(() => SendCommand(
    () => new Commands.DrawReinforcementCommand().Execute()));

// SettingsPanelViewModel 修改后
CmdGj = new RelayCommand(() => SendCommand(
    () => ServiceLocator.Resolve<Commands.DrawReinforcementCommand>().Execute()));
```

或者更简单的方式——Command 本身无状态时直接 new 是可以接受的，但 **如果 Command 需要注入服务**（如 DrawReinforcementCommand 需要 IReinService），则必须走容器。

**实际判断**：当前大部分 Command 在构造函数中不注入任何服务（它们内部用 ServiceLocator 或直接 new），所以 ViewModel 中 `new XxxCommand()` 在功能上是正确的。**真正要修的是 Command 内部的 new Service()**（任务 2.1）。

ViewModel 中的 `new Command()` 可以暂时保留，因为 Command 是无状态的轻量对象。等后续 Command 改为构造函数注入后，再统一改 ViewModel 的写法。

### Phase 3：补注册缺失的服务（30 分钟）

检查 AutofacModule，确保以下服务已注册：

| 服务 | 当前状态 | 需要 |
|------|---------|------|
| `PileLayoutService` | ❌ 未注册 | 注册为 SingleInstance |
| `PileDrawingService` | ❌ 未注册 | 注册为 SingleInstance |
| `SlabGenerationService` | ❌ 未注册 | 注册为 SingleInstance |
| `WallGenerationService` | ❌ 未注册 | 注册为 SingleInstance |

### Phase 4：消除 ViewModel.Current 静态访问（后续）

这不紧急，但方向明确：

- `SettingsPanelViewModel.Current` → 已通过 SendCommand + C1 路由，实际上命令执行时在正确的上下文中，可以通过参数传递替代
- `PilePanelViewModel.Current` → 同上
- `ClusterPanelViewModel.Current` → 同上

**暂时保留**，因为 Current 访问模式虽然不优雅，但在 AutoCAD 单线程命令上下文中是安全的。

## 四、不建议做的事（避坑指南）

### 4.1 不要拆多个 .csproj

外部建议拆成 `HyCAD.Domain.csproj`、`HyCAD.Infrastructure.csproj`、`HyCAD.Presentation.csproj`。

**不建议**：
- AutoCAD 插件加载的是单个 DLL，拆项目意味着要管理多个 DLL 的版本和加载顺序
- 热重启 C2 需要释放/重加载 DLL，多个 DLL 会增加复杂度
- 当前单项目 + 命名空间分层已经够用

### 4.2 不要引入 Application 层

外部建议加 `Application/UseCases/` 层，在 Command 和 Domain 之间加一层。

**不建议**：
- 当前 Command 直接编排 Domain + Infrastructure，代码清晰、直接
- UseCase 层在团队项目中有价值（多人协作时约束职责边界），个人项目只增加模板代码
- 如果后续命令逻辑真的复杂到需要复用，再提取不迟

### 4.3 不要用 NTS 替换自定义几何

外部建议用 NetTopologySuite 的 `Point`/`Polygon` 替换自定义的 `Point2D`/`Polygon2D`。

**不建议**：
- 自定义几何类型已深度集成到 Domain 层 21+ 个文件
- 替换工作量巨大（改接口、改算法、改转换器）
- NTS 的 API 风格（Java 移植）和项目现有风格不一致
- 当前几何类工作正常，没有精度问题的实际证据

### 4.4 不要过早建单元测试

外部建议立即建 xUnit 项目。

**不建议（现阶段）**：
- 70% 的命令还没迁移，API 还在变化，写测试会被反复修改
- C2/C1 + 肉眼看图的测试方式在 CAD 领域是最有效的（几何结果需要可视化验证）
- 等迁移完成、API 稳定后再补测试

## 五、外部建议中的有价值观点（留作长期参考）

虽然不建议现在做，但以下观点在长期维护中值得留意：

1. **几何容差统一**：当前 AutoCAD（double）、NTS（double+拓扑容差）、Clipper2（int64缩放）三套精度体系并存。如果将来出现浮点精度 Bug，优先建立统一的 `ITolerancePolicy`

2. **事务管理统一**：当前 DatabaseService、DrawingService 等可能各自开事务。如果将来出现 `eLockViolation`，考虑引入统一的事务边界管理

3. **AutofacModule 模块化**：当前 270 行的注册方法还可以管理，但如果超过 400 行，建议拆成 `GeometryModule`、`ReinforcementModule`、`PileModule` 等子模块

4. **DCEL 性能**：如果处理超大图纸（10000+ 实体），C# 的 class 对象开销可能成为瓶颈，届时考虑 struct + 数组索引
