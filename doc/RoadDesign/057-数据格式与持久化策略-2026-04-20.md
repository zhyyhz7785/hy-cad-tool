# 057 · 数据格式与持久化策略（2026-04-20）

> 目标：在 **HyCAD 道路模块当前实现** 的基础上，把 **JSON / DWG / USD** 三类载体、**图元身份（Xdata）** 与 **领域模型** 的关系说清楚，并给出 **可执行的策略结论** 与 **后续优化方向**。  
> 读者：做持久化、交换格式、Blender 管线或和 Civil 3D / LandXML 对标的工程师。  
> 对位：[053-领域类型关系](./053-道路设计领域类型关系-2026-04-20.md)（类型与 GUID）、[056-当前文件系统](./056-当前文件系统说明-2026-04-20.md)（目录与落盘）、[04Pipeline_CAD_Blender_Lumion](./04Pipeline_CAD_Blender_Lumion.md)（演进路线）。

## 0. 一句话结论（先读这里）

| 问题 | 本项目结论 |
|------|------------|
| 主存用什么？ | **`.roaddesign.json`（Newtonsoft 序列化的 `RoadDesign` 聚合根）** 为 **语义与协作的单一事实源**；DWG 为 **施工图视图与拾取交互**。 |
| JSON 与 DWG 谁说了算？ | **JSON 说了算**（线位几何、纵断面、交叉口参数、模板等）；DWG 上的 Polyline/Arc/Line 是 **渲染 + 与 AutoCAD 工具链兼容**，通过 **`HY_ROAD` Xdata（`ID` + `KIND` + `SCHEMA`）** 绑回领域 `Guid`。 |
| 全是 Xdata 还能区分类型吗？ | **能**。类型不靠 AutoCAD 的 `DXF` 类名区分，而靠 **`KIND` 字符串**（已扩展十余种，含 `Control.*` 控制体）。`ID` 区分实例。 |
| 和 USD 比？ | **USD 不是 v1 的替代主存**：强项是场景合成与非破坏性编辑，弱项是 **道路行业语义、法规校验、施工图习惯**；适合作为 **v2+ 可视化 / DCC 交换层**，而非取代 `RoadDesign` JSON。 |
| 最佳组合策略 | **JSON（权威模型） + DWG（视图 + Xdata 句柄） + 可选 LandXML（行业交换） + 远期 USD/gltf（三维合成）**。 |

## 1. 主存储：JSON —— 与 DWG、USD 的深度对比

### 1.1 三者的角色（不要用「谁更好」一刀切）

| 维度 | `.roaddesign.json`（本项目） | DWG / DXF | USD（Universal Scene Description） |
|------|------------------------------|-------------|-------------------------------------|
| **设计意图** | 领域对象树：Alignment、Profile、Intersection、Template… | 通用 CAD 数据库：图元 + 样式 + 布局 | 场景图：Prim、Layer、Variant、合成视图 |
| **语义层级** | **高**：桩号、断链、CJJ 校核、PI 表、控制体等 **道路语义** 一等公民 | **低到中**：几何强、行业语义靠插件/对象扩展 | **中**：几何与材质强；**道路业务语义**需自定义 Schema / 自定义 API |
| **人类可读 / 版本管理** | **极好**（文本 diff、CR、CI 校验） | 差（二进制为主，虽有 DXF） | 尚可（`.usda` 文本；二进制 `.usdc` 不利于 diff） |
| **与 AutoCAD 一体性** | 旁路文件，需 **同步策略** | **原生**（块、标注、出图样式） | 无（需导出管道） |
| **多软件协作** | 易（HTTP/文件监听/未来 JSON Patch） | 强在二维 CAD 圈 | 强在 **影视 / Omniverse / 大型 3D 管线** |
| **约束与校验** | 在 Domain 层集中做（C#） | 分散在实体特性与自定义 | 在组合层做，**不自带道路规范** |
| **本项目中的事实** | `RoadJsonExportService` 原子写盘、`SchemaVersion` 演进 | `HyRoadXdata` 写 **句柄**，几何可与 JSON 再同步 | `04Pipeline` 中规划为 **Blender/Lumion 侧**，非当前主存 |

**结论**：  
- **JSON**：最适合作为 **「道路设计状态机」的权威快照** —— 与 `RoadDesignRegistry`、事件总线、单元测试、未来 Blender 监听 **同构**。  
- **DWG**：最适合作为 **「交付物与编辑界面」** —— 用户锁定的行业习惯（图层、打印、标注）。  
- **USD**：更适合 **「大场景合成、LOD、材质、镜头」**；若未来要上 Omniverse / 复杂 3D 协作，可作为 **从 `RoadDesign` 编译出的视图**，而不是替代 JSON 的源数据库。

### 1.2 「深度」差异：为何不是二选一

- **DWG 深度**：在 **实体与块引用、注释性、图纸空间** 上无可替代；但 **Alignment 作为 Civil 3D 对象** 与 **作为 Lightweight Polyline** 在 **数据模型层** 不等价——后者缺少内置 Sub-entity 表，故你们在 Domain 用 **PI 分解器 + 自有表** 补语义。  
- **USD 深度**：在 **组合、变体、时间采样** 上强；但 **平面线位 + 纵断面 + 国标横断面** 的 **业务对象** 放在 USD 里会变成 **自定义 Prim + 自研校验**，重复造轮子。  
- **JSON 深度**：在 **领域不变量、版本迁移、测试** 上最深；代价是 **必须与 DWG 双向约束**（SAVEAS、孤儿实体、重绑），已由 `RoadDesignRegistry`、`RebindForDocument`、Xdata 扫描等承接。

## 2. 图形多为 Polyline / Arc / Line：如何与「原生 AutoCAD」区分？Xdata 策略

### 2.1 现象

道路模块生成的可见对象，大量是 **`Polyline`（含 bulge 弧段）、`Line`、`Arc`**。从 **DXF 层面** 看，与用户手画的同类图元 **无法区分** —— 这是 **有意选择**：  
- 用户可用 **常规 CAD 命令**（偏移、修剪、夹点）操作几何（在你们允许的流程内）；  
- 导出 PDF/第三方插件时 **兼容性最大**。

**语义区分** 不放在「实体类名」，而放在 **附加数据**：当前实现为 **`RegAppName = HY_ROAD` 的 Xdata**。

### 2.2 Xdata 方案：你们已落地的契约

实现见 `HyCADTool.Refactored/Infrastructure/AutoCAD/Xdata/HyRoadXdata.cs`：

- **`ID`**：`Guid` 字符串，与 `RoadDesign` 内领域对象 **一致**。  
- **`KIND`**：领域类型标签（如 `Alignment`、`Intersection`、`GeometryPointLabel`、`Control.ReferencePoint` 等）。  
- **`SCHEMA`**：与 `SchemaVersion.Current` 对齐，便于将来做 **读侧迁移**。

**设计取舍（代码注释已写）**：  
- 选用 Xdata 而非把大块 JSON 塞进 `ExtensionDictionary` 的 **首要原因** 是：GUID + 标签体量小，**远低于 Xdata 16KB 上限**，且 **DXF 导出可携带**、查询路径简单。  
- 工程里另有 `ExtensionDictionaryService` 存 **通用 JSON 块**（其他模块），与道路 **ID+KIND 轻量句柄** 分工不同：**道路侧以 Xdata 为统一句柄层**。

### 2.3 优缺点（针对道路插件）

**优点**

1. **与原生实体操作兼容**：图元仍是标准 `Entity`，不强制自定义 `Entity` 类（避免宿主加载与复制类 ID 等负担）。  
2. **可发现性**：可按 `RegAppTable` + `GetXDataForApplication("HY_ROAD")` 批量扫描。  
3. **类型可辨**：**不靠** `Polyline` vs `Line`，而靠 **`KIND`**；同一 `Polyline` 上可明确是 `Alignment` 还是别的（若业务允许挂接）。  
4. **跨会话稳定**：`Guid` 在 JSON 与 DWG 间 **对齐**，配合 SAVEAS 重绑，比纯 `ObjectId` 更适合「文档级持久化故事」。

**缺点与风险**

1. **用户破坏几何**：夹点编辑后，**JSON 中的 `Centerline` 可能滞后**，需依赖 **命令重同步 / 工作台提交**（你们已在部分流程用「提交/登记」收口）。  
2. **复制（Copy）行为**：AutoCAD 复制实体时 **Xdata 常一并复制**，可能导致 **重复 GUID** —— 需要 **粘贴/复制检测** 或 **命令层拒绝重复 ID**（应在文档中列为 **已知风险与对策**）。  
3. **16KB 上限**：当前只存 ID/KIND/SCHEMA 无压力；若未来把 **整段参数** 塞进 Xdata，会触顶 —— 大载荷应回 **JSON 或 ExtensionDictionary**。  
4. **过滤与图层**：仅靠 Xdata 不够表达「显示样式」，需 **`HyRoadLayers` 等图层约定** 联合。

### 2.4 「如果都是 Xdata，类型还好区分吗？」

**好区分** —— 因为 **类型字段是 `KIND`，不是 DXF 类型**。  

- 多个道路对象都挂在 **标准 Polyline** 上时：**`KIND` 不同 → 语义不同**（例如 `Alignment` vs `CorridorPlan`）。  
- 同一 **交叉口** 下多种附属图元（横道、停止线、盲道）可 **共享同一 `Intersection.Id`**，`KIND` 区分子类（`Crosswalk`、`StopLine`…），与 [053](./053-道路设计领域类型关系-2026-04-20.md) 的描述一致。  
- **控制体** `Control.*` 与实体分流：代码层已有 `IsControlKind` 帮助 **扫描时分流**。

**注意**：若两条业务线都给 **同一实体** 写 Xdata，会 **互相覆盖**（`HyRoadXdata.Write` 会重写整段 `HY_ROAD` 数据）。**最佳实践**是：**一个实体只归属一条道路语义**；多语义用 **分组、块或分别实体**。

### 2.5 最佳策略（结合目标的「可和 AutoCAD 一样操作」）

| 层级 | 建议 |
|------|------|
| **身份与类型** | 继续 **统一 `HY_ROAD` + `ID` + `KIND` + `SCHEMA`**；新增道路子类 **只加 `KIND` 常量**，避免多套 RegApp。 |
| **几何权威** | **以 JSON（Domain）为真理**；DWG 为展示时，用 **显式命令**（提交线位、同步中心线）把几何写回 `RoadDesign`。 |
| **大参数 / 历史** | 放 **JSON**（`.roaddesign.json` + `*.roaddesign.history/`），不放 Xdata。 |
| **可选增强** | 对 **单实体需挂载复杂 JSON** 的模块，可 **复用 `ExtensionDictionaryService`**，但仍建议 **用 `ID` 与聚合根关联**，避免「双真理源」。 |

## 3. 当前数据存储已做的工作 vs 可优化点（对照常见软件）

### 3.1 已实现（代码级）

- **聚合根与版本**：`RoadDesign` + `Schema`（当前 **1.2**）+ `MinimumSupported` 校验（`RoadJsonExportService.Load`）。  
- **落盘路径**：`<DWG 同名>.roaddesign.json`，`SaveForDocument`：**非空才写、未保存 DWG 跳过、原子替换**（tmp + `File.Replace`）。  
- **运行时注册表**：`RoadDesignRegistry` 按文档名持有内存态；**SAVEAS / 重绑** 与对齐服务协同（见 `RoadAlignmentService` 文档注释链）。  
- **DWG 句柄**：`HyRoadXdata` 多 `KIND`；交叉口附属共享 `Intersection.Id` 等 **幂等清理** 策略（053）。  
- **历史**：`HistoryService` + `history-index.json` + 快照 JSON（056）。  
- **交换**：LandXML 导入导出（051/054）；**Domain 纯 C#** 便于测试与未来 Headless。  
- **控制体多态**：`RoadDesign.Controls` + `HyControlJsonConverter`（JSON 多态）。  
- **事件**：`IRoadEventBus` 驱动 UI / 持久化联动。

### 3.2 与常见软件的对比（心智模型）

| 软件 / 格式 | 模型特点 | 与 HyCAD 的对应 |
|-------------|----------|-----------------|
| **Civil 3D** | Alignment/Corridor **原生对象** + 样式体系 | 你们用 **Domain + JSON** 替代「对象数据库」，**CAD 侧更轻**；**施工图习惯**靠 DWG + 自有表与标注命令补。 |
| **鸿业 / 纬地 等** | 自定义实体 + 项目库 | 你们是 **开放 JSON + 标准图元**，**互操作性**更强，**盗版式复制自定义实体**风险更低。 |
| **LandXML** | 行业交换 **平面/纵断面** | 已对接；**权威仍建议 JSON**（LandXML 无法覆盖你们全部控制体与交叉口细节）。 |
| **QGIS / PostGIS** | GIS 矢量 + 属性表 | 若上 GIS，**JSON 可映射 Feature**；CRS 已有 `CrsEpsg` 占位。 |
| **InfraWorks** | 参数化道路模型 + 云协同 | 长期可 **由 JSON 导出中间模型**；短期不必强行对齐。 |
| **USD / glTF** | 可视化与实时 | 适合 **从 Domain 编译**，非源库。 |

### 3.3 建议优化（按性价比排序）

1. **复制/块分解导致的 GUID 重复**：统一 **侦测与重生 GUID** 策略（命令或 `ObjectReactor` 级，需评估性能）。  
2. **几何与 JSON 一致性**：对「可编辑 Polyline」路径，在 **工作台 / 面板** 明确 **「同步到 JSON」** 状态提示与单键修复。  
3. **Schema 迁移**：`SchemaVersion` 已预留叙事；可增加 **显式迁移函数**（读 1.0 → 内存 1.2）而非仅 **最低版本拒绝**。  
4. **校验 CI**：对 `.roaddesign.json` 做 **JSON Schema** 或 **快照测试**，防回归。  
5. **Blender / USD 管线**：继续以 **JSON 为编译输入**（见 `04Pipeline`），USD 作为 **导出目标** 而非主存。

## 4. 总表：本项目「最佳选择」如何落地

| 需求 | 推荐载体 | 说明 |
|------|----------|------|
| 道路业务真理与版本协作 | **`.roaddesign.json`** | 与 Registry、测试、LandXML 一致 |
| 施工图与 AutoCAD 生态 | **DWG + 标准 Entity** | 样式、打印、第三方 |
| 实体 ↔ 领域绑定 | **`HY_ROAD` Xdata** | `ID` + `KIND`，轻量、可 DXF |
| 大块或非结构化载荷 | **JSON 或 ExtensionDictionary** | 避免塞满 Xdata |
| 对外设计交换 | **LandXML（已有）** | 平面/纵断为主 |
| 三维合成与渲染 | **gltf/FBX/USD（规划）** | 由 Domain **生成**，不替代 JSON |
