## 重构背景

### 问题识别

在 HYBC 命令开发完成后，架构审查发现以下问题：

**❌ Application 层违反了 Clean Architecture 原则**

```csharp
// HyApplication/Services/BreakCurvesWorkflow.cs

// 问题 1: 依赖 AutoCAD 特定类型
using Autodesk.AutoCAD.DatabaseServices;  // ❌
using Autodesk.AutoCAD.Geometry;          // ❌

// 问题 2: 依赖 Infrastructure 层
using HyCADTool.Refactored.Infrastructure.AutoCAD.Services;  // ❌

// 问题 3: 方法签名使用平台特定类型
public BreakCurvesResult Execute(
    ObjectId[] selectedObjects,    // ❌ AutoCAD 类型
    Transaction transaction)        // ❌ AutoCAD 类型
```

### Clean Architecture 依赖规则

**标准规则**：
```
Presentation → Application → Domain ← Infrastructure
                    ↑                       ↓
                    └───────────────────────┘
                       (不应该依赖)
```

**当前状态**（违规）：
```
HyApplication.Services.BreakCurvesWorkflow
    ↓ 依赖 (❌ 违规)
Infrastructure.AutoCAD.Services
```

## 重构目标

### 1. 务实原则

**用户要求**: 避免过度工程化

**决策**: 采用简化方案
- ✅ 将 Workflow 移到 Infrastructure 层
- ✅ 承认其 AutoCAD 特定性质
- ✅ 保持 Domain 层纯净（算法仍然平台无关）
- ❌ 不创建复杂的接口抽象（避免过度工程化）

### 2. 架构清晰

**期望架构**：
```
Presentation Layer (Command)
    ↓ 调用
Infrastructure Layer (Workflows + Services)
    ├── Workflows (AutoCAD 特定业务流程)
    └── Services (AutoCAD 数据库操作)
    ↓ 使用
Domain Layer (Platform-Independent Algorithms)
    ├── SpatialIndexService (空间索引，平台无关)
    ├── CurveIntersectionService (交点计算)
    └── CurveSegmentService (曲线分割)
```

### 3. 保持功能稳定

- ✅ 重构不改变任何业务逻辑
- ✅ 保持现有性能指标
- ✅ 通过现有测试用例

## 关键决策记录

### 决策 1: 不创建接口抽象

**背景**: 标准 Clean Architecture 应该在 Application 层定义接口，Infrastructure 层实现。

**用户建议**: 避免过度工程化

**决策**: 直接将 Workflow 移到 Infrastructure 层

**理由**:
1. 务实原则：当前只有 AutoCAD 平台
2. 避免复杂性：不需要过多接口抽象
3. 可扩展性：未来需要时再抽象

**影响**:
- ✅ 简化代码
- ✅ 降低维护成本
- ⚠️ 未来迁移需要重构（可接受）

### 决策 2: Domain 层保持纯净

**背景**: 空间索引、交点计算等算法是平台无关的。

**决策**: 保持这些服务在 Domain 层

**理由**:
1. 100% 平台无关
2. 可直接迁移到 Blender Python
3. 易于单元测试

**影响**:
- ✅ Domain 层可迁移
- ✅ 架构清晰
- ✅ 符合 DDD 原则

### 决策 3: 创建 Workflows 子目录

**背景**: Infrastructure 层需要组织更复杂的业务流程。

**决策**: 创建 `Infrastructure/AutoCAD/Workflows/` 目录

**理由**:
1. 与 Services 区分（Workflows 是流程，Services 是操作）
2. 为未来更多 Workflow 预留空间
3. 目录结构更清晰

**影响**:
- ✅ 目录结构更合理
- ✅ 职责划分清晰

### 经验教训

#### 1. 务实 > 理想

**学到的**:
- 完美的架构抽象不一定适合所有场景
- 避免过度工程化，保持简洁
- 在当前需求和未来扩展之间取得平衡

#### 2. 分层要清晰

**学到的**:
- 创建子目录（Workflows vs Services）有助于职责划分
- 明确注释帮助后续维护
- 命名空间要与物理目录结构一致

#### 3. 测试保证重构安全

**学到的**:
- 编译测试捕获依赖错误
- 功能测试保证行为不变
- 性能测试确认无性能损失
