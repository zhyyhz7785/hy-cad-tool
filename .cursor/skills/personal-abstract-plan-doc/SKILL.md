# 个人高度抽象 Plan 文档

## 定位(读 skill 第一句话先理解)

> **这是"用户自己用的全局视野文档",不是"AI 与用户协作执行的实施文档"。**
> **正确、简洁是第一位;任何细节都是错的。**

| 维度 | 本 skill(00 总体计划) | 具体执行计划(01/02/...) |
|------|-----------------------|------------------------|
| 目的 | 全局视野、快速浏览 | 落地实施、协作执行 |
| 受众 | 用户自己 | 用户 + AI |
| 篇幅 | **≤ 200 行(硬约束)** | 不限 |
| 写代码/接口/技术选型表 | **禁止** | 允许 |
| 阶段细节 | 一行一阶段 | 展开 |
| 演化 | 三大原则永不变 | 每阶段可重写 |

参考实例:`docs/FiniteElement/Plan/00-HYFEA总体计划-高度抽象框架与多年路线-2026-05-17-150400.md`

---

## 何时应用本 skill

用户说:

- "制定一个总体计划" / "做个 00 计划" / "顶层锚定文档"
- "我自己看的" / "只给我自己" / "用作全局视野"
- "高度抽象" / "最简约的抽象" / "提炼精简框架"
- "正确简洁第一" / "不要细节" / "细节会陷入地狱"
- "多年路线" / "未来 5 年 / 10 年怎么走"

**反向触发(不要用本 skill)**:

- "我们一起来实施"/"展开技术方案"/"详细排期"/"写接口"/"列模块清单"
- 这种是"具体执行计划",见同 Plan 目录下 `01-XXX-YYYY-MM-DD.md` 风格

---

## 命名与存放位置

| 字段 | 规则 |
|------|------|
| 编号 | `00`(总体计划永远占 00) |
| 目录 | `<相关领域目录>/Plan/`(如 `docs/FiniteElement/Plan/`、`docs/DataExchange/Plan/`)|
| 文件名 | `00-<主题>-<副标题>-YYYY-MM-DD-HHMMSS.md` |
| 时间戳 | **必须含到秒**(`HHMMSS`),便于同一天多次修订 |

示例:`00-HYFEA总体计划-高度抽象框架与多年路线-2026-05-17-150400.md`

> 子计划留给 `01-阶段1-XXX-YYYY-MM-DD.md` / `02-阶段2-XXX-YYYY-MM-DD.md` ... 由"具体执行计划"流程产出,**不归本 skill 管**。

---

## 三条铁律(永久生效,不可妥协)

1. **篇幅 ≤ 200 行** — 含修订记录、含 mermaid、含表格。超过即重写,不许扩。
2. **禁止细节** — 任何接口签名 / 代码块 / 字段定义 / 详细案例 / 11 维评分表都不进入。
3. **细节下沉** — 任何阶段、模块、机制的展开,都用一句话指向独立子文档(`01-XXX`、`02-XXX` 或同领域已有文档)。

> 用户原话(verbatim,作为本 skill 立项依据):
> "**我希望你用最简约的抽象,提炼出精简的框架制定未来多年的框架,和目录结构。**"
> "**这个文档是高度抽象的,需要的是整体框架,正确、简洁是第一位的,不需要任何细节,细节在以后完成。**"
> "**这个 Plan 和你具体执行计划不同,是高度抽象,只给我自己看,用作全局视野快速浏览用的。**"

## 固定 11 节模板(顺序固定,缺项允许)

```text
0. 一句话定位         一句话讲清"项目长期定位 + 短期目标"
一. 不可变原则        2-4 条,永远不变的工程纪律
二. 目录结构顶层框架   只列稳定顶层,允许"预留位"标注
三. 核心机制精简       (可选)如双轨/分层/插件机制 — 一图一表搞定
四. MVP 定义           (可选)第一个能让用户感知的产物,5-6 行表格
五. 验证方法           证明正确的层次 + 不可妥协的铁律
六. 后期预留           将来才启用的机制,只列"启用时机"
七. 实施步骤           分阶段,每阶段一行,带"核心交付 + 关键依赖"
八. 长期愿景           1/3/5/10 年只列时间与形态,不写技术
九. 与上承文档的关系   列出本文档锚定哪些上层文档
十. 本文档使用约定     强制"只写框架 / 不超 200 行 / 细节下沉"
十一. 修订记录         版本表
```

> 每节有"明确不写"的边界(详见 §「禁写清单」)。

## 表达密度(每节字数预算)

| 节 | 内容上限 |
|----|---------|
| 0 定位 | 1-2 句 |
| 一 原则 | 每条 1 段(2-4 行) |
| 二 目录 | 1 个代码块 + 1 段"依赖方向"约束 |
| 三 机制 | 1 个 mermaid + 1 张 ≤5 行表格 |
| 四 MVP | 1 张 5-7 行表格 |
| 五 验证 | 1 张 3-5 行表格 + 3 条铁律 |
| 六 预留 | 1 张 4-6 行表格 |
| 七 步骤 | 1 个 mermaid + 1 张 ≤7 阶段表格 |
| 八 愿景 | 1 张 4 行表格 |
| 九 关系 | 1 张表格 |
| 十 约定 | 1 张 4 行表格 |
| 十一 修订 | 1 张表格 |

**全文 mermaid 总数 ≤ 3 个;表格总数 ≤ 8 张。**

## 禁写清单(看到就停手)

| 类别 | 禁写示例 |
|------|---------|
| 代码 | 任何 ```csharp / ```python / ```cpp / ```yaml 代码块 |
| 接口 | `public interface IXxx { ... }`、`struct`、`record` 定义 |
| 字段 | `Id : string`、字段类型表 |
| 算法 | 求解器 / 评估器 / 路由器的实现伪代码 |
| 案例 | 具体案例编号清单(如 `T1-001 ~ T1-005`) |
| 维度表 | 多于 5 行的属性 / 维度 / 评分表 |
| 协议 | License 详细映射表 |
| 引用链 | 跨文档的复杂依赖图 |

> 凡发现以上内容,**立刻删除并替换为一句话**:"详见 `[XXX](path)` 第 X 章 / 第 X 节"。

## 完整执行流程(给 AI Agent)

### Step 1 — 对齐 4 个参数

向用户回显确认(未明确则按对话推断):

| 参数 | 示例 | 用途 |
|------|------|------|
| 主题 | HYFEA / 有限元 / 数据交换 / 道路设计 | 文件名主标题 |
| 副标题 | 高度抽象框架与多年路线 | 文件名副标题 |
| 领域目录 | `docs/FiniteElement` / `docs/DataExchange` | 决定 Plan 目录位置 |
| 上承文档清单 | 00 / 001 / ... / 005 | §九"与上承文档的关系" |

### Step 2 — 提炼用户给出的"原则 / 阶段 / MVP"

读用户消息,把原始需求逐条标号(1, 2, 3, ...),并 1:1 映射到模板节:

- "算法与外壳分离" → 一、原则①
- "算法模块化(后续确定)" → 一、原则②
- "双轨模式" → 一、原则③ + 三、机制
- "MVP 一个杆元 / 选直线 / 均布荷载 / 边界条件" → 四、MVP 定义
- "找到正确对比方法" → 五、验证方法
- "后期合作模式预留" → 六、后期预留
- "可分布完成" → 七、实施步骤

**用户每一条原始需求都必须落在模板某节;没落上的需求 → 主动询问用户**。

### Step 3 — 撰写,严格守边界

按 11 节模板顺序写。每节写完先自检:
- 当前总行数(包括本节)是否 ≤ 200?超了就回头精简前面。
- 当前节有没有触犯「禁写清单」?有就删。
- 当前节有没有把"细节"留下?有就用"详见 [XXX](path)"替换。

### Step 4 — 末尾自检(交付前必做)

```text
[ ] 文件名格式 `00-<主题>-<副标题>-YYYY-MM-DD-HHMMSS.md`
[ ] 编号是 00(不是 001 / 01)
[ ] 总行数 ≤ 200
[ ] 11 节模板齐(允许缺第三 / 四 / 六节,其余必有)
[ ] mermaid 总数 ≤ 3
[ ] 表格总数 ≤ 8
[ ] 无代码块、无接口定义、无字段表
[ ] 用户每条原始需求都已覆盖
[ ] §十"使用约定"含"不超 200 行 / 细节下沉"两条强制项
[ ] §十一"修订记录"v1.0 行存在
```

### Step 5 — 交付时简要告知用户

只说三件事:
1. 文档已写在哪里
2. 11 节结构是什么(简短列出)
3. 下一步建议(通常是"针对某个阶段独立发起 01/02 子文档")

## 反例(对照学习)

### ❌ 反例 1:写了具体接口

```csharp
public interface IModuleContract<TIn, TOut, TDiag> { ... }
```

→ 应改为:"每个模块输入输出有明确类型,可被任何符合契约的实现替换。具体接口见 `004` 第四章。"

### ❌ 反例 2:写了 11 维评分表

把 004 的 11 维 Fitness 整张表搬进 00 文档(15+ 行表格)。
→ 应改为:"多标准评估(11 维 Fitness)→ 详见 [004](path) 第七章。"

### ❌ 反例 3:阶段表写了具体周数与人天

```text
阶段 1 - 3 周 - 2 人天 - 实现 EulerBeam2D 类 + 提供 4 个公开方法 ...
```
→ 应改为:"阶段 1 - `EulerBeam2D` + AutoCAD 选线 + 均布荷载 + 悬臂/简支验证 - 依赖阶段 0"。
